# 流程执行与设计器：行业最佳实践与差距分析

> 结论先行：当前执行层是「治理平台里的轻量运行时」，当前设计器是「泳道卡片 + 指标面板」，
> 都不是生产级 BPM 工具。执行层的差距在**运行语义、人工任务生命周期、并发正确性、
> SLA/时间模型、可观测性与变更治理**；设计器的差距在**画布与连线编辑、模型校验、
> 版本/发布治理、协作与 BPMN 一致性**。

## 0. 一句话判断

- **执行层**：能跑线性审批和简单分支，但不能表达并行、会签、子流程、定时器、
  消息等待和异常边界；并发与幂等没有工程保障。
- **设计器**：能改节点属性和看测算，但**不能在界面上自由连线**。分支、回路、条件
  只能靠种子数据、BPMN 导入或直接调 API 产生；这不是「设计器」，更接近
  「泳道卡片列表 + 分析面板」。

## 1. 评估基准

本分析不追求「做成 Camunda」，而是以流程治理平台的定位为边界，选取六组行业基准：

1. **流程语义**：BPMN 2.0 的执行语义 + Workflow Patterns（顺序、并行拆分、同步汇聚、
   排他选择、简单合并、多选、结构化循环、取消、补偿）。
2. **建模工具**：BPMN Modeler 的画布/调色板/连线路由/属性面板/校验/撤销重做/
   版本与发布/协作，参考 Camunda Modeler、bpmn-js、Signavio、ARIS。
3. **人工任务**：候选用户/候选组、认领/释放、委托/转交、四眼原则、会签/仲裁、
   优先级、工作量、SLA 日历、提醒与多级升级、任务历史。
4. **运行工程**：幂等命令、乐观锁/行锁、状态机不变量、事务边界、失败补偿、
   部署版本、运行实例迁移。
5. **集成与事件**：消息关联、定时器、边界事件、Outbox/Inbox、死信与重放、
   契约版本、拉取接口。
6. **运行治理**：执行指标、SLA、链路追踪、审计与任务事件、职责分离、字段级权限、
   多租户、归档与保留期。

参考框架：OMG BPMN 2.0、Workflow Patterns Initiative、Camunda/Flowable 的 BPMN
执行语义、Temporal 的持久化工作流与幂等思想。

## 2. 当前实现盘点

### 2.1 已经具备的能力

| 能力 | 当前实现 | 评价 |
| --- | --- | --- |
| 实例与任务 | `process_instance` / `process_task`，启动快照 | 基础完整，快照是正确设计 |
| 顺序推进 | 单令牌，完成当前任务后推进下一节点 | 适合线性审批，不支持并行 |
| 分支 | 显式 `next_node_key` 或 JSON 条件规则 | 可用，但表达力有限 |
| 人工任务 | 候选角色/组织、默认处理人、认领、完成、经理改派 | 覆盖基础场景 |
| 表单 | 6 种字段类型 + 必填/数值边界/下拉校验 | 够用，但无版本、无复杂校验 |
| 时限/升级 | 到期时间、单级升级、扫描后改派 | 有闭环，但非日历、非多级 |
| 实例控制 | 挂起、恢复、取消、删除 | 运行控制基本可用 |
| 集成 | Outbox 出站、HMAC 入站启动/完成、幂等 `event_id` | 方向正确，缺少 worker/拉取/重放 |
| 审计 | 审计日志、站内通知、Outbox 事件 | 有记录，但无任务事件流 |
| 测试 | 228 条测试，含执行、升级、挂起、入站 | 覆盖主要路径，缺并发/故障注入 |

### 2.2 关键限制（代码证据）

- `app/services/execution.py` 文件头明确写着「单令牌顺序执行」；一个实例同一时刻
  只有一个 OPEN 任务。
- `_advance()` 只沿一条出边推进；开始节点多条出边直接报错。
- `app/services/bpmn.py` 明确拒绝 `parallelGateway` / `subProcess` / `boundaryEvent` /
  `complexGateway` / `eventBasedGateway`，理由是单令牌引擎无法正确处理并行语义。
- 任务操作是「读取 → 校验 → 修改」，没有 `with_for_update`、`version_id_col` 或
  数据库级状态条件更新；并发认领/完成存在竞态。
- 启动实例和完成任务没有幂等键；重复点击或网关重试可能产生重复实例/重复推进
  （入站 Webhook 是例外，有 `event_id`）。
- 没有独立的任务事件表：认领、改派、升级、完成只留下审计日志和当前任务字段，
  无法还原完整的任务生命周期。
- 时限按 `utcnow() + N 小时` 计算，没有工作日历、节假日、时区或 SLA 暂停。
- 挂起会跳过升级扫描，但 `due_at` 不暂停；恢复后可能立即触发升级。
- 通知只有站内信；没有邮件、企业微信、短信，也没有提醒/催办策略。
- 升级只有一级；没有「提醒 → 升级 → 再升级」的层级策略。
- 没有执行指标接口：按时完成率、积压年龄、平均处理时长、瓶颈节点都没有。
- Outbox 只有手动「运行待发送」；没有常驻 worker、死信重放和投递 SLA。
- 表单/规则是 JSON 快照，没有显式版本号；规则不支持 `all/any` 组合、表达式或 DMN。
- 没有部署/版本对象，运行实例不能迁移到新模型；只能取消后重新发起。

### 2.3 当前设计器盘点

| 能力 | 当前实现 | 评价 |
| --- | --- | --- |
| 模型展示 | 按泳道分组的节点卡片 + 箭头，按 `sequence_order` 排列 | 可读，但不是画布 |
| 节点编辑 | 名称、类型、泳道、负责人、作业/等待/成本/返工/审批层/增值 | 字段完整，适合测算 |
| 连线编辑 | 无 UI；新增节点自动接同泳道上一节点 | 不能画分支、回路、条件流 |
| 布局 | `position_x/y` 仅保存和导出 BPMN，界面不按坐标渲染 | 没有拖拽、缩放、对齐、网格 |
| 分支/回路 | 只能由种子数据、BPMN 导入或直接调 API 产生 | 设计器无法表达真实流程 |
| 校验 | 重复 key、悬空连线；分析会提示无入口/发散 | 保存不拦截不可达、无结束、概率异常 |
| 版本 | `model_version` 乐观锁 + 审计日志 | 有并发保护，无版本历史/差异/发布 |
| 协作 | 单人覆盖式保存 | 无草稿/评审/发布、无他人正在编辑提示 |
| BPMN | 结构子集导入导出，导入拒绝并行/子流程/边界事件 | 能交换简单模型，不是 BPMN Modeler |
| 分析 | 按图求期望周期、PCE、返工损失、瓶颈与建议 | 这是当前设计器最强的部分 |

### 2.4 设计器关键限制（代码证据）

- `web/js/views/designer.js` 只提供 `addNode`，自动接「同泳道最后一个节点」；
  没有新增连线、改连线、删除单条连线、设置条件/概率/标签的入口。
- `paintDesigner()` 按泳道和 `sequence_order` 渲染卡片，不使用 `position_x/y`；
  没有画布坐标系、拖拽、缩放、框选、对齐。
- 泳道只是节点上的字符串；没有泳道实体，改一个节点的泳道不会同步同泳道其他节点。
- `save_design` 只校验重复 `node_key` 和悬空连线；不校验多开始、无结束、不可达、
  自环、重复边、分支概率和、网关配对。
- `bpmn.py` 明确拒绝 `parallelGateway` / `subProcess` / `boundaryEvent` /
  `complexGateway` / `eventBasedGateway`；导入是自定义解析器，不做 XSD 校验。
- 没有模型版本历史、差异对比、草稿/评审/发布状态；`model_version` 只是保存计数。
- 没有撤销/重做、复制/粘贴、模板库、批量操作、快捷键。
- 没有协作编辑、他人光标/锁定提示；只有保存时的版本冲突。
- 设计器与执行配置分离：节点表单/规则/分派在「流程执行 → 表单与规则」里配，
  设计器里看不到某个节点绑定了什么表单、规则和 SLA。

## 3. 差距矩阵

优先级：P0 = 生产正确性/不可接受风险；P1 = 专业执行层必备；P2 = 规模化与治理增强。

### 3.1 流程语义

| 能力 | 行业做法 | 当前 | 差距与风险 | 优先级 |
| --- | --- | --- | --- | --- |
| 并行拆分/汇聚 | BPMN parallelGateway + 令牌 | 不支持，直接拒绝 | 无法表达会签、并行审批、跨部门同时作业 | P0 |
| 子流程/调用活动 | subProcess / callActivity | 不支持 | 大流程无法分层复用，模型会膨胀 | P1 |
| 定时器事件 | timer boundary/intermediate | 只有外部 cron 扫描 | 无法在流程语义内表达超时、提醒、自动推进 | P1 |
| 消息/信号事件 | message/signal catch/throw | 入站 Webhook 只能启动/完成 | 无法等待外部事件、无法做消息关联 | P1 |
| 边界事件/错误 | boundary error/timer | 不支持 | 异常只能靠人工改派，不能自动补偿 | P1 |
| 多实例/会签 | multiInstance + completionCondition | 不支持 | 无法做 N 人会签、比例通过、仲裁 | P0 |
| 结构化循环/回退 | loop / 回退边 | 可由连线表达，但无显式语义 | 回退后历史与 SLA 口径容易混乱 | P1 |
| 取消/补偿 | cancel/compensation | 只有整实例取消 | 已产生的副作用无法按业务补偿 | P2 |

### 3.2 人工任务

| 能力 | 行业做法 | 当前 | 差距与风险 | 优先级 |
| --- | --- | --- | --- | --- |
| 候选用户/组 | candidateUsers/Groups + 表达式 | 只有角色/组织/默认人 | 不能按项目、技能、岗位精确路由 | P0 |
| 认领/释放 | claim / unclaim | 有认领，无本人释放 | 认领后无法退回公共队列 | P0 |
| 委托/转交 | delegate / transfer | 只有经理改派 | 请假/出差场景必须找管理员 | P1 |
| 四眼/职责分离 | SoD + 4-eyes | 无 | 发起人可审批自己的单，审计风险 | P0 |
| 会签/仲裁 | quorum / percentage | 无 | 无法表达多人审批规则 | P1 |
| 任务优先级 | priority + SLA | 无优先级 | 队列按创建时间，紧急任务会被淹没 | P1 |
| 工作量/负载 | workload / assignment | 无 | 无法看谁积压、无法均衡分配 | P2 |
| 任务历史 | task events + comments | 只有当前字段和审计日志 | 无法还原「谁在何时认领/改派/升级」 | P1 |
| 附件/交付物 | task attachments | 任务与交付物体系未打通 | 完成审批时无法强制关联产出 | P1 |
| SLA 日历 | business calendar / holidays | 墙钟小时 | 跨周末/节假日时限失真 | P1 |
| 多级升级 | reminder → L1 → L2 | 单级升级 | 重大超时没有逐级上报 | P1 |

### 3.3 运行正确性

| 能力 | 行业做法 | 当前 | 差距与风险 | 优先级 |
| --- | --- | --- | --- | --- |
| 并发认领 | 行锁/条件更新 | 读后写，无锁 | 两人可同时认领成功，最后写入者覆盖 | P0 |
| 并发完成 | 乐观锁/版本号 | 无版本列 | 重复完成可能创建两个后续任务 | P0 |
| 幂等启动 | Idempotency-Key | 无 | 网关重试会重复启动实例 | P0 |
| 幂等完成 | Idempotency-Key + 结果回放 | 无（重复完成返回 409） | 调用方无法安全重试 | P0 |
| 状态机不变量 | DB 约束/状态迁移表 | 只有 Python 校验 | 并发或脚本写入可破坏「单 OPEN 任务」 | P0 |
| 事务边界 | 业务+事件同事务 | Outbox 同事务，较好 | 外部副作用仍靠人工重试 | P1 |
| 失败补偿 | saga/compensation | 无 | 半完成流程只能人工修数据 | P2 |
| 故障注入测试 | chaos/concurrency tests | 基本没有 | 生产并发下问题不可见 | P0 |

### 3.4 版本与变更

| 能力 | 行业做法 | 当前 | 差距与风险 | 优先级 |
| --- | --- | --- | --- | --- |
| 流程部署 | deployment + definition version | 只有 `model_version` 计数 | 无法知道某实例跑的是哪次部署 | P1 |
| 运行实例迁移 | instance migration | 无 | 模型升级后老实例只能跑完或取消 | P1 |
| 表单版本 | form definition version | 实例快照冻结字段 | 可运行，但缺少可审计的版本对象 | P2 |
| 规则版本 | decision/rule version | 随实例快照冻结 | 同上 | P2 |
| 回滚 | deployment rollback | 无 | 配错后只能手工改回 | P2 |

### 3.5 集成与事件

| 能力 | 行业做法 | 当前 | 差距与风险 | 优先级 |
| --- | --- | --- | --- | --- |
| 常驻投递 worker | queue/worker + 退避 | 手动运行 | 生产必须靠 cron 或人工点击 | P1 |
| 死信/重放 | DLQ + replay | FAILED 记录 + 手动重试 | 无法批量重放、无补偿策略 | P1 |
| 拉取接口 | pull API + cursor | 无 | 只能推送，ERP 不能主动拉 | P1 |
| 事件契约版本 | schema version | 无 | 消费方升级时容易断 | P1 |
| 消息关联 | correlationId/businessKey | 无 | 无法把外部回调关联到等待中的实例 | P0 |
| 链路追踪 | traceId 贯穿 | 无 | 跨系统排障困难 | P1 |

### 3.6 可观测性与治理

| 能力 | 行业做法 | 当前 | 差距与风险 | 优先级 |
| --- | --- | --- | --- | --- |
| 执行指标 | throughput/cycle time/backlog | 无 | 无法回答「执行层是否健康」 | P0 |
| SLA 看板 | on-time rate/breach | 无 | 有 due_at，但没有达成率口径 | P1 |
| 瓶颈分析 | node duration/bottleneck | 设计器有测算，运行时无 | 运行数据没有回流到治理 | P1 |
| 任务事件流 | append-only task events | 无 | 审计与追责证据不足 | P1 |
| 运行事故台 | stuck/failed instances | 无 | 卡住的实例只能靠人翻列表 | P1 |
| 审计不可篡改 | hash chain/WORM | 普通审计表 | 高合规场景证据力不足 | P2 |
| 数据保留/归档 | retention policy | 无 | 长期运行后表膨胀 | P2 |

### 3.7 安全与非功能

| 能力 | 行业做法 | 当前 | 差距与风险 | 优先级 |
| --- | --- | --- | --- | --- |
| 实例级 ACL | participant/ACL | 只看全局角色与候选范围 | 经理可处理所有任务，权限过宽 | P1 |
| 字段级可见性 | field-level permission | 无 | 敏感金额/人事信息可能暴露 | P1 |
| API scope/rate limit | OAuth scope/quota | 入站只有 HMAC | 密钥泄露后影响面大 | P1 |
| 多租户 | tenant isolation | 单租户 | 集团多法人场景受限 | P2 |
| 高可用 | 无状态 worker + 队列 | Web 进程内同步执行 | 多副本下并发问题放大 | P1 |
| 归档/分区 | partition/archive | 无 | 数据量增长后查询变慢 | P2 |
| 负载测试 | load/SLO | 无 | 不知道容量上限 | P1 |

| 模板/复用 | 子流程、模板库、复制粘贴 | 无 | 大模型重复劳动 | P1 |
| 设计-执行联动 | 节点上直接配表单/规则/分派/SLA | 分散在执行配置页 | 配置漏配、模型与运行脱节 | P1 |
| 仿真能力 | 离散事件/资源/队列仿真 | 期望值测算 | 只能算静态期望，不能看拥堵与产能 | P2 |
| 导入导出 | BPMN 2.0 + DI + 校验 | 结构子集 + 基础 DI | 复杂模型无法往返 | P1 |

| 变更治理 | 1.5 | 3.5 | 部署版本、实例迁移、回滚 |

## 4. 根因判断

1. **产品定位导致执行层是「够用就好」**：系统主线是架构、诊断、项目治理，执行层是
   为了让改善后的流程能跑起来，而不是替代专业 BPMS。
2. **单令牌模型是刻意简化**：它让第一版快速可用，但把并行、会签、子流程、异常事件
   全部挡在门外；继续在单令牌上打补丁会越来越别扭。
3. **缺少运行工程层**：没有并发控制、幂等、任务事件、部署迁移、worker 和指标，
   这些不是 UI 功能，而是生产执行层的底座。
4. **人工任务只做了「队列」**：认领/完成/改派之外，委托、释放、会签、四眼、优先级、
   工作日历、多级升级都没有形成完整任务生命周期。
5. **执行数据没有回流治理**：设计器有测算，运行时有 due_at，但没有把实际周期、
   瓶颈、超时、返工回流到流程治理，平台的核心优势没有闭环。
6. **设计器被当成「指标录入面板」而不是「建模工具」**：当前实现优先保证测算字段齐全，
   但没有画布和连线编辑，导致「图画不出来、测算是真的、流程跑不起来」的割裂。
7. **设计-执行-治理三条线各有一套配置**：节点属性在设计器，表单/规则/分派在执行配置，
   标准文件/交付物在交付物页；缺少以节点为中心的统一配置视角。
8. **缺少发布治理**：模型保存即生效，没有草稿/评审/发布/版本差异/回滚，
   对流程管理科来说无法做变更控制。

## 5. 目标能力分层

### Must（专业执行层的最低门槛）

- 设计器画布：拖拽节点、连线、缩放/平移、对齐；分支/回路/条件在界面上可画。
- 设计器校验：入口/结束/可达/网关配对/概率和；错误模型不能保存。
- 设计器版本：草稿/评审/发布/版本差异/回滚，而不是「保存即生效」。
- 并发安全：认领/完成使用行锁或版本号，数据库约束保证单任务状态不变量。
- 幂等：启动/完成支持 `Idempotency-Key`，重复请求返回同一结果。
- 任务事件流：认领、释放、改派、升级、完成、取消全部 append-only。
- 多级升级 + 提醒：到期前提醒、到期升级、超时再升级。
- SLA 日历：工作日/节假日/时区，挂起时暂停或明确不计入。
- 执行指标：积压、超期率、按时完成率、平均处理时长、节点瓶颈。
- 并行网关 + 汇聚：BPMN 模型、设计器、运行时、测试完整打通。
- 会签/四眼：至少支持「全部通过/比例通过」和发起人不能自审。

### Should（形成差异化）

- 设计-执行一体化：在节点属性面板直接配表单、规则、候选分派、SLA。
- 泳道实体、模板库、复制粘贴、协作编辑与评论。
- 子流程/调用活动、定时器事件、消息关联。
- 委托/转交、本人释放、批量改派、工作量视图。
- 运行实例迁移、部署版本、回滚。
- Outbox worker、死信重放、拉取接口、事件契约版本。
- 任务与交付物/标准文件关联，完成审批时校验产出。

### Won't（明确不做，避免变成通用低代码平台）

- 完整 BPMN/CMMN 全语义、复杂网关、事务子流程、补偿编排。
- 通用低代码页面设计器、任意脚本执行、插件市场。
- 多租户 SaaS 计费、移动端离线。

## 6. 建议路线

### 第 0 步：正确性加固（1–2 天，优先级最高）

先不碰多令牌，把现有执行层变成「不会因并发和重试出错」：

1. `process_task` 增加 `row_version`，认领/完成使用 `UPDATE ... WHERE status=... AND row_version=...`。
2. 启动/完成增加 `Idempotency-Key` 表或字段，重复请求返回首次结果。
3. 增加任务事件表 `process_task_event`，记录 claim/release/assign/escalate/complete/cancel。
4. 数据库层增加「一个实例最多一个 OPEN 任务」的部分唯一索引（当前单令牌语义）。
5. 补并发测试：两人同时认领、同一任务重复完成、网关重试。
6. 挂起时暂停 SLA：`suspended_at` 与恢复时顺延 `due_at`，或明确「挂起不计时」。

验收：并发测试稳定通过；重复请求不产生重复副作用；任务历史可完整回放。

### 第 1 步：设计器 v2（1–2 周）

把「泳道卡片列表」升级成真正的流程建模器：

1. 画布：节点拖拽、连线拖拽、缩放/平移、网格/对齐、框选、删除单边。
2. 调色板：开始/结束/作业/审批/判断/等待/并行网关/子流程；节点类型与 BPMN 对齐。
3. 属性面板：节点、连线、泳道三类属性；连线条件/概率/标签可视化。
4. 校验：入口/结束/可达/网关配对/概率和/自环/重复边；错误阻止保存并定位到元素。
5. 撤销/重做、复制/粘贴、快捷键、模板库。
6. 版本治理：草稿/评审/发布、版本差异、回滚；保存不再直接生效。
7. 设计-执行联动：节点上直接配表单、规则、候选分派、SLA，避免跨页漏配。
8. BPMN 2.0：使用标准 Modeler 能力或 bpmn-js 级兼容，保留 DI 坐标与扩展属性。

验收：业务人员能在界面上画出含分支/回路/并行网关的流程；错误模型无法保存；
发布前可对比版本差异；节点配置不用离开设计器。

### 第 2 步：令牌引擎 + 并行网关（1–2 周）

1. 引入 `process_token`（node_key / status / task_id），把 `_advance` 改成令牌推进。
2. 支持 parallel split / join、多 OPEN 任务、实例完成判定。
3. BPMN 导入导出支持 `parallelGateway`；设计器支持节点类型与校验。
4. 前端实例详情显示多个并行待办；任务队列支持按实例分组。
5. 补「并行分支、汇聚、部分完成、取消」测试。

验收：一个实例可同时存在多个 OPEN 任务；汇聚只在所有分支到达后继续；
BPMN 导入的并行流程可以真实运行。

### 第 3 步：人工任务专业化（1–2 周）

1. 候选用户/组 + 表达式（至少支持角色、组织、项目成员、发起人上级）。
2. 认领/释放/委托/转交；任务优先级与队列排序。
3. 会签（全部/比例）、四眼原则、发起人回避。
4. 工作日历、到期前提醒、多级升级。
5. 任务事件流 UI、评论、附件/交付物关联、批量改派、工作量视图。

验收：请假可委托；审批可配置会签；SLA 按工作日计算；任务全生命周期可追溯。

### 第 4 步：集成与可观测性（1–2 周）

1. Outbox worker（cron/队列）、死信重放、投递指标。
2. 拉取接口 + cursor + 契约版本 + correlationId。
3. 执行指标 API 与看板：积压、超期率、按时完成率、节点耗时、瓶颈。
4. 实例卡住/失败事故台；审计保留期与归档。
5. 运行实例迁移与部署版本。

验收：ERP 可推可拉；失败可重放；执行层健康度一屏可见；模型升级可控。

### 第 5 步：安全与规模化（按需）

- 实例级 ACL、字段级可见性、职责分离。
- API scope/rate limit、入站密钥轮换与审计。
- 多副本下的 worker/锁、归档、负载测试与 SLO。

## 7. 建议的下一步

**建议顺序：第 0 步正确性加固 → 设计器 v2 → 令牌引擎/并行网关。**

原因：

- 第 0 步改动小、风险低，直接解决「业余感」最核心的来源：并发、幂等、历史不可追溯。
- **设计器比运行时更紧急**：现在连分支/回路都画不出来，并行网关即使运行时做完了，
  业务人员也无法在界面上建模、评审和发布。设计器 v2 是并行网关的前置条件。
- 并行网关会放大并发问题；没有行锁/幂等/任务事件，多令牌上线后问题会更难排查。
- 第 0 步也是后续会签、委托、SLA、事故台的数据基础。

如果只能选一个「看起来最专业」的里程碑，选**设计器 v2 + 并行网关**这一组；
如果选一个「最不容易出事」的里程碑，选**第 0 步正确性加固**。建议按顺序做，
不要先做并行运行时再补画布，否则会出现「引擎支持、界面画不出」的尴尬。
