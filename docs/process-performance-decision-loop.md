## 1. 产品目标与当前判断

**绩效管理的产出不是图表，而是有可信数据依据的管理决定，以及决定实施后是否改善客户结果的验证。**

小闭环：

**客户与战略结果 → 流程目标/CSF → 指标与取数约定 → 数据核验 → 解释偏差 → 授权决策 → 原业务动作 → 效果验证 → 维持、修正或回到分析。**

每个环节回答目的、输入、责任、动作、证据和退出条件；它是持续运营的作业方式，不是新的 current_stage。没有改善项目也应能够测量、处置、复盘；需要一轮改善交付时再关联 Project，内部保持五阶段。

## 3. CSF→KPI：每个指标必须有决策用途

推导不是把战略拆成一串相似的句子。每项关系应可解释：

| 层 | 要回答 | 示例，仅作设计演示 |
|---|---|---|
| 客户/战略结果 | 最终为谁交付什么？ | 客户在承诺日期收到正确、可用的订单产品 |
| 流程目标 | 这条流程对结果承担什么？ | 缩短可控交付历时，同时保证质量与承诺履约 |
| CSF | 哪些机制必须做好？ | 授权及时、信息一次完整、拣货准确、异常及时解决 |
| KPI | 怎么知道这些机制/结果在发生？ | 审批等待分布、首次提交完整率、拣货差错率、按期足量交付率 |
| 决策约定 | 偏差出现后谁做什么？ | 核对采集→分层查原因→处理资源/表单/规则→必要时立项 |

CSF 是待证实/持续检验的成功机制，不是因果已经成立；“提高拣货效率”不能只用拣货准确率衡量，需分别考虑吞吐/处理时间和准确性。代理指标要写明盲区，不强称一个 KPI 覆盖全部目标。

每个正式 KPI 至少具备：目的/CSF 引用、结果或驱动作用、位置/粒度、公式与分母、来源及质量、频率/延迟、业务范围、目标/阈值、Owner/数据责任、异常响应规则、复核时间。拿不到数据的指标保留“待采集设计”，不能靠补几个演示值变成正式绩效。

不强制每个流程恰好 2–3 个 CSF 或每个 CSF 两个 KPI；讲义数量是练习约束。优先少而有决策价值，去除重复和可被单方轻易操纵的指标。

## 4. 四维、计分卡、指标用途：三件事不混建

当前代码 KpiDimension 为效率/质量/成本/灵活性，讲义是效率/质量/柔性/客户价值；不能把 COST 的中文直接改成客户价值。当前还有结果/过程/健康度分类，是另一轴。

建议先保留历史 dimension 代码及原标签，新增或复用原定义/模板中的“价值覆盖/计分卡用途”关联元数据：

- **绩效平衡检查**：效率、质量/效果、适应性、客户价值；成本仍单独可见，不能因换框架被删。
- **平衡计分卡视角**：财务、客户、内部流程、学习成长，是观察视角，不是另一套 KPI 数据。
- **指标用途**：结果、驱动/过程、健康/控制；同一原 KPI 可被不同视角引用，不复制定义/样本，不重复计入总分。

第一期用现有计分卡模板/定义扩必要关系和缺口说明，不重做雷达轴或迁移所有维度。若后续决定调整 dimension，必须另列数据迁移和兼容范围，不能偷偷改名。

“学习成长”不能只用培训到场或改善项目数宣布能力提升；需结合操作验证、复发、采用和实际结果。成熟度评估说明管理能力，不直接替代战略/客户结果。

本次不设计新图表。先把用途、口径和动作明确，再决定如何呈现；不为填满四个象限制造无数据指标。

## 5. 数据可信：先能复算，再判业务好坏

### 5.1 数据状态与绩效状态分开

数据质量：未配置/未采集/样本不足/过期/来源冲突/待核实/有效。绩效状态只在质量允许时判断达标、预警、未达标；法律或业务有明确保守规则时按其执行并注明，不把未知显示绿。

一次定义卡或可用 webhook 不保证样本可信。需要检查完整性、时间、重复/缺失、口径、范围、授权和业务代表性。零、无数据、未发生、不适用、未确认均不同。

### 5.2 取数语义必须显式

端到端历时、活动等待、人工投入和自动运行时长都可能以小时计，但取数事件/字段不同。不得按单位自动统一取实例历时。定义中说明日历、暂停/挂起、时区、边界和分位算法；质量/利用率等写分子分母与期间。

周期仅看已完成业务会低估仍积压问题；操作视图同时看开放业务年龄、逾期和在制数量。窗口、业务复杂度、产品/客户群组、版本/组织、工作日历变化必须可分层，不能直接把混合均值当改善效果。

### 5.3 冻结与日常运营的边界

日常运营沿原KpiDefinition/KpiRecord，无项目也可用；拟给样本记录补当时口径/来源/窗口快照及修订依据，不只靠今天定义或一个可变ID解释过去。正式改善在薄对照按时点锁process/project、现状和口径，上线后再追加实际上线版本；前后正式样本使用共同冻结口径、各自窗口和对应模型。

正式验收不能引用可变最新值；原记录更新保留修订依据，不静默覆盖已签收样本。新模型或新口径只能另修订/分组，不在看到结果后调整目标追认通过。

### 5.4 阈值、控制限、趋势不同

- 目标/红黄绿反映承诺或管理边界，须说明值恰好等于边界时如何判定。
- 若保留三个阈值，必须分别明确作用；当前 yellow 未直接参与状态分类，应明示其用途或修订契约，不能界面填了却暗示都有独立判定效力。
- 控制限用于经定义统计模型的过程变化判别，不等于目标线；现有控制图说明模板不等于已计算控制限。
- 一次越线、持续越线、异常变化、数据质量故障分别判断。需风险相称的持续窗口/恢复条件、去重和复发规则，不能一抖就发项目。
- 趋势 UP/DOWN 是数值方向，不自动等于好/坏；越低越好、区间目标、零缺陷和零分母须正确处理。当前仅支持高/低方向时，对不支持目标形式明确限制。

## 6. 绩效管理小闭环作业链

P0–P7 是作业指引，不是新的八/五/四阶段引擎。工作可按周期持续运行。

| 指引 | 核心动作 | 产出与核验 | 原模块落点 |
|---|---|---|---|
| P0 明确价值 | 关联客户结果、战略/流程目标和 CSF，明确本期决策需要 | 推导依据、责任与取舍；不是只有指标名称 | strategy、流程卡、原计分卡模板 |
| P1 约定测量和响应 | 定义指标、采集位置/口径、来源/质量、阈值和行动条件 | 可采集、可复算、有人接警和决策；取数缺口单列 | monitor 指标定义、data、原责任记录 |
| P2 采集核验 | 接收日志/回传/审核人工记录，检查样本质量和范围 | 有来源及时间的有效样本，或明确数据问题 | 原 KPI/入站/运行及质量核验服务 |
| P3 识别解释偏差 | 看目标、波动、积压及群组差异，分清测量故障和业务问题 | 固定本次判断用的数据/口径/窗口；问题线索不是根因 | dashboard 下钻 monitor/执行队列 |
| P4 决策 | 指定责任人，按证据/风险决定立即处置、采证、分析或改善 | 决定、理由、授权、预期效果、期限及复核方式 | 原异常/治理/项目步骤与审核 |
| P5 执行动作 | 在原业务位置分派、补数、改配置、分析或按需立项 | 可追溯原动作/版本/结果，失败或逾期可升级 | execution、data、analysis、projects |
| P6 验证效果 | 同口径检查预期是否发生，质量/成本/体验是否受损 | 独立验证、继续/调整/停止/升级结论，不以“已执行”代替有效 | 原异常核验、证据/签收、轮次对照 |
| P7 固化复盘 | 保留有效做法、调整监测/控制、处理复发 | 周期结论、下次复核和新问题，流程持续运营 | 原标准/培训/复盘和 dashboard |

闭环可从告警进入，但不能跳过对数据和授权的核验。重大安全/合规问题先按预案止损，同时调查，不要求等完整统计或项目立项后再行动。

## 7. 决策支持：不是“红灯→自动加人/立项”

| 发现 | 先核实 | 可选决定 | 效果验证 |
|---|---|---|---|
| 持续积压 | 到达量、能力/技能、在制年龄、工作日历、数据延迟 | 临时调度、需求分流、修输入、专项分析；资源调整按授权 | 积压年龄/尾部周期下降，质量和其他队列没有恶化 |
| 某类申请退回率高 | 分类/分母、退回原因、重复计数、规则和样本结构 | 前置校验、表单改进、培训、修规则或正式改善 | 首次通过/客户完成改善，不靠拒收复杂单“变好” |
| 周末显著变慢 | 服务承诺/日历、业务混合、值班、样本量 | 调班、调整承诺、自动化可行性验证或维持观察 | 同类业务可比，成本/人员/体验约束不被转嫁 |
| 绿灯但投诉增加 | KPI 覆盖盲区、调查偏差、内部关闭/真正解决区别 | 修测量/分析客户体验，不因绿灯拒绝投诉 | 客户结果与运行记录能相互解释 |
| 指标突降但日志缺失 | 采集故障、重复、口径/版本改变 | 修采集/补数及风险处置，先不下业务结论 | 补数可复算，修订保留，原判断有复核 |

决策记录最小结构：**偏差事实/快照 → 原因判断及不确定性 → 候选动作与选择理由 → 有权决策人 → 原动作引用/责任/期限 → 预期效果及复核日期 → 核验结果。**

不默认新增 Decision/Action 台账；存在 ExceptionEvent、ProjectStep、治理发现或相关业务记录时直接引用并补必要责任/期限/核验字段。没有正式改善必要，不强造项目；需要结构性改善再从 projects 开一轮，固定对照，五阶段不变。

## 8. 三层监控各有决策和下钻

| 层 | 看什么/决定什么 | 现有入口 | 必须能下钻 |
|---|---|---|---|
| 操作层 | 哪笔该处理、积压多久、是否违约；认领、调度、升级 | execution 任务/实例；驾驶舱相应链接 | 具体业务/节点/人员权限、时限及事件，不只总量 |
| 管理层 | 本期结果与目标、质量/成本/体验、偏差责任；分析和资源取舍 | dashboard→monitor KPI/异常/工作量 | 原指标、样本、群组、模型/口径和行动结果 |
| 战略层 | CSF 是否支撑客户/经营结果，投入和能力是否有效；优先级决策 | dashboard→strategy/流程卡/原计分卡引用 | 目标—流程—CSF—KPI—决策证据，成熟度仅作能力信息 |

监控度量按钮仍进入 dashboard，不改为 monitor。不同层不是三套数据；所有汇总回到同一原样本和冻结/当时口径。读取、聚合、导出和关联链接都受组织/对象权限约束。

“L1 采集、L2 运用”在本稿只表述为采集责任与管理运用责任的分工，不代表不同岗位只能做某半边，也不与流程架构 L1/L2 同义。正式考试/官方分级文案须核原件后再写。

## 9. 绩效是否有效：不能由总分代替

- 明确客户、质量、法律和风险红线，不能让其他指标超额完成抵消关键未达标。
- 汇总均值仅能在口径、时间和权重适当时作概览，必须同时显示关键红项、缺失、样本覆盖及质量；空维度不是 0% 绩效。
- 比例跨团队/期间汇总用可比的分子分母，不简单平均百分比；不同方向/上限/量纲未有批准归一化规则，不给貌似精确总分。
- NPS、满意度、交付及时率等各有口径和偏差，不能互代；调查响应不足或选择性回访不能伪装总体客户感受。
- 高利用率并非越高越好，过载可能导致等待/质量问题；有界/区间指标不强套单向达成率。
- 不以任务速度、工时、项目数单独给个人奖惩；团队目标、业务复杂度和不可控等待需共同评价。绩效管理不是默认建设薪酬系统。

## 10. 界面交互与统一文案

保留原 dashboard、monitor、execution、strategy/projects 分工，不新增平行看板。先补底层契约，本次不设计图表布局或新可视化。

指标详情围绕四组信息展开：

1. **为何测**：客户/战略目标、流程目标、CSF、指标用途与决策责任；
2. **数是否可信**：当前范围/窗口、当时或冻结口径、来源、样本/排除、质量/时效；
3. **偏差是什么**：值/目标/红线、分层/趋势、未知项及本次判断依据；
4. **决定与验证**：责任人、原动作入口、期限、预期效果、验证结果及复发。

每个关键指标都要能回答“若发生偏差，由谁依据什么做什么”；暂不需要响应的观察指标应写明用途/复核，不伪造行动。

| 情况 | 推荐文案 / 操作 |
|---|---|
| 配置未完整 | 尚未确认数据来源与决策用途，暂不判定正式绩效。 |
| 样本不足/过期 | 数据暂不支持本期结论；查看数据质量。 |
| 出现偏差 | 已发现偏差线索，待核对原因与处置方式。 |
| 转分析 | 带本次指标、窗口和证据进入流程分析。 |
| 原动作已执行 | 措施已执行，效果待验证；查看复核约定。 |
| 指标变绿 | 本期指标达标；相关措施是否有效仍按原验证约定核验。 |
| 行动无效 | 原措施未达到预期，请修订决定或进入进一步分析。 |
| 改善项目结束 | 项目已结项，流程继续监控；显示有效版本和下次复盘。 |

告警确认、处置完成、效果验证、异常关闭分别发生，不能一个“关闭”按钮清掉所有责任。按风险和预先约定判断，不必每个小偏差都走复杂独立审批；正式改善验收仍遵守独立核验。

## 12. 验收与推荐落地顺序

**先固定推导和取数契约，再可信判断，随后贯通决定/动作/验证，最后优化可视化。**

后续验收至少覆盖：

- CSF 与 KPI 的作用解释、同指标多视角引用、缺客户价值维度的提示而非偷改成本维度；
- 相同时间单位的不同取数、零/缺数/过期/小样本、未完业务、跨版本/窗口混合；
- 阈值等值、三阈值实际含义、上升下降方向、0 目标/分母、比率和分位聚合；
- 关键红线不被均值抵消、无样本维度不报 0% 业务绩效；
- 告警重复/恢复/复发、人工确认、并发转改善去重、数据质量故障不误判业务；
- 决策有责任/授权/期限，措施执行后未验证不可当有效关闭；
- 前后比较四身份一致、原口径不被后改覆写、项目结项后持续监控；
- 操作/管理/战略三层下钻到同一事实，权限过滤覆盖列表/汇总/导出；
- 演练/预测不进入实际绩效，未核官方引文不贴认证标识。

复用 `test_kpi_definition.py`、`test_improvement.py`、`test_escalations.py`、`test_inbound.py`、`test_dashboard_home.py`、`test_strategy.py` 和 `test_workflow_workbench.py`；前端跑当前代码服务的 verify_frontend，schema 变化走 Alembic 一致性。本次未运行这些测试。

**完成标准**：不只看到某指标红/绿，而能说明它为何重要、数据能否相信、偏差如何解释、谁作了什么决定、原动作是否执行，以及客户结果是否按同一依据改善。数据既可促进行动，也可推翻原行动；不能只允许它装饰既定结论。
