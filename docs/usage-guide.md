# 模块定位与使用指南

这份指南回答三个问题：

1. 每个模块**是什么、什么时候用**；
2. 模块之间**怎么衔接**；
3. 哪些用法是**常见误区**。

先记住一句话：

> **流程地图是家底，项目组合是改善工程，标准工作流是方法手册，工具箱是工具书，
> 设计器是图纸与测算，流程执行是日常跑流程，运营监控是看结果，知识库是沉淀。**

---

## 一、三层结构里的模块位置

| 层 | 模块 | 主要回答的问题 |
|---|---|---|
| 战略层 | 企业流程地图、对标框架 | 我们有哪些流程？哪条最该改？在行业标准里处于什么位置？ |
| 执行层 | 流程项目组合、五阶段标准工作流、流程执行 | 怎么改？改到哪一步了？改完怎么跑？ |
| 支撑层 | 方法论工具箱、流程设计器、运营监控、知识库、通知/集成 | 用什么方法？流程怎么建模？结果如何？经验怎么复用？ |

---

## 二、四个核心模块的定位

### 1. 企业流程地图（Where）

**定位**：企业流程资产台账与架构定位地图。

- 回答：L1 价值链 → L2 流程类别 → L3 流程 → L4 活动分别是什么；
  每条流程的 Owner、健康度、痛点、改善空间、优先级。
- 产出：一张可下钻的流程架构；「先改哪条流程」的候选排序在
  「管理驾驶舱 → 改善优先级」统一查看，避免地图里出现第二套榜单。
- 使用时机：年度流程规划、新业务上线前、需要向管理层说明流程家底时。
- **不要拿它做**：项目进度跟踪、日常任务分派。

### 2. 五阶段标准工作流（What & When）

**定位**：全公司共用的**方法手册 / 教学引导**，不是项目进度表。

- 回答：识别、诊断、设计、落地、运营五个阶段各有哪些标准步骤；
  每一步应该产出什么交付物、推荐什么工具。
- 产出：一套统一的语言和操作规范，让不同项目按同一节奏推进。
- 使用时机：新人培训、项目启动前对齐方法、项目推进中查「下一步该做什么」。
- **不要拿它做**：记录某个项目的完成情况。具体项目的 24 步实例在
  **流程项目组合 → 项目详情 → 工作流** 页签里推进。

> 页面上的「五阶段步骤 / 方法论匹配」两个页签都是**参考视图**：
> 前者告诉你标准动作，后者帮你判断该用 BPR、BPI 还是精益。
> 它们都不会改变任何项目状态。

### 3. 流程项目组合（Who & How far）

**定位**：改善项目的**管理容器与推进循环**。

- 回答：有哪些改善项目、谁负责、预算多少、当前在哪个阶段、整体进度多少。
- 每个项目立项时会按标准工作流**实例化 24 个步骤**；项目的实际推进，
  就是在项目详情里逐步更新步骤状态，系统自动回算进度、推进阶段、标记里程碑。
- 产出：可交付的改善项目（而不是一张流程图）。
- 使用时机：从流程地图选定改善对象后立项；此后所有项目状态都在这里维护。
- **不要拿它做**：直接运行日常业务流程（那是流程执行）。

### 4. 流程执行（Run）

**定位**：已建模流程的**运行时**：实例、任务队列、表单、规则。

- 回答：这条流程现在有哪些实例在跑？谁该处理哪个任务？审批结果是什么？
  分支走到哪里？流程是否完成？
- 产出：真实的流程实例、任务处理记录、表单数据、审计轨迹。
- 使用时机：流程设计完成并准备上线后；试点和正式运行都在这里。
- 超期处理：先设任务时限，再设升级时限与升级处理人；到点后运行升级扫描
  （或由 cron 调用 `scripts/run_escalations.py`）自动改派，同一任务只升级一次。
- 暂停运行：流程管理科可在实例详情里「挂起」；挂起期间任务不可认领/完成，
  也不会被升级扫描处理，恢复后继续，挂起时长不计入 SLA。
- 任务详情底部的「任务历史」会记录创建、认领、改派、升级、SLA 顺延、完成和取消。
- 外部系统调用启动/完成接口时建议带 `Idempotency-Key`，网关重试不会重复建实例或重复推进。
- **不要拿它做**：管理改善项目本身的进度。改善项目在项目组合里推进，
  流程执行跑的是「上线后的业务流程」。

### 5. 流程卡（单流程 360）

**定位**：一条 L3/L4 流程的跨模块聚合页，回答「这条流程现在到底怎么样」。

- 聚合内容：战略承接、RACI 权责、制度与标准文件、流程模型、标准工时、
  KPI、变更/改善、治理待办。
- 产出：一条流程的 readiness 清单（哪些区块已具备、哪些待补）和所有原模块入口。
- 使用时机：流程 Owner 月度复盘、交接、评审前自查、从战略目标「看流程」。
- **不要拿它做**：跨流程排名或项目进度跟踪（前者看驾驶舱，后者看项目组合）。

### 6. 十层单页（落地执行面）

**定位**：一条试点路径的十层落地检查表，一次只展开一层。

- 十层：战略与目标 → 架构与端到端链路 → 组织与职责 → 制度与授权 →
  流程 → 表单/工具 → 工作量 → 绩效 → 改善 → 新版本。
- 每层都有输入、动作、输出、退出条件和证据；退出门由现有证据自动计算。
- 使用时机：流程从「设计完成」走到「正式上线」的落地阶段；每层只解决一个问题。
- **不要拿它做**：替代项目组合的 24 步。项目组合管改善项目，十层单页管
  某条流程对象的落地状态。

### 7. 授权矩阵（谁有权批）

**定位**：把 PDF 里的审批权限变成可查询、可审计的数据。

- 规则：按 A/B/C/D 分类，记录风险等级、金额上限、影响范围、可逆性、频率、
  审批角色、例外路径、审批证据和依据文件。
- 例外台账：记录这一次为什么破例、谁批的、什么时候失效。
- 使用时机：制度/SOP 设计完成后；任何「金额/风险/组织范围」分级的审批事项。
- **不要拿它做**：替代制度文件。授权规则引用制度，不复制制度正文。

### 8. 数据治理（数据可用性）

**定位**：流程数字化/自动化之前的最小数据台账。

- 数据域：谁负责、谁管质量。
- 数据流：从哪个系统来、主键是什么、频率、质量规则、保留期、跨法人可见性。
- 使用时机：配 KPI、上流程执行、做过程挖掘之前，先确认数据有人负责、可取得。
- **不要拿它做**：主数据平台或 DAMA 全量治理；这里只解决「这条流程用到的数据」。

### 9. 交付物与模板库（标准与实例）

**定位**：三类受控资产的唯一入口。

| 页签 | 对象 | 回答 |
|---|---|---|
| 项目交付物 | 某个项目步骤的实例/版本 | 这一步产出什么、当前是哪一版、谁批的 |
| 流程标准文件 | 挂在 L1–L4 节点上的 SOP/表单 | 这条流程的现行标准是什么、适用范围多大 |
| 工具模板库 | 某个工具下的预制模板版本 | 用这个工具时，从哪个模板开始做 |

- 项目交付物是 **as-built**（这次项目做出来的），流程标准文件是 **as-designed**
  （组织要求长期执行的）；项目成果要变成标准，走「晋升」生成草稿再审批。
- 项目交付物行支持：**上传**文件、**新建**（从本步骤推荐工具模板复制，或登记空白版本）、
  **关联模型**（2.1/3.2）、**预览**和**详情**。
- 使用时机：项目每一步交付、制度/SOP 发布、工具模板维护、审计与基线对比。
- **不要拿它做**：知识沉淀。案例、方法、经验放知识库；交付物库只放受控文件和版本。

## 四、标准工作流与方法论工具箱是什么关系

| | 五阶段标准工作流 | 方法论工具箱 |
|---|---|---|
| 本质 | 流程管理科的**操作手册** | 方法/工具的**工具书** |
| 回答 | 下一步做什么、交付什么 | 这一步具体怎么做 |
| 结构 | 5 阶段 × 24 步 | 4 类 × 33 个工具 |
| 使用顺序 | 先看步骤 | 再选 1–2 个工具 |
| 是否改变业务状态 | 否，纯参考 | 否，纯参考 |

**正确用法（五步）**：

1. 在项目详情里确认当前阶段和待办步骤。
2. 打开标准工作流，读该步骤的「动作、交付物、关键要点」。
3. 从该步骤推荐的工具里选 **1–2 个**，不要把所有工具都上一遍。
4. 按工具的 5 步标准操作执行，把结果整理成该步骤的交付物。
5. 回到项目详情，更新步骤状态；系统自动推进阶段和进度。

**错误用法**：

- 把工具箱当成检查清单，一次上十几个工具；
- 不看步骤先选工具，导致「拿着锤子找钉子」；
- 在标准工作流页面里找项目进度——那里只有方法，没有项目状态。

### 知识库 vs 工具箱：不是重复，是两个答案

| | 方法论工具箱 | 流程知识库 |
|---|---|---|
| 本质 | 方法/工具的**工具书** | 案例/模板/参考的**沉淀库** |
| 回答 | 该用什么、为什么、怎么验证用对了 | 有没有人做过、有没有模板、效果如何 |
| 对象 | `Tool`（方法本身） | `KnowledgeItem`（案例、模板、指南、最佳实践） |
| 推荐依据 | 问题匹配 + 场景 + 使用证据 | 场景匹配 + 使用证据 + 工作流位置 |
| 产出 | 选 1–2 个方法，按验证标准执行 | 借鉴案例/模板，改编成当前项目的交付物 |

**正确顺序**：先在工具箱选方法并确认验证标准，再到知识库找同一 `tool_code`
下的案例和模板；两者通过工具编码双向连接，不维护两套方法说明。

**为什么看起来重复**：两个页面都用了「先描述问题 → 再推荐」的交互。
这是同一套推荐习惯，不是同一份数据。真正重复的是「方法说明」——
它只应存在工具里；知识库只放使用经验和可改编素材。

## 五、流程项目组合与流程设计器是什么关系

| | 流程项目组合 | 流程设计器 |
|---|---|---|
| 管理对象 | 改善项目（范围、Owner、预算、进度、状态） | 一条具体流程的模型（节点、泳道、时间、成本、返工） |
| 回答 | 这个项目做到哪了、值不值得继续 | 这条流程现在怎么走、改成什么样、能改善多少 |
| 产出 | 项目交付物与结项 | As-Is / To-Be 模型、PCE/等待/返工/瓶颈分析、改善建议 |
| 使用时机 | 立项后全程 | 诊断与设计阶段；上线后维护模型 |
| 是否运行流程 | 否 | 否；运行在「流程执行」 |

**衔接方式**：

- 项目通过 `process_id` 关联到流程地图上的某条流程；
- 在项目详情里点「查看流程模型」进入设计器；
- 设计器的测算与建议作为诊断/设计阶段的依据；
- 设计完成、表单/规则配好后，在流程执行里启动实例。
- 设计器的修改先保存为草稿；提交评审、发布后才替换运行时模型。已发布版本可在
  「版本历史」里对比、回滚（回滚会生成新草稿，仍需发布）。
- 启动前建议在「表单与规则 → 节点分派」里配好每个节点的候选角色、限定组织与默认处理人；
  不配则进入公共队列，按节点 owner/泳道做兜底校验。

**注意**：流程执行启动实例时会对**已发布模型**做快照。之后再改设计器草稿，
不会影响已经在跑的实例，也不会影响新实例，直到发布。

### 交付物与模板库和周边模块的关系

```text
方法论工具箱（Tool）
  └─ 工具模板（ToolTemplate → 版本）
        └─ 复制到项目 → 项目交付物版本（固定来源模板版本）

企业流程地图（L1–L4 节点）
  └─ 流程标准文件（SOP/表单，版本化、按组织生效）
        └─ 项目立项时复制到交付物实例（固定来源标准版本）

流程项目组合（项目 → 24 步）
  └─ 每步一个交付物实例
        └─ 项目成果「晋升」→ 流程标准文件新草稿 → 审批生效

PCF 分类框架
  └─ 只做外部对标分类/指标；通过 process_benchmark_map 映射到内部流程
        └─ 不直接挂标准文件、不参与项目推进
```

- **地图 vs 交付物**：地图是流程架构和 Owner；标准文件挂在流程节点上，
  地图详情里的「配套文件」只是读取入口，维护仍在交付物库。
- **项目 vs 交付物**：项目立项时按步骤生成交付物实例；交付物版本是项目证据，
  不是流程标准。要变成标准必须走「晋升 + 审批」。
- **设计器 vs 交付物**：设计器产出流程模型和 BPMN/SVG；SOP/表单正文仍在
  交付物库，二者通过流程节点和步骤关联，不复制正文。
- **PCF vs 地图**：PCF 是参照系，地图是公司自有架构；PCF 可以生成草稿，
  但不会产生第二套流程树，也不承载交付物。

## 六、项目组合与流程执行的区别

```text
改善项目（流程项目组合）          业务流程（流程执行）
─────────────────────────        ─────────────────────────
目标：把流程改好                  目标：按设计好的流程干活
时间：项目周期（月）              时间：每笔业务（小时/天）
对象：项目、步骤、预算、里程碑    对象：实例、任务、表单、规则
结束：结项                        结束：实例完成/取消
```

典型顺序：

1. 项目立项 → 诊断 → 设计 → 配表单/规则 → 试点；
2. 试点期间在流程执行里跑真实实例；
3. 运营监控看 KPI 与异常；
4. 项目结项；流程进入日常运营，继续在流程执行里跑。

## 七、应用场景与进入路径

| 场景 | 入口 | 路径 |
|---|---|---|
| 年度流程规划 | 企业流程地图 | 地图 → 热力图 → 选定待改善流程 → 项目立项 |
| 单条流程改善 | 流程项目组合 | 立项 → 标准工作流查方法 → 工具箱选工具 → 设计器建模 → 试点 |
| 新人培训 | 五阶段标准工作流 | 五阶段步骤 + 方法论匹配 |
| 选择方法论 | 五阶段标准工作流 → 方法论匹配 | 输入现状/目标/范围，查看推荐与风险 |
| 流程建模与测算 | 流程设计器 | 选流程 → 画布拖拽/连线（可切专业 BPMN 画布）→ 校验 → 提交评审 → 发布 → 看指标 |
| 流程上线运行 | 流程执行 | 启动实例 → 认领任务 → 填表单 → 规则分支 → 完成 |
| 日常运营 | 流程执行 + 运营监控 + 通知 | 任务队列 → 异常处理 → KPI 看板 |
| 复盘与复用 | 知识库 | 案例/模板/最佳实践 |
| 对外协同 | 集成 | 配置 Webhook → 订阅事件 → 投递/重试 |
| 行业对标 | 企业流程地图 → 对标框架 | 切换 SCOR / APQC → 看覆盖率与缺口 |

## 八、角色使用指南

| 角色 | 主要动作 |
|---|---|
| 流程管理科 / MANAGER | 维护流程地图与标准工作流；审批立项；配置表单/规则与集成；查看审计与投递 |
| 项目 Owner | 立项；推进 24 步；使用设计器；发起试点与执行；结项 |
| 任务处理人（OWNER / MANAGER） | 在流程执行认领/处理任务；填写表单；处理异常 |
| 只读 / VIEWER | 查看地图、项目、KPI、知识库；不能写 |

权限在后端独立校验：前端隐藏按钮不等于后端放行。

## 九、一条完整路径示例：采购需求提报

1. **地图**：L1-03 采购供应 → L2-003 → L3-032 采购需求提报；健康度 48，痛点 4.6，优先级高。
2. **立项**：项目组合中关联 L3-032，挂 Owner、目标（14 天 → 5 天）、预算。
3. **标准工作流**：阶段 1 用 SIPOC 界定边界，阶段 2 用 VSM/5 Why 做诊断。
4. **设计器**：打开 L3-032 模型；测算 PCE 6.9%、等待占比 87.6%；
   查看 9 类建议（等待、审批、返工、移交…）。
5. **设计 To-Be**：删减审批层级、并行化、加前置校验；可导出 BPMN 给外部评审。
6. **执行**：启动实例；n1 填需求表单（申请人/金额），n4 审批表单（通过/驳回）；
   通过规则自动流转，驳回回到修改节点。
7. **监控**：看采购周期、准时交付率、报销周期等 KPI；异常进入闭环台账。
8. **沉淀**：把有效做法写成案例/模板，进入知识库；项目结项。

## 十、常见误区

1. **把标准工作流当项目进度表**：它只是方法手册；项目状态在项目组合里。
2. **把工具箱当检查清单**：一次选 1–2 个工具，深用比全上有效。
3. **没有基线就立项**：没有周期/成本/质量基线，改善无法验收。
4. **在流程执行里追改善项目**：执行跑的是业务流程，不是项目步骤。
5. **运行中改流程模型**：实例使用启动时快照；要改请新起实例或走版本。
6. **把流程地图当组织架构图**：它描述流程与责任，不是部门汇报线。
7. **只做设计不做运营**：没有 KPI/异常闭环，改善无法持续。
