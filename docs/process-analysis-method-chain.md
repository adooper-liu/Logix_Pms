## 1. 结论：有分析内容，尚未形成完整分析作业链

当前流程分析页提供现状、瓶颈、价值流、根因、规则、基线六个分析项，并能读模型测算、实例/手记日志、异常和 KPI。工具库也有 SIPOC、VSM、5 Why、鱼骨、帕累托、CJM 等说明和填写模板。

**这些基础不能等同于“分析已经可控交付”。** 当前缺少贯穿所有方法的明确任务、共同样本、按问题选路、方法结果转证据以及最终交付确认。ABC 与客户体验更没有形成相应计算/核验链。

推荐主线是：

**明确客户价值与分析问题 → 核实实际现状和基线 → 按问题选择诊断路径 → 形成并检验原因假设 → 汇总损失、风险和客户影响 → 确认分析结论 → 交给设计或决定继续观察。**

这里的箭头是分析工作顺序和产物交接，不新增数据库阶段状态机。方法可以并行、替换或返工；不能预先指定“最终一定是缺 SLA”之类根因。

## 2. 四条链如何成为同一件事

| 链 | 必须回答 | 共同依据 | 不接受的替代品 |
|---|---|---|---|
| 思维链 | 哪个客户需要什么？何处存在差距？为什么？证据是否足够？ | 客户结果、问题陈述、竞争假设、反证、边界与约束 | 从某工具出发寻找一个能填满表格的问题 |
| 工具链 | 当前问题应选什么方法，方法的输入输出是什么？ | 同一实际活动、样本、版本和口径；方法产物可互相引用 | 人人按顺序填写全部工具；重复录入相互矛盾的数据 |
| 行动链 | 下一步由谁做，何时交，给谁确认？ | 明确原业务记录、责任、时限、核验人和阻断原因 | 点击次数、待办数量或仅有一句“已分析” |
| 作业链 | 从什么输入开始，以什么交付结束？ | 已确认现状、可复算基线、已检验根因/未决项、设计输入 | 只交鱼骨图、PPT 或未经核验的根因文字 |

共同收敛点是**客户需要的结果和端到端价值交付**，不是所有方法得出同一根因。时间、成本、质量和体验分析可能指出不同约束，需要保留分歧、验证并作取舍。

## 4. 开始：不是选工具，是确定分析委托

从现有“分析”按钮进入 `monitor?tab=analysis`，保留去向。页面第一屏回答：

1. 分析哪条流程、哪个业务范围，现状版本是什么？
2. 客户是谁，需要的最终结果和验收标准是什么？
3. 哪项结果存在什么差距，事实来自哪里？
4. 本次分析要回答什么问题，由谁做、交给谁、何时完成？
5. 哪些安全/质量/合规控制不得因效率优化而绕过？

客户可能是外部客户或明确的内部接收方，但应说明该内部交付如何支撑最终客户价值。首响更快不等于投诉解决，发送短信不等于客户已获解释，完成一个审批也不等于业务价值已交付。

有改善意图时可先保存分析范围/现状和口径草稿，确认基线后建立薄对照；project_id立项前可空，released_model_version_id上线前可空。四身份是一轮正式引用的一致性约束，不要求前置分析就有未来上线版本。日常诊断不强制项目/轮次，正式项目根因裁决才使用原ProjectEvidenceClaim/根因门；非项目方法核验须在原ToolSheet/来源记录补字段，不虚构无项目门禁已存在。

**入口产物**：一份清楚的分析任务约定，引用原目标/KPI/问题记录及本轮范围，不新增“分析项目”表。可保存在现有工具模板记录和轮次对照的固定引用里。

## 5. 推荐作业链：每一步交付下一步所需的东西

以下 A0–A6 仅为工作指引编号，不是八阶段、项目五阶段或新的 current_stage。

| 指引 | 核心问题 / 输入 | 必须做的动作 | 方法可选 | 交付物及接收条件 |
|---|---|---|---|---|
| A0 明确问题 | 客户需要什么，差距是什么？读取目标/投诉/指标 | 限定客户、端到端起止、业务群组；写分析问题、风险红线和完成标准 | SIPOC、客户声音、KPI 定义 | 分析约定；Owner/接收方确认问题值得分析，缺资料则列采集任务 |
| A1 核实事实 | 实际怎么跑？读取现场/表单/事件 | 按样本核对活动、执行者、输入输出、作业/等待、例外、手工/系统和制度差异；标来源及未知项 | 现场走查、访谈、泳道、事件日志/挖掘 | 实际现状及差异记录、模型版本、样本清单；不能用制度图或假设图冒充实测 |
| A2 固定基线 | 问题多严重？读取 A0/A1 | 固定定义、样本范围、窗口、单位、分母、排除项；核验数据质量和可复算性 | 时间分解、频次统计、质量统计、成本/体验基线 | 冻结口径和前侧样本；未取到数据明确“待核实”，不填 0 |
| A3 选择诊断路径 | 哪种损失在主导？读取同一基线 | 按问题信号选主路径；记录选法理由；时间/成本/质量/体验做必要制衡 | 瓶颈、VSM、ABC、CJM、规则分析、帕累托 | 问题位置、数量级、影响范围和候选约束；不是直接宣告根因 |
| A4 验证原因 | 为什么发生？是否存在其他解释？ | 鱼骨扩假设，5 Why 深挖可干预机制；为关键假设写验证/反证并采证；独立裁决 | 5 Why、鱼骨、分层比较、记录抽查、受控试验 | 支持/不支持/证据不足的原因清单；关键结论有来源及裁决，不强求问满五次 |
| A5 综合结论 | 解决哪处才能改善客户结果？ | 归并重复发现，比较端到端影响、成本、体验和风险；列明可改约束及不能下结论处 | 影响/证据对照、规则核验、价值判断 | 经确认的问题—根因—损失—客户影响—约束清单，允许有未决项但必须有影响和责任 |
| A6 交付与接收 | 能否交给设计？是否继续采证或无需改动？ | 提交分析结论包；接收方核对输入是否够做方案，确认/退回/继续观察/停止 | 原项目步骤/门禁、Owner 确认 | 有明确接收记录和下一步；批准诊断不等于方案已批准，更不等于改善达标 |

A1/A2 可以来回核实，A3 的多路径可以并行。A4 验证推翻原假设时回 A1–A3，不为维持“全绿”而隐去反证。简单问题可复用有效数据减少操作；裁剪的是重复工作，不是事实依据与客户结果。

## 6. 按问题选路：多种解法，同一价值目标

| 主要信号 | 首选路径 | 必需证据 | 辅助方法与制衡 | 应得到什么 |
|---|---|---|---|---|
| 周期长、排队多 | 时间拆解 → 交接/队列 → 容量与负荷 → 根因 | 同期任务开始/结束、等待、到达和可用能力；日历一致 | VSM、挖掘、排队观测；检查质量和客户反馈 | 真正约束/等待机制、影响量和证据；不把最忙的人直接当根因 |
| 退回多、一次解决低 | 缺陷分类 → 帕累托/分层 → 输入/规则核对 → 假设验证 | 返工定义、次数/业务分母、分类、来源群组 | 鱼骨、5 Why、规则样本；检查是否仅转移缺陷 | 主要失效模式、发生机制和可干预控制 |
| 单笔成本高 | 资源池 → 活动/动因 → 成本对象 → 成本集中点 | 费率、资源池/动因、使用量、期间和分摊依据 | ABC、VSM；核验质量/合规和容量利用 | 成本构成及动因，不是把部门工资粗分当真实逐单成本 |
| 投诉/满意度差，即使处理很快 | 客户声音 → 旅程/触点 → 关键时刻 → 与运行数据对照 | 真实接触记录、客户评价/样本、时间、渠道和群组 | CJM、投诉分类、首解/重开/复联统计 | 体验差距、受影响人群和与效率取舍；不虚画情绪曲线 |
| 条件多、例外绕行 | 收集判断 → 比对制度/实际 → 例外与授权 → 样本验证 | 条件字段、规则版本、来源依据、审批/例外记录 | 决策表、路径变体、相关方确认 | 规则清单、冲突/缺口、控制责任和适用上下文 |
| 只有抱怨、缺数据 | 问题澄清 → 采样计划 → 观察/访谈交叉核对 | 记录可追溯，明确假设与事实的区别 | SIPOC、样本跟踪、字段/时间采集 | 数据缺口及采集行动；不提前给确定根因或精确收益 |

不要求全部方法都用。入口根据问题推荐主路径，使用者可选其他方法但说明理由。最终验收问“是否解释客户结果与可干预问题”，不问“是否用够工具”。

## 7. 关键方法的口径与操作规则

### 7.1 As-Is：实际、制度、假设分开

活动核对表至少含：活动/节点 ID、执行角色、输入/输出、手工/系统及系统名、实际作业/等待、例外条件、来源/样本、数据类别（实测/访谈陈述/模型估算/演练假设）。制度和实际不一致的地方单列，不直接覆盖制度或自动把绕行合法化。

演练可先假设 As-Is，但页头和导出必须标“演练假设”，不能进入正式根因门、运行有效或改善收益样本。访谈是线索，需按风险与数据条件交叉核实；日志也可能缺字段或有系统性偏差，不因为叫“系统数据”就无条件可信。

### 7.2 瓶颈：候选线索不是确认结论

最长耗时、最多待办、最忙岗位、最大成本分别是线索，不是相同概念。瓶颈需与到达负荷、有效能力、在制/积压趋势及端到端结果相互验证；一段长且不限制吞吐的作业不一定是容量瓶颈。

设计器当前标注应称“模型瓶颈候选/周期贡献”，真实队列证据称“运行观察”。不能据一个时间截面的待办数量断定瓶颈，也不能把下游等待误算为该岗位实际劳动。

### 7.3 价值流：三类判定，不能由布尔值猜

按活动的实际作用判 VA（增值）/NNVA（必要非增值）/WASTE（浪费），附客户/法规依据、判断人和模型/样本版本；未知值为待判定。旧 `is_value_added=false` 只能说明非增值，不能自动补成“必须核对”。等待、检验、搬运等不能仅按名称一律判定，必要控制的删除须有替代风险方案。

PCE = 同一口径有效增值时间 ÷ 端到端历时。明确一次通过、返工、分支、并发、工时与历时差异；禁止把多人工作量简单相加除以更短并行历时产生大于 100% 的“效率”。无法统一口径则不给正式 PCE。讲义中的 5%–15% 或 20% 只能作待核背景/教学示例，不能作为全企业自动阈值或验收承诺。

### 7.4 ABC：成本动因与可避免成本分开

首批可用结构化表格，不要求新成本系统：资源/成本池、计量单位、期间、费率/总额、动因量、分配到活动、成本对象/业务样本、来源及估算/实际标签。

直接人工示例：处理分钟 ÷ 60 × 对应时薪；共享成本池按经批准动因分配：成本池总额 × 对象动因量 ÷ 该池总动因量。费率、货币、期间和范围不一致时禁止合计；零动因、未分配和多重分配必须提示。等待不是默认人工投入，不能给同一成本同时计入时薪和资源池两次。

发现合规检查成本占比高，首先验证复杂度、例外量、质量和法规要求；不能直接推导“减少合规”。降低活动时间不自动等于减少现金支出或利润增加；分别记录可避免成本、资源释放和估算节省。

### 7.5 CX：客户反馈与内部猜想分开

触点表含客户群组、旅程位置、客户需求/期望、渠道、实际经历、证据/样本、感受来源、严重性、受影响比例、对应业务节点/规则和结果指标。情绪可来自客户反馈，也可为待验证假设，必须标明，不编造数字评分。

把首响、解决、客户确认、重开/重复联系区分。交付价值的结束点应由客户接受的结果定义，不能以“内部关闭工单”自动视作客户问题解决。

首批用“效率变化—体验变化—证据—取舍”对照表，不强制画二维矩阵；两轴量纲/阈值未定义不得生成任意象限。效率改善但体验变差须显示冲突并交 Owner/客户代表决定，而非隐藏负向结果。

### 7.6 根因：问答生成假设，验证才能形成结论

5 Why 不要求恰好五问，也不能从示例推定每条流程都缺 SLA。鱼骨维度用于探索，不是每格一定有一个真实原因。每个重要原因记录：可检验主张、机制、支持/反证、其他解释、验证方法、范围、证据与独立裁决。

现有项目根因门要求同一主张至少两类已独立裁决的 L1–L3 证据；继续复用，不因两个工具写了同一句话就算两种独立证据。无需强迫所有原因都落到制度层，也不把个人归咎当机制解释。

### 7.7 规则：描述实际，不自动授权执行

规则清单至少含条件字段、比较/阈值、后续动作、优先/默认/例外、适用群组、生效版本、制度来源、Owner、风险/授权及样例。提取规则与审批规则分别操作；VIP“跳过信用检查”等只是讲义例子，未获合规授权不得自动写入执行条件。

## 8. 分析交付包与结束条件

交付包是已有业务记录的引用集合，不新建一套分析资产库。至少能打开：

1. 客户结果、问题与分析任务约定；
2. 实际现状模型/差异及来源；
3. 冻结基线口径、业务范围/窗口、样本和质量；
4. 已选诊断路径、方法输入/结果及关键发现；
5. 根因主张、反证、已裁决结论及未决问题；
6. 时间/质量/成本/体验/风险影响与必要约束；
7. 交给设计的需求、不能越过的控制、后续验证问题；
8. Owner/接收方、核验时间、接收/退回/继续观察/无需改动的决定。

**分析可以结束的条件**：问题及客户结果清楚，现状与样本可追溯，重要判断与证据相称，方法输出可复核，关键不确定性已解决或明确影响/责任，接收方具备开展设计所需输入。资料不足可交“采证计划/暂不下结论”，不能伪造有效诊断；无改动价值可以确认无需改变，不为通关强造方案。

这份接收只确认“分析交付是否足够”，不表示上线就绪、运行有效或改善达标。真正价值达成要在后续设计/运行中按本轮冻结约定验收。项目内引用五阶段第 2 阶段已有步骤/根因门；日常分析无项目则引用原流程记录/工具草稿的核验，不强制先立项。

## 9. 页面、后端和数据怎样落地

### 9.1 前端

保留 `monitor?tab=analysis`，不加顶级导航。分析主区域由“六个并列内容”升级为：

- 顶部：客户结果/问题、当前流程/轮次/版本/口径、实际或演练标签。
- 当前任务：做什么、需要什么输入、推荐方法及理由、直接办理、产出与接收要求。
- 原六分析项作为查阅/专业操作入口，不再用“有几条原因/几个节点”暗示已核验。
- 补“成本与体验”内容，ABC/CX 可分别打开；待实现时明确缺口，不能把节点 cost 和 CJM 文本当完整能力。
- “交付核对”列产物引用、审核结论、缺项和下一步；不新增可手动推进的分析阶段。

首屏突出当前最需要做的一项，其他方法按问题显示；支持返回采证、复用同轮样本和继续未完成记录。帮助解释方法，办理就在当前任务或原专业模块，绝不要求先离开当前范围再重新填一份工具表。

短文案：

| 位置 | 文案 |
|---|---|
| 页面说明 | 从客户结果出发，核实现状、验证原因，形成设计依据。 |
| 起始问题 | 本次要解释哪个客户结果差距？ |
| 选法区 | 推荐分析路径；显示选择依据，不写“最佳算法” |
| 候选结果 | 模型提示的候选问题，尚待运行证据核实。 |
| 假设记录 | 原因假设已保存，尚未验证。 |
| 样本冲突 | 样本与本轮冻结口径不一致，暂不用于结论。 |
| 结束操作 | 提交分析交付 / 接收分析结果 / 退回补证 |
| 无改动决定 | 现有证据不支持改动，记录理由并明确复核条件。 |

### 9.2 后端与原表复用

- 薄轮次对照按确认时点固定本轮身份/交付引用；分析时允许未立项、未上线，不虚构后续版本。不增加AnalysisProject/AnalysisStage表。
- ToolSheet/模板保存具体方法的结构化输入、结果、来源/版本、核验和 output_refs。ABC/CX 方法若当前缺少正式配置，按既有 Tool/ToolTemplate 扩充并标拟新增，不硬编码在前端。
- 现状、活动分类、作业/等待及业务规则由原模型/版本/表单承载；访谈、日志和观察保留原来源。三类价值判定通过原模型字段增量扩展并兼容旧布尔值，未知历史不自动归必要非增值。
- 原异常、KPI、ProjectEvidenceClaim、ProjectStep/GateAttestation 负责问题/样本/裁决/交付；直接引用，不将异常中的 root_cause 文本自动升级为“已验证”。
- 方法映射/推荐依据统一从后端输出，前端不再各维护 TOOL_MOUNTS、方法中文状态及计算公式。
- 算法输出返回 basis、source_refs、model_version、contract_hash、sample_count、quality、limitations；同一计算只有一个服务实现。跨方法复用一份数据，修改正式来源需产生修订，不在方法表静默改正式指标。
- 查询按 process/round/版本/窗口过滤及对象授权。分析只读结果不更改生产流程；“应用规则/提交方案”是单独有权限的动作。

## 10. 投诉处理演练的落地示例

输入只有：首响 4.2 天、首次解决率 58%、满意度 3.1/5。它们是题设，不是已核真实业务基线；没有各活动样本，不能算真实 PCE 或 ABC。

1. 明确客户需要：在约定时间内获得有效响应和真正解决，并理解结果；先定义首响/解决/重开和满意度样本口径。
2. 画假设 As-Is 并标演练；收集/提供后续样本后才确认真实路径，拆清受理、分派、诊断、处理、通知、客户确认与重开。
3. 延迟路径查交接和队列；低首解路径查分类/信息/能力/规则；低体验路径查触点和反馈。三条路径可并行，不预设同一个原因。
4. 鱼骨列假设，5 Why 深挖其中可检验的一条；为每个关键机制指定数据、反证和验证人。
5. VSM 分类活动；有同口径时间才能估算 PCE，明确估算。ABC 需费率与动因，才能列成本最高活动；CJM 需反馈才可确认最差触点，缺时记“候选触点”。
6. 汇总时间/首解/满意度/成本/风险之间的关系：例如自动回复可能缩短首响但不改善解决，不能据此判客户价值已交付。
7. 提交有来源、可反驳、可交给设计的结论。样本不够则交采证计划；已证实问题进入 To-Be 设计，但改后是否有效仍由真实运行与验收决定。

**结论**：可控的流程分析不是每次使用同一套工具，而是任何选路都具有明确输入、可追溯事实、可检验判断、可接收产出和端到端客户价值约束。方法可以不同，证据标准和交付责任不能散。
