## 1. 产品定位

**转型是基于客户/战略结果，选择并实施持续升级的方向，不是工具的终点菜单。** 建模、分析、设计和绩效为它提供事实、方案和验证；转型又把新目标、新标准、组织能力和学习反馈到这些管理活动。

三条路径用于确定改变范围、治理强度、能力和验收；具体实践提供思考、诊断、设计、交付和持续控制方法。只有知识、模板、算法、专业工具、业务系统及组织行为能够按同一依据交付，才称为实践能力。

八阶段的“变革优化”仍进入 projects/项目组合，项目内仍按五阶段推进；Lean/PDCA、DMAIC 等作为原项目方法任务/证据视角，不建立互相竞争的阶段状态机。日常 Kaizen/异常处置不强制每次立项；结构性变更才按批准范围形成项目和轮次。项目结束，流程及有效做法继续运行。

## 3. 三条路径作为底层选择逻辑，而不是三档工具套餐

| 路径 | 核心判断 | 典型工作/适用实践 | 必交结果和风险 |
|---|---|---|---|
| 持续改进 | 当前价值逻辑/框架仍有效，有局部浪费、流动/标准执行问题 | Lean、PDCA、Kaizen、标准作业；适用时借助TOC/统计方法 | 局部改变不转嫁损失，有实际效果和持续控制；小改也不能绕安全/授权 |
| 流程改进 | 框架可用，但存在系统性失效、波动、质量或协调问题 | 数据驱动诊断、DMAIC、Lean Six Sigma、TOC等 | 测量可信、机制验证、方案/试点及控制有效；不是“中等百分比”自动套DMAIC |
| 流程再造 | 战略/客户价值/服务方式变化，原假设或端到端架构已不适配 | BPR、业务/价值流重构、组织授权和系统协同；可结合精益/统计 | 新价值逻辑、架构/角色/控制/系统和采用成套交付；大收益愿望本身不是再造依据 |

三条路径不是对 Lean/Six Sigma 能力上限的普遍断言。Lean也可用于端到端，组织调整也不必然升级BPR。选择至少考虑客户差距、战略适配、根因/数据、风险、依赖、授权、实施能力与成本；目标幅度只作一个信号。

推荐输出：主路径、证据、关键假设、可选替代、能力缺口、风险、所需授权、下一步验证。现有confidence未经校准不能表述为“成功概率”；范围/证据变化可复评，保留原选择，不静默给项目换方法。

现有 BPR/BPI/LEAN/HYBRID code 先兼容，不用批量改码解决理论问题。界面区分“改变路径”与“使用实践”，允许同一项目以一个主路径和多个明确分工的实践交付。

## 4. 三层分类：方向、实践、能力

| 层 | 内容 | 不能混同 |
|---|---|---|
| 转型路径 | 持续改进/流程改进/流程再造 | 工具清单、行业域或软件引擎 |
| 实践体系/领域 | Lean、Six Sigma、TOC；SCM等领域管理体系与行业配置 | 都当互斥的Project.methodology枚举 |
| 可交付能力 | 知识、诊断、工具/算法、外部服务、验证、实施与固化 | 写一篇介绍或挂一个API链接就算具备能力 |

SCM提供供应链端到端计划/采购/生产/交付/协同等管理场景；Lean关注价值/流动/浪费；Six Sigma关注测量与变异/缺陷；TOC关注系统约束与整体产出。它们作用层次不同，可以共同服务同一问题，不能凭名字并排打分选唯一胜者。

## 5. 实践纵深：每个体系必须交付完整能力路径

每个实践用原 Tool/ToolTemplate/案例/标准及其元数据形成版本化能力清单。首批用引用目录/配置，不先建“实践主库”。最少包含：

**要解决的问题与价值逻辑 → 适用/不适用和前提 → 必需输入/测量 → 诊断方法 → 设计/干预 → 验证 → 组织采用 → 持续控制/复用。**

每一步声明原记录位置、输入/输出、方法/算法版本、责任/能力要求、审核、证据和下一步；区分仅参考、可填写、可计算、外部验证、已集成并验证。覆盖缺口必须可见。

| 实践 | 应有的纵向链 | 关键质量门与能力边界 |
|---|---|---|
| Lean | 客户价值→实际价值流→浪费/流动→拉动/在制/标准作业/Kaizen→验证→日常管理 | 不只列七浪费/5S；核验端到端、客户质量、必要控制；局部利用率不等于整体流动 |
| Six Sigma | CTQ/问题→操作定义/采样→测量系统适用性→变异/能力→假设/原因验证→试验/措施→控制 | 统计方法前提、量表、分布/独立性/稳定性、样本/不确定性和专业复核；未做MSA/DOE/控制限算法就不显示“已完成” |
| TOC | 明确系统目标/边界→识别约束→充分利用→其他环节协同约束→提升约束→重新识别 | 最忙/最慢不是自动约束；缓冲/在制/吞吐共看；禁止各部门局部提效让约束更堵 |
| SCM/行业实践 | 客户服务承诺→供应链策略/架构→需求/供给/库存/计划协同→供应商/执行→风险→绩效与再平衡 | SCOR/APQC作为参照不直接充当企业规则；主数据、计划周期、伙伴权限、波动/服务/成本需共同验证 |
| BPR | 客户/战略重构需要→挑战原假设→备选服务/价值结构→To-Be→治理/系统/岗位→试点和采用→成果持续验证 | 不以“节点删得多”或自动化比例评价；组织授权、客户体验、控制与切换风险不可省 |

3.4 PPM/DPMO、六西格玛水平及长期漂移约定不能作为所有流程统一目标，也不能不注明“缺陷机会”就与不良品率互换；本稿未核讲义的官方考点/统计出处。方法能力必须按具体业务和统计前提评价，不靠认证名称代替结果。

## 6. 横向融合：一套事实、多种视角、明确交接

融合不是每个体系各跑一遍完整阶段、各造基线、各报收益。统一：

- 客户/战略目标、业务范围和硬约束；
- 同一As-Is、采集事实与操作定义；
- 同轮的process_id/project_id/模型引用/冻结口径；
- 原风险、授权、变更、培训和恢复记录；
- 共同收益/副作用验收，避免Lean省一次工时、Six Sigma降一次返工后重复算同一收益。

方法之间保留差异：同一“产能”“缺陷”“客户及时交付”不能只因词相近合并。跨体系交接表明输入、映射、单位/时间/粒度、不可比部分和接收人；冲突由Owner/有权业务方依据客户结果和风险裁决。

示例：订单交付不稳定，先用SCM定位需求/供给/库存承诺，TOC核实系统约束，Lean改善约束周边流动与在制，Six Sigma验证关键缺陷/波动，必要时BPR重构服务或职责，再由变更管理支持采用。具体顺序随证据改变，不宣称这串组合总是最佳。

## 7. 转型作业小闭环

T0–T7是作业指引，不是另一套项目进度字段。

| 工作 | 要回答/动作 | 原业务产出与验收 |
|---|---|---|
| T0 确定方向 | 客户/战略差距是什么？现有框架哪里不适配？ | 原目标/分析证据/章程；是否值得改，有权Sponsor和Owner确认 |
| T1 选择路径 | 哪条主路径适合，哪些假设待验证？ | 原方法论推荐加路径决定，保留替代/风险/理由，不靠目标百分比独断 |
| T2 配置实践能力 | 选主实践/辅助实践，检查数据、技能、工具和外部能力 | 原工具使用计划/模板引用和能力缺口；方法有输入输出和接收要求 |
| T3 组织与方案共同准备 | 利益相关者、岗位/权限/激励、方案和控制怎样一起变？ | 原设计/变更/RACI/ADKAR/沟通/培训证据；不把变革管理推迟到上线前发通知 |
| T4 验证与切换准备 | 技术、业务、人员、合作方及恢复能否承接？ | 原测试/试点/回退/培训核验；限定范围和准入，失败可停止 |
| T5 受控采用 | 新版真实被用了吗？旧路径/例外/人工后备如何共存？ | 原实例/数据、采用/例外与支持记录；分母可解释，不强迫用户隐瞒问题 |
| T6 结果与行为核验 | 客户/经营结果、风险、能力和真实采用是否改变？ | 同轮样本、独立效果验收、组织行动核验；不以发布/签到等同转型成功 |
| T7 固化与再选择 | 哪些保留、推广、停止，下一约束/目标是什么？ | 原标准/控制/复盘/复制包，项目结项流程继续，必要时下一轮新项目 |

可在一个项目中组合方法，但Project.current_stage仍为1–5。DMAIC/PDCA任务关联相应ProjectStep和证据，方法视图不与current_stage互相推进；不要求所有日常改善都填满24步，裁剪须遵守批准规则而非偷偷跳门。

## 8. 人与文化：以保障原记录核验，不造新任务堆

ADKAR用于发现需要补什么，不用于给人员贴“抵抗者”永久标签。利益相关者中也包括客户、合作伙伴、一线和受影响岗位；“阻力”可能是新方案风险或实际障碍，应反馈设计，不一律当成沟通不足。

| 关注 | 保障动作 | 能证明什么 / 不能证明什么 |
|---|---|---|
| 为什么变 | Sponsor明确问题/影响，听取疑虑并回应 | 信息确实被理解；发过邮件不代表理解 |
| 愿意参与 | 澄清岗位/工作负担、公平影响、支持和反馈渠道 | 承诺及参与行为；不要求收集心理评分作为自动准入 |
| 知道怎么做 | 分角色教材、导师/培训、可查标准 | 具备学习资料；签到不等于掌握 |
| 能做到 | 演练、试运行、辅导、权限/工具/资源到位 | 实际操作验证与补训；不能用“不愿意”掩盖系统不能用 |
| 能持续 | Owner复盘、共同目标、真实采用、反馈和认可 | 经过窗口验证的持续行为；一次上线/庆祝不等于文化完成 |

复用章程、RACI、培训、复盘、异常/项目步骤，缺责任、期限、核验字段才补原对象。此前20项保障清单只是这些原记录的核验投影，不生成20条平行任务。可见范围、人员隐私、HR政策和职责分离必须遵守；系统不自动判定晋升/薪酬。

## 9. 外部能力与集成：能力契约先于连接器

“支持外部能力”包括知识/标准、专家服务、统计/仿真工具、ERP/MES/WMS/CRM数据和执行系统，不意味着把全部算法嵌入PMS。

| 外部能力 | 接入方式 | 必须控制的契约 |
|---|---|---|
| 行业实践/标准/案例 | 官方/授权内容引用、组织模板、受控导入 | 来源、版本、许可/署名、适用条件、有效期、中文译文口径；不用未经授权全文当种子 |
| 统计/仿真/优化 | 文件/报告先行，成熟后受控API | 问题、输入数据/哈希/版本、方法及参数/前提、输出/不确定性/限制、审核、回写对象 |
| 外部专家 | 原项目交付物/评审引用 | 范围、保密、责任、证据来源和接收；专家结论不能绕过业务授权 |
| 业务数据 | 原DataFlow、签名入站/明确拉取适配器 | 数据责任、字段映射、业务键、单位/时区、同轮口径、授权最小化、质量/幂等/补数 |
| 外部执行 | 原Outbox/入站与受控连接器；Flowable依R3 | 命令/事件契约、权限、确认/重试/对账、超时未知、补偿及运行责任 |

能力统一用独立属性“参考说明、可填写、直接办理、可计算、外部核验、已验证集成”声明，附范围/版本/限制，不作为自动递增成熟等级。HTTP 200不等于业务成功，报告已接收不等于结论已核验；来源/目标、字段、凭据、文件和数据最小化受控。

首批从原文件/模板/报告和现有集成接口建立可追溯的输入—结果—审核链，不先建万能插件市场或让用户上传任意脚本执行。每次外部计算/调用记录输入版本、operation/job ID、状态、结果和原目标引用；失败/结果不明可查原操作，不能重试后重复下单/付款。无连接器时明确人工受控导入，不冒充实时自动化。

## 10. 恢复与业务连续性：不能把“有备份”当通过

讲义的Solution Blackout不能直接译为技术“黑启动”；应按原文语境区分停机/不可用窗口、业务连续性、回退和灾难恢复。本次未核Competency Model原件，不作官方技能/译法结论。

四类方案分别核验：模型/应用版本回退、外部业务补偿、数据/系统恢复、人工/备用业务连续性。它们不能互相替代。切旧版本不撤销已付款/建单，取消实例也不等于补偿完成。

最低演练链：

1. 业务影响分析：关键服务、依赖、最大可容忍中断、RTO/RPO由业务与IT批准；示例2小时/零丢单不作默认承诺。
2. 触发/指挥：谁宣布中断、冻结哪些写入、谁切后备、何时通知客户/员工/伙伴。
3. 后备办理：唯一业务编号、授权、敏感资料、容量与工作积压、人工留证；避免新旧两边同时无控制接单。
4. 恢复/对账：恢复数据/附件/密钥/配置及集成游标，核对在途和外部副作用；人工后备补录幂等且顺序/审批可追踪。
5. 回切与验收：谁确认依赖就绪，怎样逐步恢复，检查重复/丢失/不一致及客户结果，实际记录耗时/数据损失。
6. 复盘修订：失败和未达目标保留，修原预案/培训/技术方案，复测。

当前SQLite演练验证临时样例数据的备份恢复；PostgreSQL分支仅schema-only且不覆盖业务数据/附件/外部系统，不能用脚本打印通过证明生产DR。RPO=0需跨系统持久接收/复制/对账设计和演练证据，不因配置一项“0”自动成立。所有演练先在隔离环境；不得把当前脚本指向真实业务库执行恢复。

## 11. 界面与数据落点

保持变革优化→projects。原项目详情/工作台中组织以下工作区，而非新增平行转型主模块：

- **方向与路径**：客户/战略差距、选择/替代、证据和授权；
- **实践方案**：主/辅实践、能力路径、产物依赖及缺口，直接进入原工具/分析/设计；
- **采用与切换**：原ADKAR/相关方/培训/上线/恢复记录的核验；
- **效果与迭代**：同轮对照、原验收、控制/复制和下一步。

Tool/ToolTemplate等增加必要的实践引用/关系元数据及版本，不按行业复制整套工具。原Project保存主路径和方法选择依据，原步骤/证据承接产物；薄对照固定正式本轮引用；原ReplicationPack记录适用性与来源；原集成模型承接受控能力调用，确需新作业基础设施时单独论证实施范围。

短文案：“路径建议，待依据核验”“本实践具备填写模板，统计验证尚未接入”“外部结果已接收，待审核”“培训已完成，实际采用待验证”“恢复演练未满足约定目标，请修订方案”。不说“选精益即可提升X%”“有DMAIC标签即已六西格玛”“复制成功即转型完成”。

## 12. 实施顺序与验收

1. 明确路径/实践/工具三层契约，修正把目标幅度当方法能力定律的推荐；
2. 先把一项主实践做深到实际产物/核验，建立共同输入输出结构；
3. 用同一真实流程验证两项实践的交接、冲突和收益去重；
4. 补外部报告/专家/数据的受控接收，再按需求建立专业API集成；
5. 人员采用、恢复和持续控制贯穿，不能排到“最后才做”；
6. 验证结果/采用持续后才复制，下一轮根据新约束和客户需求重新选择。

后续测试：路径建议可解释及复评；BPI≠Six Sigma；DMAIC不改项目五阶段；实践缺能力不冒充已集成；方法间口径映射/冲突/收益不重复；同轮四身份；ADKAR草稿/签到不自动有效；原保障记录去重；外部重复/超时/恶意或越权回写；恢复在隔离库、后备补录/外部对账及实际RTO/RPO；复制拒绝理由/条件/版本可追溯。

代表落点：`methodology.py`、`tool_lifecycle.py`、`tool_sheet.py`、`project_workflow.py`、`projects.py`、`inbound.py`、`integrations.py`、`replication.py`及原测试；前端projects/workflow/toolbox和帮助，不改现有主跳转。后端pytest、前端verify_frontend、schema走Alembic、真实外部/恢复集成分项验证；本次均未执行。

**验收底线**：不是实践名称齐全，而是能说明为什么选、缺什么、怎么联合交付、谁真正采用、结果和风险如何验证、失败怎样保业务，再把经验证做法反馈到持续运行的流程。纵深是实践能做成事，融合是大家在同一客户价值和证据上做成同一件事。
