# Logix PMS 流程经营管理系统规格

> 版本：v1.0
>
> 日期：2026-11-13
>
> 状态：系统级业务规格草案，尚未进入代码实施。

## 1. 系统定位

**Logix PMS 是一个把战略目标、流程架构、组织责任、资源能力、执行控制、绩效结果和持续改善绑定在流程对象上的流程经营管理系统。**

系统的最终用户目标不是查看页面、维护流程图或填完一套表单，而是：

```text
从一个业务目标或问题出发
→ 建立/识别一条流程
→ 明确它要交付的结果
→ 让组织、岗位、资源和控制条件到位
→ 让员工能够按标准执行
→ 让系统记录真实运行
→ 用绩效和工作量验证结果
→ 根据证据改善、固化和复制
```

`L3-032 采购需求提报` 只是当前测试与反推样本，用于验证系统能否支持上述从 0 到 1 的过程；它不是生产规则、唯一流程模板、固定业务边界或系统最终对象。

## 2. 目标用户结果

业务负责人最终应该能够针对任意一条流程作出以下决定：

```text
开始识别
批准改善
批准设计
批准试点
批准上线
暂缓并补齐缺口
回退重新设计
继续改善
固化并复制推广
```

系统必须解释每个决定的依据：

```text
当前事实
→ 已有证据
→ 缺口和风险
→ 责任人
→ 下一步动作
→ 预计验证方式
```

系统不能只显示“完成/未完成”，也不能把数据库中存在一条记录当作业务事实已被确认。

## 3. 系统核心对象

### 3.1 唯一经营对象：流程

```text
Process / L3 流程
```

流程是目标、组织、资源、执行和绩效的共同上下文。

### 3.2 流程下的事实对象

```text
L1/L2 架构归属
L4 活动
流程边界与结果
战略目标与 KPI
模型节点与版本
岗位、人员与 RACI
表单、规则与控制点
SOP、制度、工具与培训
系统、数据、接口与资源
标准工时、实际工时与产能
风险、授权与例外
项目、试点与阶段门
运行实例、任务与异常
绩效、改善轮次与复制包
```

### 3.3 事实、证据、决策三层分离

| 层 | 作用 | 示例 |
|---|---|---|
| 事实 | 系统记录对象和关系 | L3-032 有 6 个 L4、2 个表单 |
| 证据 | 证明事实或结果已经成立 | 业务确认、真实运行、下游签收、正式 KPI |
| 决策 | 根据事实和证据采取动作 | 批准试点、暂缓上线、继续改善 |

系统不能把三层混为一谈：

```text
有字段 ≠ 已确认
有配置 ≠ 可运行
有执行实例 ≠ 真实试运行通过
有 KPI 定义 ≠ 正式绩效成立
有 SCOR/APQC 映射 ≠ 最佳实践已落地
```

## 4. 用户从 0 到 1 的通用主线

三个工作台入口保留，但它们是三种起点，不是三套孤立系统：

```text
工作台
├── 流程框架：识别公司流程家底，选择或建立流程
├── 一条流程：进入某条流程的经营主线
└── 一个项目：进入改善工程，回到关联流程上下文
```

选定一条流程后，系统主线必须按当前任务引导，而不是按历史模块平铺：

```text
0. 选择/建立流程
1. 目标与结果
2. 边界与架构
3. 现状与问题
4. 设计与控制
5. 组织与资源
6. 工作指引与能力
7. KPI、工作量与数据
8. 试点与上线
9. 运营、改善与复制
```

每一步必须输出：

```text
当前结论
阻断项
待确认项
责任人
证据要求
下一步
```

## 5. 通用验收能力框架

原来的 12 个验收门不再是 `L3-032` 的业务验收表，而是系统对任意流程提供的通用经营能力框架。

### Gate 1：战略与目标承接

系统帮助用户回答：流程为什么存在、承接什么目标、要交付什么结果、谁负责。

最低能力：目标关系、基线、目标值、责任人、批准依据、KPI 承接。

### Gate 2：流程边界与架构归属

系统帮助用户明确 L1/L2/L3/L4 位置、起止事件、范围、输入、输出、上下游和 Owner。

最低能力：流程边界记录、上下游确认、范围版本和冲突提示。

### Gate 3：客户/下游结果与服务承诺

系统帮助用户定义谁接收结果、如何判定接收、如何拒收/退回/返工。

最低能力：输出验收标准、交接字段、时限、接收记录和退回原因。

### Gate 4：业务过程与控制

系统帮助用户把活动、模型、表单、规则、时限、升级、异常和版本绑定起来。

最低能力：关键路径可运行、条件可判断、关键控制可审计。

### Gate 5：组织、岗位与责任

系统帮助用户把流程 Owner、活动、岗位、人员、RACI、审批、替补和升级责任绑定起来。

最低能力：唯一 A、执行岗位、实际分派、职责分离和责任有效期检查。

### Gate 6：工作内容、能力与工作指引

系统帮助用户把活动转化为员工能执行的工作内容：输入、步骤、标准、异常、SOP、工具、培训和能力核验。

最低能力：关键活动存在有效版本的可执行指引，不把培训签到当作能力证明。

### Gate 7：系统、数据与资源

系统帮助用户确认人员、系统、数据、接口、表单、制度、工具、设备和降级方案是否可用。

最低能力：最小运行资源检查、数据来源检查、资源责任人和阻断处理。

### Gate 8：KPI、绩效与收益

系统帮助用户定义并验证指标：目的、CSF、公式、范围、来源、质量、目标、阈值、责任、行动和收益。

最低能力：能区分正式绩效、待核数据、样本不足和数据质量问题。

### Gate 9：工作量、效率与能力配置

系统帮助用户计算标准工作量、实际工时、等待、返工、可用工时和负荷，并支持组织/能力决策。

最低能力：支持“不适用/轻量核验/正式分析”分级，不用单流程样本冒充生产跨流程负荷。

### Gate 10：风险、授权与合规

系统帮助用户登记风险、控制点、授权、例外、有效期、审计、变更门禁和风险接受。

最低能力：风险结论能够影响试点/上线决定，例外不会绕过审计。

### Gate 11：试点、采用与上线

系统帮助用户准备和记录真实试点：范围、人员、数据、旧路径、回退、采用、下游接收和业务 Owner 决定。

最低能力：能区分系统冒烟、受控试点和正式上线，不用 Seed 数据冒充真实业务证据。

### Gate 12：运营、改善与复制

系统帮助用户持续采集、解释偏差、执行行动、验证效果、固化标准和复制推广。

最低能力：上线后复核，不作为新流程首次上线前的硬阻断。

## 6. Gate 的生命周期位置

12 个 Gate 按三个时间层组织：

### A. 上线准备层

```text
Gate 1–10
```

判断：是否具备受控试运行条件。

### B. 试点/上线决策层

```text
Gate 11
```

判断：真实试点后是否批准上线、暂缓或回退。

### C. 运营有效性层

```text
Gate 12
```

判断：上线后是否持续有效、固化或复制。

Gate 12 不能作为新流程首次上线前的硬阻断。

## 7. 通用状态模型

每个 Gate、每个验收项和每条证据都必须区分：

```text
未开始
进行中
阻断
条件通过
通过
不适用
```

同时记录：

```text
责任人
核验人
证据等级
风险等级
截止时间
下一步
影响的决策
```

证据等级：

```text
E0：页面/字段/标签存在
E1：系统配置或数据关系存在
E2：正式确认、审批、责任接受或版本记录
E3：真实业务运行、真实数据、下游接收
E4：同口径效果验证、独立复核、复制结果
```

## 8. L3-032 样本的正确角色

`L3-032 采购需求提报` 只用于：

1. 验证系统是否能处理一条 L3、6 个 L4 及其关联事实；
2. 验证用户能否沿 0 到 1 主线完成目标、过程、组织、资源、绩效和改善动作；
3. 暴露系统缺失的事实模型、证据模型、决策模型和页面引导；
4. 作为回归测试的干净样本。

它不用于：

- 定义生产只能有一条流程；
- 预设所有流程都必须有相同 KPI、组织或方法；
- 用 Seed 数据证明真实上线；
- 把 L3-032 的当前状态直接写成生产规则；
- 决定所有页面都必须保留或删除。

## 9. 最佳实践的集成契约

最佳实践不是平行页面，也不是全部流程的必选菜单。每个实践必须说明：

```text
为什么选择
适用前提
输入数据
方法/算法版本
输出结果
责任人
专业核验
影响哪个 Gate
如何验证有效
```

| 实践 | 主要作用 | 系统落点 |
|---|---|---|
| PMO | 目标、项目、阶段门、风险、收益和结项 | 项目/阶段门/证据/决策 |
| 精益 | 价值、流动、等待、返工、标准作业 | 现状分析/设计/工作量/KPI |
| 六西格玛 | 缺陷、测量、变异、根因和控制 | 数据质量/分析/改善/运营 |
| SCOR | 供应链分类、计划、采购、交付和对标 | 参考映射/供应链 KPI/差距 |
| APQC | 流程分类、能力缺口和外部参照 | 分类/覆盖度/对标 |
| IPD | 产品/研发流程的跨职能、阶段评审和需求冻结 | 仅适用流程的模板/门禁 |
| 供应链实践 | 需求、供给、库存、计划、服务、成本和风险 | 目标/边界/控制/KPI/资源 |

适用实践应判定为：

```text
适用
部分适用
不适用
```

“不适用”不是缺口；“有方法名称”也不是已集成。

## 10. 当前能力与系统缺口的判断方式

后续每个能力都用三栏评估：

| 系统能力 | 当前已有 | 需要补齐 |
|---|---|---|
| 目标承接 | StrategyObjective、流程/KPI 关联 | 批准依据、责任、CSF/决策用途 |
| 过程控制 | 模型、表单、规则、执行 | 活动级时限、升级、异常和完成标准 |
| 组织责任 | Owner、岗位、RACI、治理角色 | 活动级唯一 A、实际分派、替补/升级 |
| 资源能力 | 工时、产能、表单、数据、工具 | 统一活动资源视图、可用性和缺口决策 |
| 工作指引 | 文档、工具、培训、交付物 | 活动级工作包、版本一致性、操作验证 |
| KPI | 定义、记录、阈值、流程/活动关联 | 来源质量、窗口快照、偏差行动和收益验证 |
| 工作量 | 标准工时、实际工时、产能汇总 | 按岗位/流程分组、跨流程负荷和前后对照 |
| 治理 | RACI、授权、例外、审计 | 责任/权力一致性、风险接受、效果核验 |
| 试点运营 | 执行、异常、项目、改善、复制能力 | 真实试点、采用、下游接收、上线决策 |

## 11. 页面反推规则

本规格不提前决定页面保留、合并或后台化。页面资格由它对系统主线的实际贡献决定：

### 主线页面

必须直接帮助用户完成当前 Gate 或作出流程决策，能够显示：

```text
当前结论
阻断
责任人
证据
下一步
```

### 聚合/投影页面

可以展示同一流程事实的另一种业务视角，但不能复制第二套数据口径。

### 后台能力

主要维护主数据、配置、方法、权限、参考框架、接口和扫描规则；它可以被主线调用，但不应该强迫业务用户先理解它。

### 页面挂载顺序

每次只处理一个主题：

```text
明确用户任务
→ 明确输入事实
→ 明确输出证据/决策
→ 明确阻断和下一步
→ 用 L3-032 验证
→ 再决定是否挂载
```

## 12. Process Operating Contract 生命周期

### 12.1 经营周期是流程 Gate 的历史边界

Gate 状态不能直接写在 `ProcessArch` 上，也不能让一条流程只有一份可变的当前验收表。任意 L3 可以经历多次改善、试点、回退、重新上线和运营复核，因此系统需要一个通用经营周期概念：

```text
ProcessOperatingCycle
├── process_id                 # 任意 L3
├── project_id                 # 可空；关联本轮改善工程
├── model_version_id           # 可空；本周期采用的设计版本
├── cycle_type                 # BASELINE / IMPROVEMENT / PILOT / OPERATING
├── status                     # DRAFT / ACTIVE / CLOSED / SUPERSEDED
├── started_at
└── closed_at
```

同一流程可以有多个历史周期，但同一时刻只有一个适用的 ACTIVE 周期；历史周期不可被后续周期静默覆盖。

### 12.2 Gate 评估是周期级事实

每个周期包含 Gate 评估记录，而不是把 Gate 状态塞进流程主表：

```text
ProcessGateAssessment
├── cycle_id
├── gate_key
├── status
├── applicability            # APPLICABLE / NOT_APPLICABLE
├── rigor                    # STANDARD / LIGHT / FULL
├── owner_user_id
├── verifier_user_id
├── risk_level
├── conclusion
├── next_action_ref
├── due_at
└── updated_at
```

`NOT_APPLICABLE` 不是默认逃生口：必须有理由、确认人、适用范围和必要时的失效/复核日期。Gate 7 和 Gate 9 必须支持 `STANDARD/LIGHT/FULL` 的严谨度选择；其他 Gate 只有在其定义明确允许时才可标记不适用。

Gate 评估是对现有事实服务的聚合与决策层，不取代现有来源：

```text
asset readiness
execution readiness
ProjectGateCondition
EvidenceClaim
ExceptionEvent
ProjectStep
RACI / KPI / workload 服务
```

冲突时，原事实来源优先；Gate 记录保存冲突、缺口和引用，不复制另一套事实。

### 12.3 证据引用是可审计关系

Gate 不复制业务事实，而引用原对象：

```text
ProcessGateEvidence
├── gate_assessment_id
├── source_type
├── source_id
├── source_version_or_hash
├── evidence_grade       # E0–E4
├── verification_status
├── verified_by_user_id
├── verified_at
└── verification_note
```

证据等级含义：

```text
E0 页面/字段/标签存在
E1 系统配置、数据关系或模型记录
E2 正式确认、审批、责任接受或版本记录
E3 真实业务运行、真实数据或真实下游接收
E4 同口径效果验证、独立复核或复制结果
```

系统可以根据来源提出证据等级建议，但业务核验人确认最终等级。Seed、开发测试数据和系统冒烟最高只能作为工程验证，不能自动升级为 E3/E4。

### 12.4 流程决策必须留痕

可用决策不是临时按钮，而是可审计记录：

```text
ProcessOperatingDecision
├── cycle_id
├── decision_type
├── decision
├── decision_by_user_id
├── authority_basis
├── reason
├── evidence_snapshot
├── decided_at
├── valid_scope
└── follow_up_due
```

决策类型至少包括：

```text
START_IDENTIFICATION
APPROVE_IMPROVEMENT
APPROVE_DESIGN
APPROVE_PILOT
APPROVE_LAUNCH
HOLD
RETURN_TO_DESIGN
CONTINUE_IMPROVEMENT
STANDARDIZE
REPLICATE
```

项目阶段门、异常关闭或模型发布可以成为流程决策的证据，但不自动等于流程层的上线决定。正式上线、固化和复制的授权人不是由系统角色固定推导，而是按流程经营对象配置的指定决策人；每条流程/经营周期可以指定不同的上线授权人、复核人或复制批准人。系统在写入决定时必须校验指定人处于有效状态、属于适用组织/权限范围，并能引用对应的授权规则、章程或流程配置。`ADMIN`、`MANAGER` 或流程 Owner 身份本身不自动等于正式上线批准权。指定人变化必须保留历史，不得回写覆盖已作出的决定。

### 12.5 Gate 11/12 状态机

```text
Gate 1–10 达到受控试点条件
→ 创建/激活 PILOT 周期
→ 真实试点与采用证据
→ Gate 11 评估
→ 流程层批准上线/暂缓/回退
→ 创建/进入 OPERATING 周期
→ Gate 12 运营复核
```

Gate 12 永远不作为新流程首次试点或首次上线的前置硬阻断。回退、重新试点或新改善周期不删除旧周期和旧证据，而创建新周期并保留来源关系。

### 12.6 主线与 Gate 正交

用户主线回答“现在应该做什么”，Gate 回答“是否具备进入下一生命周期的条件”。`current_gate` 不同时承担页面导航位置和生命周期状态；主线页面读取 Gate 结果，但不复制 Gate 判定。

## 13. 第一阶段计划边界

本规格确认的下一阶段不是“补齐 L3-032 的业务缺口”，而是建设系统级能力：

1. 建立通用 Process Operating Contract：流程对象、Gate、状态、证据、责任和下一步；
2. 建立通用的流程经营清单数据结构，不把 L3-032 编码写进生产逻辑；
3. 用 L3-032 演练从 0 到 1 的第一条垂直主线；
4. 通过样本暴露缺失的事实/证据/决策能力；
5. 再反推页面保留、合并和后台化；
6. 后续每次只挂载一个经过验证的主题。

第一阶段不包含：

- 真实生产上线承诺；
- 让 L3-032 的数据成为生产规则；
- 一次性重写全部页面；
- 为每种最佳实践建立平行引擎；
- 新增第二套流程目录、项目引擎或指标主库。

## 14. 完成标准

当系统能够用同一套通用契约引导 L3-032 完成以下过程时，第一阶段系统能力才算形成：

```text
用户选择流程
→ 系统显示当前目标和边界缺口
→ 用户补齐事实和证据
→ 系统给出下一步和责任人
→ 用户完成过程、组织、资源、指引和 KPI 配置
→ 系统区分工程基线与业务证据
→ 用户准备并记录受控试点
→ 系统输出试点/上线决策所需信息
```

此时 L3-032 仍只是样本；系统能力才是交付物。
