# L3-032 单条流程最终验收基线

> 版本：v1.0
>
> 对象：L3-032「采购需求提报」
>
> 用途：作为后续页面保留、合并、后台化和逐页挂载的业务判断基线。
>
> 重要声明：本文不是页面设计，也不是“已有功能清单”。它定义一条流程被业务负责人判定为可试点、可上线、运营中或可复制时，必须具备的事实、证据、责任和决策条件。

## 1. 最终结论

一条流程真正完成，不是流程图画完、项目步骤完成或页面数据填满，而是形成一个可以被业务负责人作出以下决定的**流程运行包**：

```text
批准试点
批准上线
暂缓并补齐缺口
回退重新设计
继续改善
固化并复制推广
```

流程运行包必须把以下内容绑定到同一个 L3 经营对象，并能追溯到具体 L4 活动：

```text
战略目标
→ 流程结果与边界
→ 业务过程与控制
→ 组织、岗位与责任
→ 工作内容、能力与工作指引
→ 系统、数据与资源
→ KPI、绩效与收益
→ 工作量、效率与能力配置
→ 风险、授权与合规
→ 试点、采用与上线
→ 运营、改善与复制
```

## 2. 本规格的三层判定原则

任何验收结论都必须区分三层，不能混写：

### 2.1 验收标准

生产环境中，一条合格流程应达到什么状态。

### 2.2 系统能力

当前代码是否能够记录、计算、检查或追踪该事实。系统有字段或页面，不代表业务事实已经成立。

### 2.3 当前证据状态

L3-032 当前是否已有可核验的业务证据。开发/测试 Seed 数据、页面可打开、接口返回成功、管理员填写记录，均不能自动等价为正式业务验收。

本规格中的“当前状态”基于当前代码、当前开发数据库和现有测试结果作出的工程判断；它不是业务负责人签字，也不替代真实现场、真实数据和真实下游确认。

## 3. 状态、风险和证据等级

### 3.1 验收状态

| 状态 | 含义 |
|---|---|
| 未开始 | 尚未形成有效验收输入 |
| 进行中 | 已有责任人和动作，但证据尚未完成 |
| 阻断 | 缺口会阻止进入当前门或阻止上线 |
| 条件通过 | 可继续有限范围工作，但必须带着明确风险、责任人和截止时间 |
| 通过 | 本门的必要证据完整，允许进入下一门 |
| 不适用 | 业务负责人确认本门不适用于当前范围，并记录理由 |

### 3.2 风险等级

| 等级 | 含义 |
|---|---|
| 硬阻断 | 未关闭不得试点或上线 |
| 重大风险 | 需要有权人接受风险或限定范围后才能继续 |
| 一般缺口 | 不影响当前有限工作，但必须有责任和期限 |

### 3.3 证据等级

| 等级 | 证据示例 | 能证明什么 |
|---|---|---|
| E0 | 文案、标签、页面存在 | 系统有表达能力，不能证明业务成立 |
| E1 | 数据关联、配置、模型记录 | 系统记录了关系或配置 |
| E2 | 审批、版本、培训、责任确认 | 有人作出正式确认或接受责任 |
| E3 | 真实运行、真实数据、下游签收 | 业务过程确实发生并产生结果 |
| E4 | 同口径前后对照、独立复核、复制结果 | 结果有效且可持续/可推广 |

上线关键门至少需要 E2；运行和效果门至少需要 E3；固化和复制至少需要 E4。

## 4. 验收记录统一字段

每一条验收记录至少包含：

```text
验收门
验收项
事实结论
证据引用
证据等级
当前状态
风险等级
责任人
核验人
截止时间
下一步
影响的最终决策
```

禁止只写“已完成”“已配置”“有数据”。必须写清：事实是什么、依据是什么、谁确认、是否允许进入下一门。

## 6. 十二个最终验收门

## Gate 1：战略与目标承接

### 要回答的问题

```text
为什么要改善 L3-032？
它承接哪个客户、市场或经营目标？
流程结果是什么？目标值是多少？谁对结果负责？
```

### 必要证据

- 客户/市场/经营要求；
- 已批准的战略或年度经营目标；
- L3-032 流程目标；
- 基线、目标值、单位、周期和来源；
- 目标与 L3-032 的承接关系；
- 目标与 KPI 的承接关系；
- 目标 Owner 和流程 Owner；
- 目标取舍和资源假设。

### L3-032 当前状态

**条件通过；不可作为正式上线证据。**

当前已有“采购需求端到端周期缩短”的目标、项目和 EFF-01 关联能力，但战略批准依据、目标来源、责任确认和正式绩效口径尚未形成完整 E2 证据。

### 硬阻断

- 没有可追溯的业务目标；
- 目标没有基线或目标值；
- 目标没有责任人；
- KPI 与目标关系无法解释。

### 下一步

由业务 Sponsor/流程 Owner 确认：

```text
14 天 → 5 天是否为正式目标？
目标来源是什么？
谁批准？
谁负责结果？
```

### 通过后的决策

允许进入流程边界确认和改善项目正式执行。

## Gate 2：流程边界与架构归属

### 要回答的问题

```text
L3-032 在企业流程架构中的位置是什么？
从什么事件开始？以什么结果结束？哪些内容属于或不属于本流程？
```

### 必要证据

- L1/L2/L3/L4 归属；
- 起始事件和结束事件；
- 输入、输出和接收方；
- 上游/下游交接；
- In Scope / Out of Scope；
- 流程 Owner；
- 边界确认记录和版本。

### L3-032 当前状态

**条件通过。**

架构层级和 6 个 L4 已存在；章程、流程卡和项目范围具备承载能力，但起止、最终接收方和边界确认尚未汇聚为正式 E2 业务结论。

### 推荐边界描述

```text
开始：需求部门提交合格采购需求
结束：采购计划生成并被下游接收
最终结果：完整、合规、可执行的采购计划
```

### 硬阻断

- 起止事件无法被不同角色一致复述；
- 输出没有接收方；
- 流程范围与项目范围混淆；
- L4 活动无法解释为主路径或明确异常路径。

### 通过后的决策

允许进入现状核验和 To-Be 设计。

## Gate 3：客户/下游结果确认

### 要回答的问题

```text
流程输出是否被真实接收？
接收标准是什么？什么情况会拒收、退回或返工？
```

### 必要证据

- 下游接收方；
- 输出验收标准；
- 交接字段和时限；
- 接收/拒收/退回记录；
- 返工原因；
- 客户或内部下游反馈；
- 结果确认人和时间。

### L3-032 当前状态

**未开始/阻断。**

当前有流程模型和执行能力，但没有足够证据证明“采购计划生成并被下游接收”已经作为真实业务结果验收。

### 硬阻断

- 只有系统完成状态，没有下游接收；
- 输出质量没有判定标准；
- 退回/返工没有原因和责任；
- 接收方不认可流程结束条件。

### 通过后的决策

允许把“流程完成”定义为业务结果，而不是节点完成。

## Gate 4：业务过程与控制

### 要回答的问题

```text
6 个 L4 是否能按规则运行？
关键字段、分支、审批、时限、升级和异常是否受控？
模型版本是否可追溯？
```

### 必要证据

对每个 L4 分别核验：

| 内容 | 必须存在 |
|---|---|
| 输入 | 来源和必填条件 |
| 输出 | 完成标准和接收方 |
| 责任 | 执行岗位、审批角色 |
| 表单 | 必填字段和校验 |
| 规则 | 分支/审批/拒绝条件 |
| 时限 | 处理时间和日历 |
| 升级 | 超期责任和动作 |
| 异常 | 处理路径和补偿 |
| 版本 | 模型和配置版本 |
| 审计 | 事件、操作人、时间 |

### L3-032 当前状态

**条件通过。**

当前已有 6 个节点、6 条连线、表单和审批规则，但不能由数量推断 6 个活动均已具备时限、升级、异常和完成标准。

### 硬阻断

- 关键路径不能完整运行；
- 必填字段无法校验；
- 关键分支没有规则；
- 运行实例引用的版本不明；
- 关键控制可以无记录绕过。

### 通过后的决策

允许进入受控试运行准备。

## Gate 5：组织、岗位与责任

### 要回答的问题

```text
谁对流程结果负责？谁执行每个 L4？谁审批？谁协助？谁知会？谁替补和升级？
```

### 必要证据

- 流程 Owner；
- 每个 L4 的唯一 A；
- 执行岗位和账号；
- RACI；
- 审批人；
- 备用责任人；
- 升级责任人；
- 组织和岗位有效期；
- 责任接受记录。

### L3-032 当前状态

**条件通过。**

当前有流程 Owner、岗位、治理角色和 RACI 数据，但 RACI、岗位、Owner Role、实际账号分派是不同层次，尚未证明每个 L4 的执行绑定均已闭合。

### 硬阻断

- 关键活动没有唯一 A；
- A/执行人已停用或不在组织范围；
- 任务无法分派；
- 审批人可审批自己的申请；
- 无替补和升级安排。

### 通过后的决策

允许配置执行并进入岗位工作指引验收。

## Gate 6：工作内容、能力与工作指引

### 要回答的问题

```text
员工能否不依赖口头传授完成每个关键活动？
```

### 必要证据

- 活动工作说明；
- 输入/输出；
- 操作步骤；
- 表单填写说明；
- 判断规则；
- 完成标准；
- 异常处理；
- SOP/制度版本；
- 方法工具和模板；
- 培训/演练；
- 上岗或能力核验；
- 员工可查到的有效版本。

### L3-032 当前状态

**阻断。**

系统有流程文档、工具、培训和交付物能力，但当前没有证据证明 6 个 L4 均已形成可执行的活动级工作指引包。

### 硬阻断

- 员工不知道输入、步骤或完成标准；
- SOP 与模型/表单版本不一致；
- 关键异常没有处理指引；
- 培训只有签到，没有操作验证。

### 通过后的决策

允许受控试运行；正式上线前必须通过。

## Gate 7：系统、数据与资源

### 要回答的问题

```text
人员、系统、数据、制度、接口、表单和授权是否足以支撑流程运行？
缺资源时是否有降级方案？
```

### 必要证据

- 人员和岗位资源；
- ERP/OA/BPM 等系统；
- 数据域、数据流和主数据；
- 表单字段来源；
- 接口和集成；
- 制度/授权依据；
- 工具、设备或外部资源；
- 资源可用性确认；
- 资源缺失的风险接受或补齐计划。

### L3-032 当前状态

**条件通过。**

系统具备组织、岗位、表单、工具、数据治理、授权和集成模型，但当前单流程开发基线中部分资源关系并未形成完整闭环，不能把主数据存在当成资源可用。

### 硬阻断

- 关键系统不可用；
- 关键数据无法取得或质量未知；
- 表单字段没有可靠来源；
- 资源缺失没有责任和降级方案。

### 通过后的决策

允许试运行；关键资源必须在上线前达到 E2/E3。

## Gate 8：KPI、绩效与收益

### 要回答的问题

```text
流程结果是否可测？数据是否可信？偏差是否会触发有责任的行动？收益是否被验证？
```

### 必要证据

每个正式 KPI 必须有：

- 目的和 CSF；
- 结果/驱动作用；
- 公式、分子、分母；
- 范围、粒度、窗口和频率；
- 数据源和数据责任；
- 基线、目标、阈值；
- 质量、时效、样本量；
- Owner；
- 偏差响应规则；
- 复核时间；
- 收益或副作用验证。

### L3-032 当前状态

**条件通过；不可作为正式上线绩效证据。**

当前有 EFF-01、EFF-04、CST-01、HLT-01 等 KPI 定义和记录能力，但当前开发基线仍存在来源待核实、质量待核实和非正式数据状态。

### 硬阻断

- 指标口径无法复算；
- 数据源未确认；
- 样本不足却给出正式结论；
- 红黄绿状态掩盖数据质量问题；
- 收益没有独立验证。

### 通过后的决策

允许把 KPI 用于正式上线和运营决策。

## Gate 9：工作量、效率与能力配置

### 要回答的问题

```text
流程需要多少工作量？岗位是否过载？改善后释放了多少能力？
是否需要调岗、增员、自动化或改变承诺？
```

### 必要证据

```text
L4 活动
→ 岗位
→ 标准时间
→ 业务频次
→ 标准工作量
→ 可用工时
→ 实际工时
→ 等待/返工
→ 负荷率
→ 改善前后对照
```

还必须区分：

- 单流程标准工作量；
- 岗位跨流程总负荷；
- 实际运行工作量；
- 预测/估算工作量。

### L3-032 当前状态

**条件通过。**

当前已有部分标准工时、岗位和产能日历能力，但尚未形成可供业务负责人作出人员、能力或自动化决策的完整结论。单流程测试数据也不能代替生产环境的跨流程负荷验证。

### 硬阻断

- 标准时间没有来源；
- 频次没有依据；
- 可用工时无效；
- 只能看到局部岗位，不能看到跨流程负荷；
- 改善前后口径不可比。

### 通过后的决策

允许进行资源和组织调整决策；不得仅凭局部估算增员或减员。

## Gate 10：风险、授权与合规

### 要回答的问题

```text
哪里不能出错？哪些动作需要授权？例外如何处理？风险是否影响上线？
```

### 必要证据

- 风险与控制点；
- 授权规则；
- 审批角色和阈值；
- 例外台账；
- 失效时间和复盘；
- 审计记录；
- 模型/规则变更门禁；
- 安全、合规和数据访问边界；
- 风险接受决定。

### L3-032 当前状态

**条件通过。**

当前已有授权规则、授权例外、RACI、审计和变更门禁能力，但尚未证明风险结论已统一进入流程上线判定。

### 硬阻断

- 关键风险无控制；
- 审批超授权；
- 例外无失效时间或复盘；
- 关键操作不可审计；
- 高风险问题被一般状态掩盖。

### 通过后的决策

允许在明确授权范围内试点或上线；重大风险必须由有权人接受。

## Gate 11：试点、采用与上线

### 要回答的问题

```text
流程是否真实跑过？员工是否采用？旧路径是否受控？能否批准上线？
```

### 必要证据

- 真实业务试运行案例；
- 真实输入、执行人和任务轨迹；
- 实际处理时间；
- 真实异常和处理；
- 输出和下游接收；
- 培训、演练和采用记录；
- 旧路径/人工后备规则；
- 试点问题和整改；
- 业务 Owner 验收；
- 上线、暂缓、回退或扩大试点决定。

### L3-032 当前状态

**阻断。**

当前执行实例和任务主要证明系统链路可启动，不能替代真实业务试运行、员工采用和下游结果验收。

### 硬阻断

- 没有真实业务试运行；
- 只证明发布，没有证明运行结果；
- 员工不会按新流程执行；
- 旧路径和人工后备无控制；
- 业务 Owner 未作决定。

### 通过后的决策

只能在本门通过后选择“批准上线”或“扩大试点”。

## Gate 12：运营、改善与复制

### 要回答的问题

```text
上线后如何监控？偏差如何进入改善？收益是否保持？能否固化和复制？
```

### 必要证据

- KPI 周期采集；
- 数据质量和口径复核；
- 运行积压、异常和超期；
- 偏差解释；
- 有权决策和行动；
- 行动效果验证；
- 复发处理；
- 标准、培训和模型固化；
- 复制适用条件；
- 接收组织本地验证；
- 复制后的实际结果。

### L3-032 当前状态

**未开始。**

当前已有监控、异常、改善项目、资产包和复制能力，但尚未有正式上线后的持续运营证据，因此不能判定“已固化”或“可复制”。

### 硬阻断

- 上线后无人监控；
- 只关闭异常，不验证效果；
- 项目结项后没有持续流程治理；
- 复制只复制文档，没有接收组织验证；
- 收益重复计算或无法追溯。

### 通过后的决策

允许固化、复制推广或进入下一轮改善。

## 8. 最佳实践如何进入验收，而不是成为平行模块

最佳实践只有在改变验收事实、控制点、指标、行动或结果时，才算被集成。

| 实践 | 主要进入的验收门 | 对 L3-032 的作用 | 不能宣称的结果 |
|---|---|---|---|
| PMO | Gate 1、11、12 | 目标、项目、阶段门、收益、风险和结项治理 | 有项目页不等于收益实现 |
| 精益 | Gate 3、4、8、9、12 | 识别等待、返工、交接和不增值活动，并验证流动改善 | 有 VSM/Kaizen 工具不等于精益改善成功 |
| 六西格玛 | Gate 8、9、11、12 | 定义缺陷、测量偏差、验证根因、控制波动 | 有 DMAIC 标签不等于完成六西格玛 |
| SCOR | Gate 2、3、8、10 | 供应链 Source 参照、供应响应、计划和风险绩效 | 有 S1 映射不等于采用 SCOR 规则 |
| APQC | Gate 2、8 | 分类、能力缺口和外部对标 | 有 PCF 映射不等于行业最佳实践落地 |
| 供应链实践 | Gate 1、3、4、7、8、10 | 连接需求、预算、计划、供应响应、服务、成本和风险 | 有供应链标签不等于端到端协同 |
| IPD | 仅在适用的产品/研发流程中进入 Gate 3、4、5、11 | 借鉴跨职能团队、阶段评审、需求冻结和变更控制 | 不作为采购流程的默认主框架 |

### 8.1 实践集成的求真标准

每个实践至少要留下：

```text
为什么选择
适用前提
输入数据
方法/算法版本
输出结果
责任人
专业核验
与原流程对象的关联
对下一验收门的影响
实际效果
```

“工具存在”“框架已映射”“培训已签到”“接口返回 200”都只能是 E0/E1，不能自动升级为已集成。

## 9. 规格边界

本规格暂不决定哪些现有页面保留、合并或后台化。页面判断必须在这 12 个验收门稳定后，以以下原则反推：

- 直接帮助业务负责人作验收决策的能力进入主线；
- 只维护主数据、规则或方法资产的能力作为后台支撑；
- 同一事实只保留一个来源，其他页面只读投影；
- 页面不因模块名称存在而获得主线资格；
- 页面是否挂载由其对某个验收门的实际贡献决定；
- 每次只优化和挂载一个可验证主题。

## 10. 后续规格变更规则

以下情况必须修订本规格，不得在页面或测试中悄悄改变：

- L3-032 的起止、结果或下游发生变化；
- KPI 正式口径、数据源或目标发生变化；
- 组织责任、授权或风险边界发生变化；
- 试点范围、上线策略或回退条件发生变化；
- 最佳实践被正式采用并改变验收条件。

所有修订必须保留版本、变更理由、批准人、影响的验收门和旧结论。
