# 推介附件｜跨境供应链业务理解与信息化思路

刘志高｜财务 × 现场 × 流程 × 系统 × 经营结果

本文以 Logix 跨境物流项目的业务蓝图与设计资料为基础，说明我如何理解跨境供应链、组织岗位协作，以及规划信息化建设。

## 核心定位

我的能力不只在于懂物流、能向 IT 提需求，而是从经营问题出发，设计跨境供应链流程，并把它转成岗位可操作、数据可追溯、责任可交接的信息系统。

关注的不是单纯“货在哪里”，而是“为什么这样组织货物流动、当前应该采取什么行动，以及最后带来了什么经营结果”。

## 一、跨境物流不是孤立的运输，而是经营履约

我把跨境物流放在完整的经营链上理解：

市场与经营信号 → 选品与产品开发 → 寻源与供应 → 需求、库存与补货 → 采购与可出运供给 → 出运、分仓与组柜 → 海运与清关 → 提柜、送仓、卸柜与还箱 → 费用、异常与复盘。

这不是要求一次建设所有模块，而是先看清物流决策的前因后果：

- **发什么货**：取决于需求、库存、利润和现金，不只是供应商有什么货。
- **发到哪里**：先服务国家、渠道和仓库的销售与库存需求，再考虑目的港和装柜，不能为了凑柜倒推目的地。
- **何时补、补多少**：海运周期、清关和到仓的不确定性，会影响补货量、安全库存、缺货风险与资金占用。
- **是否必须新增采购**：先比较现有库存、在途、跨仓调拨、再分配和加急方案，采购只是可能的执行方式之一。
- **原来的判断是否成立**：实际费用、交期、销售和退货应回流，修正后续补货、供应和运输策略。

物流的价值不仅是把货运到，还包括在时效、库存、成本、资金和风险之间形成可执行的安排。

## 二、把制造业排程经验迁移到跨境物流资源调度

制造业里的计划、产能、瓶颈、缓冲和成本，同样存在于跨境履约网络。提柜、送仓、卸柜和还箱不是四件互不相关的事，而是一组共享资源、互相影响的任务。

| 制约因素         | 需要权衡的问题                               |
| ---------------- | -------------------------------------------- |
| 码头与免费期     | 什么时间提，晚一天增加多少费用               |
| 车辆与司机       | 是否有可用运力、资质、工时与合适的运输窗口   |
| 仓库月台与班组   | 送到了能不能卸，会不会形成等待和拥堵         |
| 三方堆场         | 增加中转与堆存费用，能否换取整体成本下降     |
| 空箱与还箱期限   | 提得早是否反而增加滞箱风险，卸后能否及时还箱 |
| 已对外承诺的安排 | 重排收益是否抵得过通知、协调、等待和违约成本 |

**只优化一个节点，可能只是把等待和成本转移到另一个节点。** 码头滞港费降低了，如果仓库等待、二次运输和滞箱费上升，不能直接认定为改善。

因此，我对智能排柜的设计思路是：

1. 先满足安全、合规、可提条件和物理资源等硬约束。
2. 再保护免费期、最晚还箱日和已经对外确认的安排。
3. 比较直送仓、等待、经三方堆场中转等候选方案的总成本、时效和风险。
4. 由授权人员确认并发布计划，保留版本、调整原因和受影响任务。
5. 用实际提送卸还结果复盘费用、等待和计划稳定性，而不只看算法分数。

可视化与甘特拖拽只是操作手段，核心是让调度员看清约束、比较方案并作出可解释的安排。

## 三、让财务思维进入业务与系统设计

算账不只是谈运价、压供应商报价或月底汇总费用，而应贯穿事前、事中和事后。

### 事前：看清费用暴露，推动可避免损失的处置

在免费期和资源窗口结束前，比较等待、提柜、调整仓库预约、使用堆场和二次运输的代价。预警必须连接到责任岗位的具体行动，不能只生成一个红色提醒。

### 事中：依据业务事实核验账单

用真实作业事件、合同费率、计费对象和服务期间核验收费，识别重复、缺证、费率不符和期间错误，并保留争议或索赔的证据与窗口。

### 事后：完成分摊与关账，把结果反馈给经营

费用应能追溯核定依据、分摊去向、支付或争议结论，再反馈到单柜、SKU、国家及相关作业的成本分析。

系统设计中必须分清：

- 预计费用不等于实际发生费用，预计避免支出不等于已实现收益。
- 计提、账单、核定和支付是不同阶段，不能互相替代。
- 物流责任关闭不等于财务关账，货柜已还箱也可能仍有账单和争议未结。
- 收入与贡献、成本、现金、库存和风险分别表达；对象、期间、币种或范围不可比时，不强行相加成一个净额。

我的目标是让经营判断有依据、执行有回执、实际结果能回来验证，而不只是生成一份费用报表。

## 四、信息化是重建协作机制，不是把 Excel 搬到网上

企业的难点往往不是缺少数据，而是同一个事实被多个部门重复维护，日期和状态含义不一致，谁应处理、什么算完成也不清楚。

因此，我在业务设计中坚持几个区分：

- **来源表不等于业务模块**：货柜、清关、物流、仓库表是现有工作的观察角度，不能直接成为长期系统边界。
- **一柜一档不等于一张大表**：用户可以从同一入口看全貌，但运输、清关、仓库、费用和证据仍有各自的事实归属。
- **计划、预计、承诺和实际分开**：不能用新的预计覆盖实际，也不能用今天的数据改写当时判断。
- **状态、任务、事件和日期分开**：任务被点击完成，不证明实物已经流转或海关已经放行。
- **发送、接受、执行和核验分开**：邮件发出、伙伴接单、服务完成和结果被采信，不是同一种“完成”。

外部接口同样遵守这一原则：先保存原始观测及来源，再进行对象匹配、语义核验与业务采信；接口返回成功，不能直接变成内部放行或可提结论。

同时，规范不能变成新的等待：**信息流转与动作前置要分离。** 一个字段待核，不应冻结整票；有权下游应及时获得带来源、版本和核验状态的信息，并开展不依赖该缺项的工作。只有真正依赖缺失条件的动作才受到限制，并说明谁补、补什么、怎样恢复。

## 五、建设岗位工作系统，而不是展示系统

我对工作台的要求是让岗位回答六个问题：

> 今天先处理什么、为什么、还缺什么、可以做什么、失败怎么办、完成后交给谁。

Logix 蓝图划分了 23 个岗位工作台，覆盖主业务链及合规、费用、异常等横向职责。这是业务范围设计，不代表 23 台都已上线或完成验收。

每台工作台不是同一张详情页的角色复制，而是同一组可信事实在不同岗位目标下的呈现。设计和建设必须围绕同一个业务步骤，同时对齐：

- **岗位任务**：谁为什么现在处理、要得到什么结果、截止何时、交给谁。
- **数据事实**：所用信息来自哪里、是什么版本、哪些仍然未知。
- **界面操作**：先看到优先事项和缺口，再进行判断、执行并确认结果。
- **技术保障**：状态、事务、幂等、并发、审计和失败恢复能够承接真实动作。
- **权限边界**：明确谁能对什么对象执行什么动作，界面按钮不代替服务端授权。

完成标准也要回到岗位结果：

- 页面存在，不等于岗位可用。
- 接口成功，不等于业务完成。
- 数据落库，不等于责任已经交接。
- 正常路径走通，不等于等待、拒绝、冲突、返工和恢复能处理。
- 技术机制可用，不等于经营损失已经下降。

软件必须承接工作，而不只是承载信息。

## 六、全局设计、分阶段建设，自动化不混淆责任

### 1. 整体业务不断链，建设范围分阶段

从已经出运的真实货柜接管入手，优先解决海运、清关、提送卸还等后半程问题；历史导入与未来上游正常流程使用同一套业务对象和交接关系。

这样不必等企业把所有上游环节改完才开始使用，也避免以后采购、备货和装箱接入时重建下游。后续按真实岗位缺口增加能力，而不是先铺满空页面、接口和平台。

### 2. 自动化辅助判断，不替代正式责任

AI 应嵌入文件抽取、资料比对、法规定位、异常解释和方案建议，不是另建一个脱离业务的聊天窗口。

AI 建议、人员决定、实际执行和最终结果应分别保存。放行、计划发布、风险接受等正式动作由相应规则和授权岗位承担；模型不可用时，核心业务仍须有明确的等待、人工处理或受控降级方式。

### 3. 防止技术建设反客为主

全局规范和技术底座是必要保障，但不能挤占单个岗位连续做到可用的时间。建设节奏应是每次完成一个真实业务步骤，同步交付任务、事实、界面、权限与技术保障，再用实际操作验证。

不能用组件覆盖率、字段数量或技术门禁通过，代替岗位结果和经营价值。

## 能带来的复合能力

这套思路将我的财务、制造现场、供应链、流程与系统经验连在一起：

**财务定义价值与损失 → 现场识别约束 → 流程明确责任与交接 → 系统承接事实和动作 → 实际结果回流验证。**

具体体现在：

1. 跨境供应链端到端业务蓝图设计。
2. 物流资源、时效、风险与总成本协同规划。
3. 岗位流程、责任交接和异常恢复设计。
4. 业务对象、事实口径与信息治理。
5. 分阶段信息化建设与业务验收设计。

Logix 跨境物流项目体现的是上述能力在具体业务领域中的应用；Logix PMS 流程管理系统体现的是把流程建设方法做成通用工具。两者相互支撑，但不是同一个项目。
