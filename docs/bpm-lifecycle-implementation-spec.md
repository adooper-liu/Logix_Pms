## 1. 产品边界与第一批范围

**以客户与战略价值为目标，以长期流程为主对象；项目只交付一轮改善，模块在原记录上作业和核验，以版本、样本和验收引用协同。**

- 八阶段是管理导航，不是状态机；九知识域是能力，不是九步通关。
- `Project.current_stage`保持1–5。执行属于实例，项目结项后流程继续运行、监控、复盘。
- 四种结论只表示选定轮次对照的核验进度，不建四阶段引擎。
- APQC是可选参照，公司流程目录唯一；层级/类型/成熟度分开。
- 保留FastAPI/SQLAlchemy/PostgreSQL、原生ES模块、零构建、后端枚举中文、UTC/纯日期约定和Alembic。

### 1.1 本次综合评审后的实施分期

第一批开发候选只新增 `ProcessImprovementRound` 薄业务表，并给原对象补必要外键/快照/核验字段，完成固定依据、绑定项目/上线版本、原证据引用、验收追溯和既有页面操作。不新增发布包、部署、执行范围、方案、绩效基线、指标修订或验收计划主库。

后续方法直接操作、专业算法、治理/战略与组织采用逐项定义计划，不能因出现在专项设计里就算第一批需求。R3已采纳Flowable方向，届时才按真实需要确定引擎映射、命令/事件和运行设施。独立发布包等结构未被本规格批准；如必要，另交必要性/迁移/验证设计。

R0–R5是改造工作分组，不是执行批次或强制全串行依赖。第一批可跨R0/R2/R5做一条最小证据链；基础异常和验收可以使用现有可靠数据，不以接完Flowable为一切后续工作的前提。

第一批**审定与实施**见 [Brief](bpm-first-batch-brief.md)、[开发计划](bpm-first-batch-dev-plan.md)、[需求追溯表](bpm-requirements-traceability.md)、[审定交接](bpm-review-handoff.md)；**审定通过前不得编码**。R1 相对代码复审见 [bpm-r1-implementability-review.md](bpm-r1-implementability-review.md)。

### 2.1 上下文

- 第一批使用 `process_id/round_id/project_id/model_version_id/tab`，必要窗口字段明确命名；组织范围用原org_unit及批准的业务过滤，不要求不存在的execution_scope_id/release_id/deployment_id。
- `process/project`等旧URL别名兼容，解析后写回规范参数；URL显式选择优先于缓存，换流程清掉不匹配的轮次/版本。
- 未选流程、未知或不可见引用不能回落到另一条流程生成结论。业务不可见统一404，不泄露名称、计数、下载或关联摘要。
- 查询GET不写入层号、阶段或结论；下一步从原证据/权限派生。返回来源恢复原筛选。

### 2.2 作业融合

统一交互为：**本步任务—方法与步骤—直接操作—产出与核验**。保留原专业画布和服务，工具箱保留资源/模板，不要求用户离开当前任务另找工具再重复填数。

阶段/方法映射由 `tool_lifecycle.py` 及拟新增lifecycle只读聚合输出；Tool负责方法基本信息，ToolTemplateVersion负责有效模板，help/catalog负责长说明。一个方法可用于多个活动，定义/模板不复制；前端不维护平行业务映射和计算算法。

能力用独立属性说明：参考说明、可填写、直接办理、可计算、外部核验、已验证集成。保存方法记录不自动写EFFECTIVE；产物核验只证明该版本/用途满足要求，不是通用方法有效性认证。

### 3.1 一个概念一个权威来源

|---|---|

| 标准任务 | ProcessTaskDefinition；不等于运行待办 |
| 模型 | ProcessModelVersion及XML/内容快照；正式引用不可漂移；原版本唯一键不变 |
| 当前发布 | 有真实发布记录的模型版本行；当前publish会替换运行模型，不是仅审批 |
| 项目 | Project/ProjectStep/ProjectGateCondition；current_stage 1–5 |
| 根因/项目门禁 | ProjectEvidenceClaim/GateAttestation；当前均受项目上下文约束 |
| 日常非项目核验 | 原ToolSheet、文件/章程、异常/治理等承载，按计划补责任/期限/核验；没有能力先标缺口，不冒用项目门禁 |
| KPI/样本 | KpiDefinition/KpiRecord及原日志/工时；本轮固定口径/样本，日常保留当时依据 |

### 3.2 薄轮次对照

新增业务实体暂名 `ProcessImprovementRound`，只是同轮固定引用集合，不是新项目/状态机/样本库。

| 字段组 | 内容与约束 | 时点 |
|---|---|---|
| 身份 | id、process_id、project_id（立项前可空）、revision、supersedes_id、原组织/业务范围、创建/确认人和时间 | 准备时可草稿；确认现状与口径后锁定前侧依据 |
| 模型 | asis_model_version_id、tobe_model_version_id（适用时）、released_model_version_id及确认hash | 对应角色分别钉版本；尚未上线允许为空，不能阻断前置分析 |
| 指标口径 | metric_contracts：kpi_id/原version、contract_key/hash、公式/分子分母、单位、粒度、来源/算法、日历/时区、过滤/排除 | 诊断基线确认时固定；KpiDefinition后改不改快照 |
| 样本 | baseline_window/after_window规则与实际锚点、样本范围、数量/质量、sample_refs和来源摘要 | 前后窗口不同但同口径/可比规则；可变数值同时固定当时值/来源，不能只存可覆盖ID |
| 设计/验收约定 | acceptance_snapshot：目标、红线、比较/观察规则、授权审核者及批准时点 | 目标可依据基线提出；比较标准在比较前，正式目标在后侧观察前锁定 |
| 原验收引用 | acceptance_ref、原决定/依据、审核人/时间的只读投影 | 先正式原核验，再追加引用，不从项目CLOSED自动推出达标 |

同轮匹配 `process_id + round_id + project_id(立项后) + contract_key/hash`。基线样本用现状版本，上线后样本用实际上线版本，不能要求改前改后版本ID相等；混合版本需分组或判不可比。范围/项目/指标不属同流程时拒绝。

冻结前可改草稿；冻结后依据不能原位覆盖。绑定项目、选定上线版本、引用验收属于有审计的追加动作；改已固定内容须新修订并保留旧版引用，禁止见到后侧结果再追认新目标。乐观锁用expected_revision，幂等用原IdempotencyRecord能力，具体API在开发计划固定，不另建通用幂等库。

原业务回指：根因已有project_id补round_id；实例保留definition_version/snapshot补直接model_version_id和可选round_id；KpiRecord补口径/模型/窗口/来源及使用角色；变更/培训/验收引用本轮，标准/模板/复制包固定原版本。原 `change_request_id`、`source_model_version_id` 继续使用。

同一业务可被后轮分析显式引用，不复制实例、不改原归属；结束改善后的日常业务不永久贴旧项目。项目删除/归档不能级联抹掉正式版本、样本、裁决；优先停用/受保护引用，隐私/法定删除须单独有权处理及审计。

### 3.3 已发布身份与草稿冻结

当前实例的definition_version是整数，需连process_id回查模型行；不是模型主键。仅明确匹配并能证明真实发布时才回填，历史SUPERSEDED但有发布事实可作历史已发布身份，不能只检查当前status=PUBLISHED。匹配不明留snapshot并标待核实，不能用最新版本猜测。

As-Is/To-Be角色不等于发布状态。前置分析可引用在原ProcessModelVersion中固定内容的非运行版本，不能为了冻结现状而覆盖运行指针。当前草稿可原地更新，正式引用之前须在原版本机制内实现不可变保存；具体冻结动作/枚举按开发计划明确，本稿不虚构它已存在。

复杂XML存在不等于无损，当前结构子集保留/校验限制要明确；不能丢扩展后重建并称原版本相同。当前发布行与未来Flowable deployment ID分开，R3才建立映射。

### 3.4 四种核验结论，不是另一套阶段

| 结论 | 必须成立 | 不能冒充 |
|---|---|---|
| 资料就绪 | 本轮适用的目标/边界/现状/责任/口径及证据被确认 | 工具填完、记录计数够 |
| 上线就绪 | 本轮已固定真实发布的模型版本，必要上线条件通过；R3后另核引擎就绪 | 仅有草稿、设计接收或BPMN无错误 |
| 运行有效 | 实际范围内运行、数据质量、人员操作和异常处理满足批准要求 | 隔离UAT、仅有一条机器人运行或HTTP200 |
| 改善达标 | 与运行判定使用同一冻结口径、可比前后样本和预先约定，有权独立验收 | 项目结项、单次绿灯、估算收益或未经验证因果 |

每项返回conclusion_key、核验状态/标签、原decision_ref、缺项、条件核验数/待审核、下一步和评估时间；整体可说“本轮2/4项结论已确认”。不保存独立current_stage，不提供advance。缺引用随时点显示待补，不能要求创建对照时四项齐全。

有改善目标的项目不能把改善达标设不适用；可被判未达标/停止，项目仍可按合法结案规则结束。无改善项目的日常运营直接展示运行/复盘，不造“改善达标不适用”或强迫立项。可选方法/条件裁剪不豁免目标。

“运行有效”依原批准的运行/控制要求判定，“改善达标”依改善目标判定，可分别得出结论；运行不稳定或质量红线未满足时，不能用均值改善冲过验收。

### 3.5 用途与前后准入

模型保存、沟通/分析接收、设计交付、当前运行发布、实际运行验证、改善验收、战略支持分别核验。标准、企业规范、业务真实性、算法/引擎能力分域，任何一个检查不能包办其余。

当前publish将模型版本应用到运行表并更新发布指针；现在没有独立“批准但未部署”的模型状态。第一批沿用这个事实，前置UAT/人员/恢复证据与上线后运行样本分开。MANUAL/EXTERNAL业务也可持续治理，不强迫它们部署到PMS；但本轮要确认“上线就绪”仍须固定已发布模型作为受控业务基准，并记录真实执行位置，不能冒称该模型已在外部引擎执行。R3会出现远程部署和启用，届时设计明确新状态，不改写旧发布含义。

持续硬准入失效时应阻止相应新操作，但不能自动取消所有在途；复核/恢复在原发布/执行权限入口处理。非准入复盘到期提示和升级。R3签名命令、入队/执行二次核验与恢复接口由接入计划设计，不在第一批暴露 `/releases` 之类不存在接口。

### 3.6 权限、审计、历史

复用原deps/ownership/org_access，检查系统准入、对象范围、业务授权和专业资格。ADMIN不天然是业务验收者；RACI的A不自动授全部系统权；正式自验/越权拒绝。低风险普通动作按批准规则裁剪，不能每项都机械两人签。

全部列表/聚合/导出/下载/关联/后台动作应用同范围，敏感不可见返回404。来源/核验/签收追加留历史；组织/人员变化复核当前权限与责任，不重写过去。GET不推进业务。结构化错误兼容原detail字符串，前端不匹配中文判断业务；未知、失败、结果待确认和空数据分别展示。

## 4. R0–R5工作项：位置、改法、验收

下列20项是总体工作分解。只有标为第一批的最小部分进入下一份开发计划，不能自动执行全部；专项是作业设计，不是表结构指令。

### R0-01 既有导航与用途说明

- 位置：start/cbok、state、help及原模块标题。
- 后端/前端：统一只读导航/方法目录，保留第2节路由；建模/设计拟增加用途参数，在同一画布选择现状/方案引用，当前尚未实现。
- 文案/验收：说“当前任务/下一步/产物”，不说进入第N阶段；治理单列不编号。测试原URL、未选流程、跨流程上下文、无项目访问。
- 分期：第一批只统一入口和本轮上下文；完整方法工作区后续。

### R0-02 流程卡本轮对照

- 位置：process_card，项目/分析页链接同一round。
- 增量：原聚合增加round列表/选择、固定身份摘要、缺项、原证据入口和核验投影。GET不造轮次、不选另一流程/轮次猜结果。
- 验收：历史/当前对照区分、项目结项后原记录仍可查，无数据不报零收益，权限覆盖计数；不产生影子资产。
- 分期：第一批。

### R1-01 分类和排序依据

- 位置：map原编辑/筛选、流程卡；原ProcessArch/schema/API按需扩类型/依据。
- 规则：三类流程不是层级；不按PCF或名称猜历史类型。参考分保留原算法含义，风险/价值/资源排序有批准依据，不承诺核心流程永远第一。
- 验收：继承/例外/未知、筛选保留祖先、越权/并发、原分数不冒称投资结论。
- 分期：后续架构/组合工作，不前置第一批。

### R1-02 横向交接

- 位置：map/流程卡和原SIPOC/RACI/标准记录。
- 增量：先用原结构化模板/版本保存提供者、接收者、交付/质量/时间/例外和双方确认，固定原引用；不先新增ProcessHandoff关系主表。
- 验收：返工关系可成环、不等于目录树；共用标准不复制；实际SLA与其测量证据分开。后续若需可查询关系表，独立论证。

### R1-03 章程、任命与资源

- 位置：原ProcessCharter、治理角色/授权、版本化文件及模板。
- 增量：缺责任/期限/接受/授权/审核字段补原对象；原章程仍是流程范围与Sponsor，不把它改造成每项目一份的平行项目引擎。任命/资源/批准文件固定原版本，来源不明不自动批准。
- 验收：有姓名不等于有授权/资源，变岗/到期/代理可复核，历史保留；只引用原关系，不再独立编辑Owner副本。

### R1-04 十层适用性核对

- 位置：pilot、process_evidence、原条件/文件/模板和签收。
- 增量：区分上线前/运行后、必需/可选/不适用、证据范围/有效性，原路径可加round_id/model_version_id等必要引用；不先建PilotCondition或新条件状态主表。
- 规则：RPA/技术登记/案例不是所有流程强制条件；首次上线不强造历史变更或改善项目。原advance若保留，不能绕过原证据核验，也不成为八阶段推进接口。
- 验收：无RPA可核验、错轮/错版本/过期不通过，GET不更新层号；可选条件裁剪不豁免改善目标。
- 分期：第一批只接本轮引用/缺项；全套政策裁剪后续。

### R1-05 五因素保障核验视图

20项是原章程、RACI、标准/方法、绩效、培训和复盘记录的核验要求，不预生成PilotTask/ProjectStep或平行保障任务；现有任务仅引用。缺来源时指向原模块，不能为显示勾选创造泛化任务。

| 代码/因素 | 核验的真实动作 | 主要原来源 | 责任/时点/验收要求 |

### R2-01 薄轮次对照及原引用

- 位置：拟新增models/schemas/services/api的improvement_round职责模块，原模型/项目/流程卡。
- 接口候选：`/processes/{id}/improvement-rounds` 查询/创建，round上的bind-project、bind-published-version、acceptance-reference；具体方法、schema、签名和测试在开发计划锁定。
- 验收：第3节的逐时点冻结、版本/项目冲突、幂等/并发修订、历史未核实、无项目日常运营、结项保护、跨组织授权。
- 分期：第一批核心。

### R2-02 显式指标取数与样本依据

- 位置：原KPI/schema/service/monitor/inbound；同轮定义快照在metric_contracts，不新增指标修订库或独立基线库。
- 规则：测量语义明确到实例/活动/工时/外部值及来源、聚合/窗口/质量。单位只换算，不决定来源；不得向所有时长指标回写端到端周期。保留原值修订和来源，不覆盖正式验收样本。
- 日常无round的数据仍可用，但要记录当时口径/窗口；正式同轮样本带round/contract/hash/模型/角色，唯一性和NULL范围分别定义，不能凭一个可空复合键宣称所有去重完成。
- 验收：同单位不同指标、缺数/零/零分母、小样本/过期/混合群组、阈值/方向/时区、补数/冲突/重放；不把比例均值当合法汇总。
- 分期：第一批固定引用/快照和禁止篡改；完整计算规则/质量处理单列后续，错误自动取数可先独立修。

### R2-03 分析与方案交付

- 位置：monitor、designer、原ToolSheet/项目步骤/证据/变更。
- 规则：分析用问题→事实→选路→原因验证→接收；设计用依据→方案决定→验证/控制→比较→接收。方案备选先存原方法/项目产物，不新建ProjectSolutionOption；BPR原则统一版本而不平行新工具，ECRS作为独立适用方法引用，不混称BPR原则。
- 估算/路径枚举/专业仿真/实测标清能力与限制；未验证并行/资源争用不报精确效益；接收不自动发布/达标。
- 分期/验收：按专项后续实现，第一批只固定原产物引用。无项目的ToolSheet核验须扩原字段，不调用项目专用根因门。

## 5. R3：已采纳的引擎方向，待接入设计

### R3-01 支持范围与服务边界

- Flowable独立Java服务与PMS受控适配器，兼容版本/许可证/镜像按技术验证固定；不改原前端零构建。
- PMS管业务治理/权限，Flowable管接管实例运行；不各算下一步。模型的标准合法性与引擎支持范围分开，脚本/任意类/URL不默认开放。
- 候选验证：顺序/排他、并行汇合/会签、子流程/调用、消息/定时器和受控服务任务；只把实测通过项宣称支持，剩余明确未验证。复杂场景可分批，不把本表当已经支持的产品清单。

### R3-02 模型版本到引擎部署映射

- 继续以原模型版本为业务发布身份，追加不可变执行配置快照及外部definition/deployment映射，不能把业务模型行主键当Flowable ID。
- 原复杂XML保存/校验/差异需无损，不能降级重建；条件受控编译、概率仅估算、子流程定义绑定策略明确。
- 远程审批/部署/启用是否拆操作及API在R3计划确定；当前publish的运行效果不重命名为“仅批准”。不在本规格先指令创建ProcessRelease/独立审批状态机。
- 验收：失败/结果未知、旧版仍可运行、并发启用/回退、在途钉版本、配置和子流程不漂移。

### R3-03 运行任务与业务权限

- 扩原实例/任务的engine身份和直接模型映射，按能力增加活跃活动/等待/子流程投影；并行不再受单OPEN约束，旧实例保留其原不变量。
- 表单/分派/变量/授权引用对应快照；并行局部变量冲突、模型允许动作和服务账号权限明确；不得以候选字符串或模型输出跳过业务授权。
- 异步界面兼容已接收/处理中/待确认/完成，不提前移除任务或报业务完成。

### R3-04 命令、事件和对账

- 必要的持久command/inbox/outbox/历史设施在接入计划逐项设计，不受第一批“一张业务表”限制，也不提前建空表。
- 命令key+hash去重、超时确认原操作、事件身份/版本/去重/缺口/重放、投影与本地副作用一致、定期对账、失败可处理；不承诺跨系统exactly-once。
- bridge若需与引擎同事务保存结果，须实测其事务边界；顺序保证按聚合需求定义，不能先验要求全局事件排序。
- 自动任务/消息/定时器也产生同样事件，不能只通知一个open_task；原升级扫描与引擎SLA明确分工，不重复改派。

### R3-05 迁移与恢复

- 新实例按范围受控切换，旧在途按原语义结束；不静默回退引擎，不永久维护两套新实例推进。
- PMS迁移走Alembic，Flowable及其bridge设施按对应Java版本迁移；同一表不能两个迁移器管。
- 备份恢复覆盖PMS、引擎、附件、密钥和事件游标及外部业务对账；mock/容器启动/备份脚本打印通过均不能替代恢复和真实集成验收。
- 原API/整数ID尽可能兼容，退役旧推进器但保留必要历史读取，不破坏审计和引用。

## 6. R4：运行偏差与决策闭合

### R4-01 异常和响应

原ExceptionEvent/治理/项目步骤负责处置。质量故障与业务偏差分开，保留当次口径/样本/窗口、持续/恢复/复发、责任/期限/授权决定和验证。沿当前人工确认候选策略，不默认每个红黄创建项目；重复/并发去重、复发不永久忽略、行动后验证有证据。

第一批可先引用可靠的现有异常/记录，不依赖Flowable。后续规则化告警另有契约；关闭原异常入口加风险相称的核验，不新增行动任务库。

### R4-02 分析与可比性

前后比较必须用本轮固定口径/范围/窗口/模型角色，缺条件返回不可比。实际日志不齐或并发因果不明时显示限制，不按完成先后推路径/负等待。

基础串行/样本对照可先用现有数据；依赖并行活动/事件的增强分析在R3相应能力之后交付。原designer图测算、路径模拟和新方法不得各自维护互相冲突的返工/成本定义。

## 7. R5：核验、采用、复盘和推广

### R5-01 本轮验收与结项

验收引用轮次对照固定依据、前后样本与原有权核验。Project的verification/benefit文字不是单独达标证明；原GateAttestation目前项目绑定且stage为1–5，需补round_id/证据快照及明确验收用途/结论，不能把普通PASS直接映射成改善达标。

不另建ProjectOutcomeReview库。正式结果保存在原验收记录及项目产物，对照只投影其结果；一项核验若原对象无法表达，先在原接口/字段明确扩展而非虚构已有支持。停止/取消可结案但不标达标；通用PATCH不能绕过核验。项目关闭后当前流程继续运营。

### R5-02 人员采用和持续控制

原ProcessTrainingRecord保留到场事实，按用途补模型版本/round/验证、责任和期限；不能把到场或一句培训说明视作会操作。采用率必须有可核分母，缺总体业务范围就标未核实。

控制计划/周期复盘先使用原有效标准/模板、方法记录、绩效/治理处置及版本引用，补责任/期限/核验字段，不新增ProcessControlPlan/ProcessReviewRecord库或新任务中心。当前没有专用复盘对象，文档明确这是拟扩原载体，不写成已有接口。多人/代理/组织调整按权限保护个人资料，HR承接不自建薪酬。

### R5-03 固化与复制

原ReplicationPack/AssetBaseline/文件模板版本保存适用条件、精确模型/文件版本与hash、同轮验收、失败经验和来源；原包修订及接收方决定优先扩原结构化记录，不先建ReplicationDecision表。

接受推广只形成已批准范围的本地准备动作，不能直接覆盖当地有效版本或自动标上线/项目完成；已有目标项目/标准引用原记录。拒绝有理由/授权/时间；源资产更新不漂移历史包。复制包可含多业务范围时需显式逐项来源，不能一个source_project_id证明所有收益。
