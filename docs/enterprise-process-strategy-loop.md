## 1. 产品原则：从战略开始，回到战略是否得到有效支持

**企业级管理不是汇总流程数和项目进度，而是持续验证：客户/经营目标是否被正确解码，关键流程是否承担了必要结果，组合投入是否改善这些结果，原战略假设是否仍成立。**

主链：战略/客户结果 → 关键流程 → 流程目标/CSF → KPI → 团队/岗位及适用的个人责任目标 → 差距与约束 → 改善组合 → 运行/采用/收益证据 → 战略复盘。

不是每条箭头都天然成立，也不是所有结果变化都由流程项目造成。必须解释贡献机制、外部因素、相互依赖、数据质量和不确定性；战略复盘可继续、调整、停止投入，或修订目标/假设，不能只接受“项目都完成所以战略达成”。

流程现状先在业务里发生，战略对齐赋予管理意义；项目只交付其中一轮改善。项目结项后有效流程和企业治理继续，下一轮依据新问题选择。

## 3. 先统一三个口径

### 3.1 层级、类型和端到端关系分开

讲义把L1写成运营/支持/管理，L4写子流程；项目当前L1价值链、L2类别、L3流程、L4活动，L5任务在独立实体；APQC又有自身分类/层级。它们不能不经解释直接替换。

推荐批准公司的层级命名、定义及与PCF的映射，先保持现有数据身份/约束；三类流程用用途分类，不等于任何公司必须有三个L1。端到端价值流可以跨多个目录节点和业务系统，不能只靠一条父子链或“L3”标签证明完整。

### 3.2 成熟度是有证据的能力判断

讲义的五级可作教学参考；缺Owner、仓库或挖掘只形成调查线索，不足以自动定企业等级。成熟企业可能不用某项技术；安装挖掘/AI也不自动升L5。

当前0–5是维度评分尺度，须与企业1–5阶段模型明确映射/量表版本，不能简单加一或平均。企业评估声明组织/流程范围、样本覆盖、标准、证据、时间和审核者；未知/未评估不等于0或最低级。分维度缺口先可用，形成企业整体等级时另需批准聚合/必要条件，不能让高分维度抵消关键治理短板。

### 3.3 个人目标不是一刀切下摊

战略→流程→KPI到团队/岗位/个人的承接须保留责任、影响能力、共同成果和职能义务。端到端周期不宜平均分摊给每个员工；不可控等待、业务复杂度、质量、协作及客户结果要共同考虑。具体个人权重/考核/申诉由组织与HR确认，不默认建设薪酬系统，也不因“最后一公里”自动监控个人行为。

## 4. 战略流程地图：关系必须带解释、证据和责任

首期用原strategy页面的层级/承接表增强，不新增图形编辑器；“地图”指关系表达，不要求新建可视化。

每条承接至少能看见：

| 关系 | 必须说明 | 核验 |
|---|---|---|
| 战略→关键流程 | 客户/经营结果、为什么该流程关键、范围/依赖、责任 | 不由名称相似或PCF类别自动推定贡献 |
| 关键流程→目标/CSF | 对结果承担什么、基线/目标/期限、成功机制与假设 | 可干预且不丢质量/风险/客户约束 |
| 流程目标→KPI | 指标用途、公式/来源/范围、口径/时效/责任和行动规则 | 数据可采、可复算，代理指标盲区明确 |
| KPI→共同责任 | 团队/岗位/人员可以影响什么，如何协同、评价和申诉 | 不把流程Owner、任务处理人与个人考核身份混同 |
| 差距→项目组合 | 哪些差距值得改，选什么/不选什么、依赖/资源/风险 | 不用“红灯”直接替代组合决策，不把所有差距立成项目 |
| 运行/改善→战略 | 哪个目标变化、有何贡献/反证，假设是否仍成立 | 正式改善引用同轮模型/样本/口径/验收，经营结果与估算分开 |

通过率、及时率等目标必须解释分母、承诺/有效时间和样本结构；案例中的90%、4h、98%只作练习参数，不能灌成全组织政策。

## 5. 企业级小闭环

E0–E7是管理作业指引，不加新阶段字段。

| 工作 | 具体动作 | 交付与反馈 |
|---|---|---|
| E0 明确战略结果 | 收集客户/经营方向、外部约束和原假设，明确范围/期间/责任 | 有依据的目标，记录未知和风险，不用愿景短句代替可管理结果 |
| E1 选择参照并确认家底 | 按需选APQC/行业框架；核对实际业务范围、层级/类型、Owner及横向关系 | 唯一公司目录、采用/裁剪理由、覆盖缺口，不把生成草稿当业务确认 |
| E2 解码并确认承接 | 识别关键流程、目标/CSF/KPI和共同责任，检查未承接和重复承担 | 原目标/关系/定义的固定引用及Owner/资源方确认 |
| E3 评估差距与能力 | 核实际绩效、客户影响、风险、成熟度/实施能力与依赖 | 有来源/日期的差距与约束清单；缺数据先补数据，不任意打分 |
| E4 选择组合与资源 | 先硬约束，再比较价值/难度/成本/风险、前置依赖与资源容量 | 选择/延后/不改/停止/采证理由、Sponsor/Owner、预算及复核约定 |
| E5 交付并观察 | 原项目五阶段实施，运行系统执行，部门/CoE支持采用 | 模型/规则/标准/培训/真实运行及同轮对照，不以项目进度当收益 |
| E6 战略支持复核 | 核客户/经营结果、流程贡献、组合成本/副作用和假设变化 | 继续/调资源/改组合/改流程目标/重审战略假设的有权决定 |
| E7 固化和再解码 | 保留有效资产、控制与复盘，推广按适用性，更新下一期间重点 | 项目结束、流程持续；新目标/约束再启动分析或新一轮，不重复建树 |

E6不是最后开一次总结会：可以由周期/阈值/外部变化触发。战略/流程目标改变应复核受影响的指标、授权和组合；已批准历史/验收不回写，现行计划以明确修订生效。

## 6. 组合管理：不只是排分数

保留现有改善参考分与热度作为线索，不伪装成完整投资排序。组合决策至少看：战略/客户价值、痛点/实际损失、机会证据、实施难度、数据/技能/组织准备、投入与运行成本、风险、依赖、资源冲突、时机和收益不确定性。

- 安全、法律、重大持续运营义务先按硬约束处理，不总选“高价值低难度”。某低分项目可能是另一个关键项目的前置基础。
- 估算ROI声明货币、期间、一次/持续成本、转移/机会成本、风险假设及收益实现者；同一收益多项目贡献避免重复计算。
- 个人/部门评分可能冲突，保留提出者、依据、日期和有权裁决；未知不能填一个3分当中等难度。
- 资源不是只有预算，还含Owner/业务/IT/数据/变革/CoE的能力和时间。项目过多会争抢同一人，选择须有容量与在制约束。
- 组合状态、原项目阶段、运行情况和结果分别呈现。延后、停止、试点、补证都是合法决定；不能为好看持续保留无价值在办项目。

首期在原projects的多维筛选/项目卡和strategy承接视图补依据、依赖和资源确认引用，不先建独立PPM系统或另算一套收益。

## 7. APQC、战略与实际业务的关系

APQC帮助分类、对标和识别遗漏，不直接决定公司客户价值、真实顺序或治理授权。选择参照框架/版本、采用哪些项、合并/本地化/不适用及原因都应可解释；企业特有流程可以存在，不为满足分类删真实业务。

当前严格项目门禁要求APQC映射，需区分“该组织批准采用APQC后应检查映射”与“任何项目无APQC就不准改善”。可选参照的产品原则下，按组织政策核验已采用参照或批准的本地架构依据；不能在界面称可选、后端却永远强制。变更策略要兼容既有已启用门禁，保留历史，不静默取消约束。

PCF覆盖、公司工作覆盖、Owner/资产覆盖、战略承接覆盖和实际绩效，是不同指标。PCF映射100%不等于业务无遗漏；目标有一个链接不等于已落地；岗位有Owner也不等于授权资源足够。

## 8. 端到端治理与现实约束

端到端SLA应定义客户可接受交付、交接输入/输出、时间/日历、质量、责任、例外/升级与证据。各部门SLA相加不自动等于客户历时；共享资源、在制/并发、重复移交和外部伙伴时间需正确处理。

联合KPI引用原指标和同一口径，团队共同承担可影响结果，避免上游“快速转单”导致下游积压。跨系统/组织协同明确权威数据与业务键、权限和对账；一个平台不必替代所有业务系统，也不复制流程树解决边界问题。

治理会议/委员会/CoE沿原角色、授权、发现和项目步骤运作，记录真实决定/行动核验，非平行任务库。重大冲突按组织治理专项解决；目标架构须有现实过渡，不把理想图直接当现实。

## 9. 九模块的小闭环及交接总表

九个模块是知识与能力域，不是九个必须顺序通关的阶段。每个小闭环都要有明确输入、真实作业、可接受产出和反馈条件。

| 模块 | 自身小闭环 | 必交给谁的什么依据 | 什么会触发返回/修订 |
|---|---|---|---|
| 1 流程思维/BPM | 明确客户结果→边界/责任→共同理解→用实际交付检验理解 | 给架构/建模的流程定义、客户与价值标准 | 客户需求、范围/价值假设变化，局部优化损害整体 |
| 2 建模 | 目的/事实→标准表达→分层校验/评审→版本入库→使用反馈 | 给分析/设计/执行的可解释且用途适合模型版本 | 语义错误、实际偏离、异常遗漏、使用者不能理解或实施 |
| 3 分析 | 问题→事实/基线→按问题选路→原因验证→交付接收 | 给设计的根因/损失/约束、同轮样本口径和未决项 | 反证、样本不足/偏差、事实或口径变化 |
| 4 设计 | 承接依据→备选/原则模式→验证/控制→比较→接收 | 给实施的方案版本、规则/控制/依赖、验证与观察约定 | 前提不成立、控制失败、负向客户影响或实施不可行 |
| 5 绩效 | 价值/CSF→可信取数→解释偏差→决定→行动→效果核验 | 给分析/Owner/战略的偏差、响应和真实结果证据 | 数据故障、措施无效、绿灯与客户结果冲突 |
| 6 转型 | 路径选择→实践组合→组织采用/切换→结果→固化再选择 | 给持续流程的有效版本/标准/人员能力/复盘和复制条件 | 抗拒揭示真实风险、能力不足、试点失败、约束/目标变化 |
| 7 技术 | 问题/契约→映射与验证→受控接入→运行对账→升级/退出 | 给各模块的可信数据、能力结果、可移交资产与恢复依据 | 语义/权限/可靠性失败、技术不再合适、成本风险超限 |
| 8 组织文化 | 目标职责→核当前事实→差距/冲突→协调决定→落实核验 | 给流程/组合的授权、资源、专业支持和解决冲突机制 | 责任权力不匹配、代理失效、决定不落实或组织改变 |
| 9 企业级管理 | 战略解码→家底/差距→组合投入→结果/贡献→战略复盘 | 给各流程/组织的新目标、优先级、资源和约束；接收其运行与验收反馈 | 战略支持未被证明、客户/经营结果偏离或外部假设改变 |

多轮驱动是这些循环以业务事件和交付依据连接，而不是让用户重复填九套表：一次客户投诉可以触发绩效/分析；发现系统性责任冲突交组织治理；设计需新能力交技术；跨流程资源争议回企业组合；真实运行结果最终回战略。不同循环有不同周期，不能强制等所有模块完成一轮才响应风险。

## 10. 同一证据跨层使用，但不能任意累加

流程层：原模型/实例/标准/KPI及常规复盘持续存在。改善轮次：薄轮次对照固定 process_id/project_id/现状方案上线模型/冻结口径/前后窗口/原验收引用。企业层：引用战略期间、承接关系、组合决定及这些原结果，不复制第三份证据库。

战略支持须分开呈现：

1. **有关联**：已识别贡献流程和责任；
2. **可管理**：目标、口径/取数和响应可用；
3. **有执行**：资源和措施真实交付，流程被采用；
4. **有结果证据**：同口径显示客户/经营结果、贡献及限制；
5. **有决策反馈**：有权方据此调整或维持目标/组合。

这只是解释证据充足程度，不增加战略状态机。多个流程贡献同一目标不强求收益加总等于战略结果；区分贡献、相关和因果。跨期间、群组、口径和货币聚合须有批准规则，缺信息显示未证实而非0%或100%。

## 11. 界面与后端如何接续

保留开始使用及生命周期现有路由：战略→strategy、架构→pcf、建模/设计→designer、分析→monitor、执行→execution、监控→dashboard、变革→projects；治理authorization贯穿，不作为第九阶段。

| 原位置 | 推荐增量 | 权威记录与边界 |
|---|---|---|
| strategy | 战略流程地图关系表：目标/关键流程/流程目标-CSF/KPI/责任/差距/结果与待决定 | 扩原目标/承接/方法模板引用，不用新树或新KPI库；区分已承接与已有效支持 |
| pcf→map | 参照选择/裁剪说明、真实目录/业务覆盖、缺口和责任 | 原框架/映射与公司目录分开；L1–L5术语明确，不偷偷迁移数据 |
| projects | 组合选择依据、难度/依赖/资源与推迟/停止决定；打开仍是五阶段 | 原Project/步骤/预算/证据，正式结果引用薄对照；不把排序分当准入结论 |
| dashboard | 战略支持的证据/风险/待决概览，可下钻到原样本与行动 | 汇总不是重新计算各模块的另一套结论；组织/对象权限覆盖计数/导出 |
| process_card | 本流程承接目标、当前有效版本、相关轮次、共同绩效/交接及复盘 | 日常运行无项目照常可用，项目结项不删除有效资产 |
| maturity/治理原入口 | 量表/范围/证据/到期/差距、能力改进与复核 | 不机械平均成企业等级、不以安装工具数升级 |
| orgs/authorization | 对组合资源/跨流程冲突的授权及原决定 | 委员会和Owner权限明确，20保障只引用原记录 |
| 帮助/实训 | 九能力闭环、八生命周期导航、五项目阶段及本轮四结论的区别 | 统一术语/例子，不复制多套长期映射 |

首批可用对照表和原字段引用，不要求新图表、流程组合引擎或新的企业治理总表。只在原记录缺责任、期限、来源/核验时增量扩字段；后续新实体必须单独说明必要性并获准。

## 12. 优先顺序及验收

先选一个明确战略/客户结果，完成一条“目标—关键流程—CSF/KPI—差距—组合决定—交付—真实结果—战略复盘”的端到端样例，贯通九模块需要的交接，不一开始铺满全企业所有类别。

随后检查未承接目标、重复收益、资源冲突、无Owner/授权、数据缺口及依赖；再扩大流程覆盖和能力评估。不是用更多流程/项目/工具填满看板。

后续验收至少包括：APQC可选政策与后端门禁一致；讲义/公司/PCF层级区分；无映射/无样本不冒称全覆盖/高成熟；战略关联与成果分离；项目组合难度/资源/前置和风险有依据；跨项目收益不重复；个人责任承接需适用授权；指标/样本/模型版本一致；项目关闭后运营持续；结果反证可改变组合/目标且不覆盖历史；全部聚合/导出可见范围受控。

原测试扩展：test_strategy.py、test_pcf_draft.py、test_benchmark.py、test_dashboard_home.py、test_maturity.py、test_workflow_workbench.py、test_governance_audit.py及前端自检；schema增量走Alembic。当前仅检查文档，不声称这些功能/测试已实现或通过。

**企业级治理的闭环成立，不是战略“分解过”，而是分解依据明确、责任资源可兑现、行动真实发生、客户与经营结果有证据、有权方据此持续修正管理。九个模块各自闭合、交接相通，才形成多轮驱动的运营方式。**
