# APQC PCF 中文参考译文

本文说明 APQC PCF 对标数据的中文化约定：译文放在哪、怎么合并、
界面怎么标注、以及**哪些事情不能做**。

## 一、为什么是「参考译文」而不是「官方译名」

APQC 只发布了 L1–L3 的中文整理版（`APQC_PCF_v80_跨行业流程分类框架_中文整理版.xlsx`），
**L4 活动、L5 任务、官方定义、全部指标都没有官方中文版**。

所以本系统里的中文分成两类，界面上必须区分：

| 来源标记 | 含义 | 覆盖范围 |
|---|---|---|
| `APQC_CN` | 来自 APQC 中文整理版 | L1–L3 分类名（449 个） |
| `REFERENCE` | 本系统自建参考译文 | L4/L5 名称、官方定义、指标全部字段 |

**硬性约束**：译文一律标「参考译文（非 APQC 官方）」，官方英文原文始终保留并排展示。
任何对外引用、指标口径确认、客户交付材料，**必须使用英文原文**，
不得把参考译文当成 APQC 官方口径。

## 二、数据流

```text
APQC 官方 Excel（3 个变体 + 中文整理版）
        │  scripts/import_pcf.py（只读源文件，不手工编辑）
        ▼
app/seed/data/pcf_v80.json        ← 官方数据（4.4 MB），只由脚本生成
        │
        │  app/seed/pcf_data.py 在运行时合并（不写回官方 JSON）
        ▼
app/seed/data/pcf_v80_zh.json     ← 中文覆盖层，人工维护
app/seed/data/pcf_zh_glossary.json← 术语表，统一译法的唯一权威
        │
        ▼
app/seed/runner.py → 数据库（benchmark_category / benchmark_metric）
        │
        ▼
API（app/schemas/benchmark.py）→ 前端 web/js/views/pcf.js
```

**为什么覆盖层独立于官方 JSON**：

- 官方 Excel 升级重导时，`pcf_v80.json` 会被整体覆盖；译文若在其中就会**全部丢失**。
  独立文件重导不受影响。
- 译文是**人工审校资产**，需要单独 review、单独版本管理，和机器生成的官方数据
  混在一个 4.4 MB 的文件里没法评审。
- 官方数据保持「只由脚本生成、不手工编辑」的纪律。

## 三、覆盖层文件结构

`app/seed/data/pcf_v80_zh.json`：

```jsonc
{
  "schema_version": 1,
  "provenance": {
    "kind": "reference_translation",
    "label": "参考译文（非 APQC 官方）",
    "note": "..."          // 界面按这段话标注来源
  },
  "metric_categories": { "Cycle Time": "周期时间", ... },   // 枚举级，全局映射
  "units": { "percent": "百分比", ... },                    // 枚举级，全局映射
  "categories": {
    "19945": { "name_zh": "识别竞争对手", "description_zh": "..." }
  },
  "metrics": {
    "10002|101337": { "name_zh": "...", "formula_zh": "..." }
  }
}
```

- 分类键是 **PCF ID**（`external_id`），不是 Hierarchy ID——后者会随行业元素插入而漂移。
- 指标键是 **`external_id|metric_id`**。
- `units` / `metric_categories` 是**全局映射表**：132 个单位、5 个指标类别各写一次，
  合并时批量套用到 3453 条指标上，不必逐条重复。

## 四、术语表

`app/seed/data/pcf_zh_glossary.json` 是**统一译法的唯一权威**：

- `verbs`：动作词（Identify→识别、Evaluate→评估、Define→定义…）
- `nouns`：名词（customers→客户、baseline→基线…）
- `metrics`：指标类别
- `units`：度量单位
- `verb_exceptions`：动词的语义分支（Develop→制定/开发/开发和管理…）
- `literal_fixes`：**同义异译的字面量收敛表**（`日历天`→`自然日`、`订单到收款`→`订单到现金`）。
  由 `pcf_zh.py normalize` 批量应用，代码里不私造映射——术语表是唯一权威。

规则：**英文里出现术语表已收录的词，必须用术语表里的中文**，不得自创同义译法。
这是 10,000+ 条译文能保持一致的唯一手段，也是并行翻译能收敛的原因。

新增术语时**先改术语表，再写译文**——顺序反了就会出现同一术语两种译法。

> `literal_fixes` 段是为「已经落库的译文」准备的：并行翻译期间同一术语会分裂成两种译法
> （实测 calendar day 分成「日历天」12 条 +「自然日」12 条），改术语表后用这张表一次性收敛。
> 改术语表的 `nouns` 段只能挡住**新写**的译文，挡不住已落库的。

### 动词口径是从官方数据反查出来的，不是猜的

APQC 中文整理版给了 449 条 L1–L3 官方译名。把这些译名的首词按英文动词归类，
就得到一份**有统计支撑**的动词表：

| 英文动词 | 官方译名 | 样本 |
| --- | --- | --- |
| Manage | 管理 | 112 / 113 |
| Develop | 制定（开发 22） | 44 / 69 |
| Define | 定义 | 26 / 26 |
| Establish | 建立（确立 2） | 13 / 17 |
| Perform | 执行（开展 3） | 20 / 28 |
| Evaluate | 评估 | 8 / 8 |
| Control | 管控 | 4 / 4 |

`Develop` 有两套官方口径，**必须按宾语判断，不能只看动词**：

- `Develop and manage / maintain X` → 开发和管理X（官方 22 条里 17 条属此类）
- `Develop 战略/计划/政策/愿景/使命/目标/举措/需求/预算` → 制定
- `Develop 能力/产品/服务/模型/体系` → 开发

术语表的 `verb_exceptions` 段记录的就是这批分支规则。
反过来，官方译名里的**自造译法一律不进术语表**——例如官方把 `Control` 译作「管控」，
就必须跟着用「管控」，不能写「控制」。

### 标点口径也是实测出来的

官方 1347 条中文译名里，顿号「、」出现 60 次，其余标点（。，；：！？（）「」）出现 **0 次**。于是：

- **活动名 / 指标名**：只用顿号分隔并列项，其他标点一律不用；限定说明用全角括号；
- **定义 / 指标口径**：是中文正文，正常使用中文标点，句末句号。

这条区分很重要——把「名称标签」和「定义正文」用同一套标点规则去卡，会误报几百条。

### 公式里的逗号统一成全角

口径是中文正文，所以逗号用全角「，」。实测发现同一批 `IF(...=0,0,...)` 的公式有三种写法并存：
半角全角混用（`=0,0，`）、全半角全用（`=0，0，`）、以及把 `0,0` 当成千分位数字保护掉的漏网之鱼。

现在由 `pcf_zh.py normalize` 统一（`merge-dir` 结束时会自动跑），
并由审计的半角标点检查守住。**千分位逗号是数字字面量的一部分，必须原样保留**——
所以审计里的数字保护正则要求千分位严格 3 位一组，否则 `0,0` 会被误当成 `1,000` 放过。

> 官方中文整理版**没有**中文公式（实测 0 条），所以公式标点没有官方先例可循，
> 只能按术语表规则 9「口径是中文正文，正常使用中文标点」定口径。

### 官方译名里的半角括号是「逐字引用」，不是标点违规

官方中文整理版有 7 条译名本身带**半角括号**：

```
处理应收账款(AR)   管理应付账款(AP)   管理人力资源信息系统(HRIS)
管理信息技术(IT)   管理环境健康与安全(EHS)
实施和维护企业质量管理体系(EQMS)   制定上市(go-to-market)战略
```

引用活动名必须**逐字照抄官方写法**（交叉引用检查 `「译名」[PCF ID]` 比的是逐字一致，
不是归一化后一致），所以这些括号不能被当半角标点处理。审计里对应放行逻辑在
`strip_official_paren_names()`。

> 反过来：本系统**自己写**的正文（定义、口径）里，括号一律用全角。
> 官方译名的括号形态不动，本系统正文的括号形态统一——两件事分开。

### 引用的活动名必须收敛到一种译法

指标名里用弯引号引用 APQC 活动名（`“管理与处理催收”`），口径正文里用直角引号加编号
（`「管理与处理催收」[10745]`）。并行翻译时最容易出的偏差就在这里：同一个英文活动名，
在不同批次里被译成了两三种中文。

收敛办法是**以英文原文为锚**：

1. 官方原文用直双引号引用活动名（`perform the process "manage sales orders"`），
   中文侧指标名用弯引号、口径与定义用直角引号；
2. 英文能对上分类树里**单个活动**的，取该活动的规范译名（官方中文整理版优先，
   见 `pcf_data.canonical_category_names()`）；
3. 英文是 APQC 自有简称（`"manage customer requests/inquiries"`）或把多个活动并进
   一个引号串（`"provide sourcing governance and perform category management"`）时，
   **树里本来就没有对应节点**，一律不改，只在审计里作提示。

> 早期版本改成拿中文引号内容去比对树里的中文名，结果 222 条提示全是误报
> ——「提供寻源治理并执行品类管理」是两个活动合成的一个引号串，本就不该有对应节点。
> **判定必须以英文为锚**，否则误报会淹没真问题。

实测一次收敛了 **176 处**引用。其中曾有一个陷阱：按位置配对时少数条目会错位
（英文顺序与中文顺序不一致），结果把 11 个活动名互相错换。**错位比漏译更危险**——
所以配对必须「按内容认领」（用英文活动名的规范中文去认领中文引号），
认领不到的才按剩余顺序兜底；而且要先从覆盖层回滚再重做。

对齐动作固化在 `scripts/pcf_zh_align.py` 里，每次合并后跑一次：

```bash
python scripts/pcf_zh_align.py --dry-run   # 只报告
python scripts/pcf_zh_align.py             # 对齐并写回覆盖层
```

它改的是**译法**不是**排版**：官方中文整理版的括号全半角混用（实测 12 条全角、
7 条半角，如「处理应收账款(AR)」），本系统译文统一用全角，比对时归一化、
写回时保持全角，不会把 100 多条译文的括号从全角改成半角。

另外还有 7 个活动名（`Conduct board activities` 等）在 PCF v8.0 分类树里根本不存在，
官方没有译名。指标名里引用它们时用本系统统一定稿的译法，并写进术语表 `nouns` 段，
保证全文一致。

## 五、翻译工作流

工具：`scripts/pcf_zh.py`

```bash
python scripts/pcf_zh.py coverage              # 看当前中文覆盖率
python scripts/pcf_zh.py validate              # 校验覆盖层（孤儿键、空译文、非中文）
python scripts/pcf_zh.py orphans                # 官方数据升级后查孤儿键
python scripts/pcf_zh.py export --kind category_names --start 0 --count 200 --out s_x.json
python scripts/pcf_zh.py merge --file s_x.json --translated zh_x.json
python scripts/pcf_zh.py merge-dir --dir <目录>  # 批量并回一个目录下的全部片段
python scripts/pcf_zh.py normalize            # 归一化口径译文的标点
python scripts/pcf_zh_align.py                  # 把译文里的活动名引用对齐到树里正式译名
python scripts/pcf_zh_audit.py                 # 一致性审计（--strict 有错误则退出码 1）
```

`--kind` 取值：`category_names` / `category_descriptions` / `metric_names` / `metric_formulas`。

### 流水线顺序

```
merge-dir（末尾自动跑标点归一化） → pcf_zh_align.py → pcf_zh_audit.py
```

顺序不能换：`merge-dir` 会用批次原文覆盖覆盖层，批次里存的还是未对齐的译法，
所以**每次合并后都必须再跑一次 `pcf_zh_align.py`**。`pcf_zh_align.py` 是幂等的，
已经对齐的内容不会被二次改写。

> **注意**：`export` 会**过滤掉已译条目**。所以切片必须从 `start=0` 开始切，
> 按原始序号偏移会漏条目。

### 并行翻译

10,000+ 条不可能手工翻，流程是：

1. `export` 切出切片文件（每片 200–430 条）；
2. worker 读切片 + 术语表 + 已定稿样例，产出 `{key: {field: "译文"}}`；
3. `merge-dir` 批量校验并合并——**任何一条缺译文、非中文、键对不上，整批拒绝合并**。

校验是硬门禁，不是建议。

### 合并必须字段级

同一个分类可能同时出现在 `category_names` 和 `category_descriptions` 两种切片里。
早期 `merge-dir` 用整块 `update` 覆盖同一键的字典，结果 **defs 批次的 203 条把先并入的
162 条 `name_zh` 冲掉了**（覆盖率从 1229 掉到 1107，且不报错）。

现在合并走 `apply_translation()`，只写本次要落的字段：

```python
overlay.setdefault(section, {}).setdefault(key, {})[field] = value
```

`tests/test_pcf_chinese.py::test_merge_keeps_other_fields_on_the_same_key` 守这条，
`COVERAGE_BASELINE` 是它的端到端版本——丢字段会让覆盖率跌破基线而失败。

## 六、测试守卫

`tests/test_pcf_chinese.py` 守住四条底线：

1. 覆盖层里的每个键都必须存在于数据集（官方数据升级后能发现孤儿）；
2. 每条译文必须非空且含中文；
3. **覆盖率不得倒退**（`COVERAGE_BASELINE`）——译文是人工资产，重导或改代码都不能让它悄悄变少；
4. 官方英文原文**永不被覆盖**：译文另存，`name_en` / `description` / `formula` 原样保留。

另外 `tests/test_pcf_import.py::test_committed_bilingual_pairs` 按
`name_zh_source` 区分「官方中文整理版 449 个」与「覆盖层补充的译文」，
两者的口径不能混为一谈。

### 审计脚本查的是「一致性」

`pcf_zh.py` 管「译文能不能进覆盖层」，`pcf_zh_audit.py` 管「进了之后一致吗」：

| 检查 | 抓的是什么 |
| --- | --- |
| 同英文 → 多译文 | 同一活动名/指标名在不同切片里译法不同 |
| 交叉引用一致 | 定义正文里 `「译名」[PCF ID]` 与该 ID 的活动名译文不逐字一致 |
| 活动名引用一致 | 指标名/口径里引用的活动名与树里正式译名不一致（**以英文原文为锚**） |
| 标点口径 | 名称类混入句读，或正文用半角标点 |
| 术语表遵从 | 英文命中术语表词条，中文却没用术语表译法 |
| 健康度 | 孤儿键、空译文、非中文 |

审计分**错误**（阻塞）和**提示**（不阻塞）两档。提示里会有些假阳性——
例如「客户对保修处理的满意度」不字面包含术语表的「客户满意度」，但译法是对的；
这种要看，不要无脑改。

活动名引用那条最容易出假阳性：英文引用的是 APQC 简称或多个活动合并的引号串时，
树里本来就没有对应节点。此时只作提示，不判错——**判错必须以英文能对上树里单个活动为前提**。

`tests/test_pcf_chinese.py::test_overlay_audit_has_no_errors` 把审计接进了 CI，
错误档必须为空。

## 七、界面标注

`web/js/views/pcf.js`：

- 分类树行：有中文显示中文，没中文显示英文并标 **未译**；
- 详情标题：中文为主、英文原文为辅，附来源徽标（官方中文版 / 参考译文）；
- 官方定义区：有中文译文则中文在上、**官方英文原文在下**，并标「参考译文」；
- 指标表：中文名/口径/单位在上，英文原文在下，表尾标注「指标中文为参考译文，非 APQC 官方口径」。

## 八、已知上游数据特征

这两条来自官方 Excel，**不是译文造成的**，翻译时只能如实保留：

1. **59 条 AI 专项指标的 `formula` 是裸数字**（`535.1160` 这类），不是计算式。
   官方工作簿里这几行的 Formula 列存的是行标识。译文保留字面量并补单位注解
   （`535.1160（百分比）。`），不臆造计算式。
2. **`metric_conflict_count = 138`**：同一指标在跨行业 / 消费品 / 消费电子三套工作簿里
   公式或名称措辞不同。`scripts/import_pcf.py` 保留主变体（跨行业）版本并计数，
   便于追溯而不静默覆盖。

## 九、明确不做的事

- **不覆盖官方英文原文。** 任何情况下 `name_en` / `description` / `formula` 保持原样。
- **不把译文标成官方。** 来源徽标是硬要求，不是可选项。
- **不手工编辑 `pcf_v80.json`。** 它只由 `scripts/import_pcf.py` 生成。
- **不把译文写进前端。** 前端只读后端下发的字段，不维护映射表
  （与 CLAUDE.md「枚举的中文标签由后端下发」一致）。
- **不在术语表之外自创译法。** 遇到术语表没有的词，先加术语表再翻译。
