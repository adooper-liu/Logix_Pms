# 产品语言、页面文案与交互表达规范

> 状态：待评审规范；2026-11-03补充产品语言治理，静态核对基线 `4607792`，不代表页面改造已完成。服从[产品基本原则](bpm-product-principles.md)。本规范不借文案创建新状态/接口或宣传未实现能力；当前轻量发布与未来R3部署的词汇分开。
> 配套：[落地规格](bpm-lifecycle-implementation-spec.md)、[闭环路线](bpm-lifecycle-gap-and-roadmap.md)、[文字清单与差异](product-language-inventory.md)、[页面职责与拆分](page-responsibility-and-decomposition.md)。
> 本文是唯一表达规范；清单只登记证据、目标和落实状态，不另定义一套规则。统一术语、字段、字典、状态、动作、提示、错误、示例与帮助，不要求所有页面机械地把全部字段铺在首屏。

## 1. 表达原则

1. **对象明确**：说流程、模型版本、实例、任务、指标和证据；“发布包/部署”只在R3真正实施后使用，不代替当前模型发布身份。
2. **动作准确**：当前动作使用保存草稿、提交评审、发布模型、完成任务等准确名字。R3若明确拆审批/部署/启用，再分别采用这些动作词，不提前改变当前publish的含义。
3. **结果有边界**：已接收不等于已生效，已部署不等于已启用，已结项不等于改善达标。
4. **一句一事**：标题说明对象，说明句讲用途，状态讲事实，提示给下一步；不把背景、原理、风险都挤进标题。
5. **短而完整**：不使用口号、拟人化、责备语气和连续感叹号；专业词首次解释，之后保持一致。
6. **不用文字做逻辑**：前端根据代码/允许操作渲染，不通过“包含某句中文”判断错误、权限或分支。

长度作为审校参考而非强制截断：标题约 4–12 个汉字；按钮约 2–8 个汉字；用途说明通常一句、约 20–40 字。关键风险即使较长也不能省略；详细规则可展开或进入帮助。

## 2. 统一信息结构

### 2.1 页面：对象与目标—当前状态—待办原因—下一步操作

| 区块 | 必须回答 | 示例 |
|---|---|---|
| 标题/用途 | 管什么、为何来这里 | 流程指标；“核验数据来源，查看流程结果与目标的差距。” |
| 上下文 | 当前看的哪条、哪轮、哪版 | 订单履行 / 改善项目 PRJ-… / 运行版本 v… |
| 状态 | 现在发生了什么 | “观察中”；“尚未部署”；“样本不足” |
| 待办/原因 | 为什么还不能继续 | “缺少接收方确认”；“指标口径与基线不同” |
| 主要操作 | 下一步做什么 | “确认交接”“核对指标口径” |
| 证据与详情 | 判断从哪来 | 来源、版本、窗口、样本、审核者、时间；按需展开 |

无阻断时不要生造待办；无当前数据时不铺一排 0；多个原因按“风险/权限—必要配置—数据质量—其他”排序，只突出当前最相关一项，完整清单可展开。

### 2.2 条件/门禁行

固定为：**条件｜状态｜原因｜操作**。

示例：

| 条件 | 状态 | 原因 | 操作 |
|---|---|---|---|
| 现状基线 | 待补充 | 本轮尚无已确认基线 | 建立基线 |
| 模型发布 | 待核验 | 本轮尚未固定已发布模型版本 | 选择发布版本 |
| 引擎部署（仅R3） | 结果待确认 | 引擎响应超时，正在核对原命令 | 查看进度 |
| 机器人运行 | 不适用 | 本流程不使用机器人；已审核 | 查看依据 |
| 操作验证 | 待验证 | 两名参与人尚未完成操作验证 | 查看人员 |

“不适用”不显示成“已完成”，也不要求补造记录以填满绿色条。

### 2.3 表单

按“基本信息—适用范围—业务规则—责任与审核”分组，仅显示当前任务需要的组。

- 字段名用稳定名词：“流程类型”“适用组织”“观察截止日期”，不用“你想什么时候结束”。
- 必填标识与可选说明明确；占位符只给示例，不替代 label。
- 校验靠近字段：“目标值不能为空”“结束日期须晚于开始日期”。
- 禁用操作附可见原因，键盘可访问；权限和服务端校验独立。
- 未保存离开提示保留内容，不因刷新数据覆盖用户输入。

### 2.4 列表和详情

业务列表优先：**对象｜状态｜责任人｜时间/期限｜操作**；指标增加“值/目标/质量”，版本增加“版本/范围”。不为了模板统一删掉必要业务列。

详情按：**基本信息—适用范围/版本—结果或内容—证据—操作记录**。较长审核意见、系统错误、样本规则可展开，不压在主表每一行。

### 2.5 本轮核验：四项结论与进度

**资料就绪、上线就绪、运行有效、改善达标**同属薄轮次对照的核验进度，按时点补齐process/project、现状/方案/上线模型与冻结口径。创建/分析时可尚未立项或上线；对应结论未成立就显示缺项，不强迫伪造未来版本。它们不构成独立阶段机；项目current_stage仍为1–5。

| 展示内容 | 示例 | 含义 |
|---|---|---|
| 本轮对照 | PRJ-… / 现状 v1 / 上线 v2 / 口径快照… | 四身份同时成立，不凭“同流程”混入数据 |
| 核验进度 | 本轮 2/4 项结论已确认 | 不是另一个阶段进度，不提供“进入下一阶段” |
| 条件明细 | 4/6 项已核验，1 项待签收 | 仅表示本项证据准备程度，不自动通过 |
| 模型发布待核验 | 本轮已发布版本v2，其他上线证据待补充 | 尚不能写“上线就绪”；草稿/待评审不能代替已发布身份 |
| 运行与改善 | 同一冻结口径，分别核验运行和改善结果 | 有改善目标的项目不能把改善达标设不适用 |
| 复核提示 | 样本与本轮口径不一致，请核对来源。 | 保留原记录与决定，不覆盖冻结依据 |

页面显示“资料待补充 / 上线证据核验中 / 运行证据待签收 / 改善未达标”等事实，不称“四阶段”。无改善项目时展示持续运行/复盘，不创建“改善达标不适用”来凑进度。底层可选工具和风险条件仍可按批准政策裁剪，不因此豁免项目改善目标。

### 2.6 方法工作区：本步任务—方法与步骤—开始操作—产出与验收

保留当前 start 的实际去向：战略对齐→strategy；流程架构→pcf/APQC；建模、设计→同一 designer 的现状/方案模式；分析→monitor?tab=analysis；执行→execution；监控度量→dashboard/驾驶舱；变革优化→projects/项目组合。治理仍可进入 authorization，但标为贯穿治理，不是第九个工作阶段。需要下钻地图、指标或项目工作台时经原模块入口，不把改主跳转称为“对齐”。各模块继续补“任务—方法—操作—产出核验”，不是只有学习链接。

| 区块 | 内容要求 | 战略对齐示例 |
|---|---|---|
| 本步任务 | 本次要形成的业务结果和必要输入 | 明确交付目标，并关联承接流程。 |
| 方法与步骤 | 说明为何选此方法、如何操作；允许替换/复用 | 用 OGSM 明确目标和度量；用 SWOT 核对事实依据。 |
| 开始操作 | 页内表单/结构化表格/原专业画布，保留范围和草稿 | 选择已有目标 / 填写 OGSM / 预览目标草稿。 |
| 产出与验收 | 保存到哪个业务对象、由谁按何规则核验 | 确认写入战略目标；补基线、责任人与期限后提交审核。 |

按钮采用“填写 OGSM”“分析样本”“编辑现状模型”“比较方案”“提交核验”，不笼统叫“使用工具”。选择方法前可展开短原理；长理论进入帮助，但必要操作步骤就在当前任务旁。画布类保留专门页面，使用相同上下文往返，不另做简化副本。

首屏不铺全部方法。先显示本任务推荐且有依据的方法，允许查看其他适用方法；方法能力使用独立属性“参考说明、可填写、直接办理、可计算、外部核验、已验证集成”，不是自动升级等级；无算法不报计算，存在接口不证明业务有效。保存反馈说“方法草稿已保存”；业务写入说“目标草稿已生成”；审核后才说“本项产出已核验”，不能写“方法已证明有效”。

### 2.7 保障清单：事项—责任—时点—证据—核验

清单按高层支持、流程负责人、统一方法、绩效承接、文化与采用分组。20 项只是章程、RACI、培训和复盘等原记录的核验视图，不新建 20 条平行任务。缺责任、期限或核验字段时仅在原对象补齐；来源记录不存在则指向对应模块创建原业务记录。页面主表呈现“事项 / 原记录 / 责任人 / 期限 / 核验结果 / 操作”，展开证据与审核要求。

- 行内 checkbox 表示选择待提交的事项，不直接把业务状态改成完成；批量提交也逐项服务端核验。
- 按钮：“提交核验”“补充证据”“记录评审”“申请不适用”“查看审核意见”。
- 已核验显示“已核验〔时间/审核者〕”；未发生的会议/资源到位/操作验证不得只凭计划自动勾选。
- 期限已到未做显示“已逾期”，已做待审核显示“待核验”，证据过期显示“需复核”；三者不能混称“未完成”。
- 汇总：“本期 8/12 项已核验，2 项待复核”；禁止“高层支持 100%”“文化转型完成”。清单进度只表达保障动作，不等于组织效果保证。

### 2.8 流程主线与本轮对照的表达边界

八阶段是这条流程的管理导航，标明当前任务该去哪个既有模块；不显示“八阶段项目进度”，不提供“推进到第 8 阶段”动作。项目内部保持五阶段，项目结项后流程仍运行、监控和复盘。建模/分析/执行/监控没有项目也可进入；变革优化按需打开或建立一轮项目。

流程卡“本轮对照”固定展示：**流程｜关联项目｜现状/上线模型版本｜冻结口径｜前后窗口｜验收结论**。箭头用于解释业务先后，不能替代这组同时成立的引用。未关联项目显示“尚未立项”；无法确认历史版本或口径显示“历史依据未核实”，不自动填最新值。

当前轻量运行时使用“发布版本 v…（模型版本记录…）”，不显示不存在的独立部署 ID。Flowable 接入后才显示“模型版本 / 引擎部署”两项，并说明映射；它们不是同一种 ID。

短提示：“同一轮比较须使用已冻结口径，并分别固定现状和上线版本。”“项目已结项，流程继续运行。”“口径不一致，本轮暂不可比较。”业务关联键仅标识外部同一笔业务，不显示为轮次、版本或口径的替代项。

## 3. 术语表

| 统一用词 | 含义 | 不混用为 |
|---|---|---|
| 企业流程地图 | 公司自己的流程目录和关系 | PCF 标准原文、流程运行图 |
| PCF 分类框架 | 对标参照分类 | 公司的实际业务步骤 |
| 流程类型 | 核心/支持/管理 | 层级、阶段、优先级 |
| 流程负责人 | 对端到端结果负责的人；帮助中标注 Owner | 当前任务处理人、系统管理员 |
| 项目发起人 | 支持并授权本次改善/试点的 Sponsor | 项目创建人 |
| 项目负责人 | 负责本项目交付与协调；当前Project归属账号也是权限依据 | 不因流程关联自动等于流程负责人 |
| 任务处理人 | 被指派或已认领该运行任务的人 | 流程负责人、项目负责人、治理角色 |
| 治理角色 | 对流程或事项承担的业务职责 | 系统账号角色及其API权限 |
| 系统角色 | 控制账号允许的系统操作范围 | 不自动证明业务任命或专业验收资格 |
| 现状版本（As-Is） | 本轮诊断引用的实际现状模型 | 最新草稿 |
| 目标版本（To-Be） | 本轮选定的未来方案模型 | 自动等于生产运行版本 |
| 现状基线 | 固定范围的绩效/样本及口径 | 文件资产基线 |
| 资产基线 | 固定的文件/模板等资产版本集合 | 实际绩效基线 |
| 本轮对照 | 同时固定流程、改善项目、现状/上线版本及冻结口径的一组引用 | 另一套项目台账、业务关联键 |
| 当前发布身份 | Flowable 接入前为已发布 ProcessModelVersion 行 | 版本整数本身、外部引擎部署 ID |
| 发布包（R3） | Flowable 接入时若需要，固定模型和相关执行配置 | 当前已存在的独立实体；本轮证据链的前置表 |
| 部署（R3） | 引擎实际部署，与原模型版本建立映射 | 已启用、业务已开始运行 |
| 启用（仅R3，若设计为独立操作） | 允许新实例使用经确认的引擎映射 | 当前模型发布、修改全部在途实例 |
| 流程实例 | 一次具体业务运行 | 改善项目、标准任务定义 |
| 运行任务 | 实例中的待办/人工工作项 | L5 标准任务定义 |
| 活动执行 | 一次节点执行，含自动/等待活动 | 必定是人工待办 |
| 指标口径 | 来源、公式、范围、粒度和版本 | 指标单位 |
| 达成状态 | 有效样本与目标/阈值的比较 | 数据是否可靠 |
| 数据质量 | 样本的有效性、时效、完整性 | 业务结果好坏 |
| 核验 | 检查证据是否满足条件 | 自动授予审批权限 |
| 效果验收 | 独立判断改善结果 | 项目步骤勾选完成 |
| 复盘 | 周期性审查运行和行动 | 再填一份没有结论的记录 |

代码中的 `owner_user_id` 等字段名不因此改名。界面按所属对象分别使用“流程负责人”“项目负责人”“文件负责人”等名称，不能把所有Owner统一改成“流程负责人”；任务的assignee称“任务处理人”。英文Owner仅作术语解释，系统角色OWNER沿原权限代码保留。中文业务枚举标签的唯一运行时来源仍是后端meta/响应。

证据等级已有 L1–L5，容易与流程层级 L1–L5 混淆；界面显示“证据等级 L1：现场观察数据”，不能只写“L1”。不得擅自替换既有证据分类代码。

本次统一保留“流程卡”作为导航、页头、帮助与返回来源的名称；“闭环”用于描述业务关系，不再将“流程闭环”作为同页另一标题。该决定替换本规范原先拟议的概览改名，路由仍为 `process_card`。

## 5. 状态词汇

不建立前端映射；下表是后端标签规格。不同状态机可以用相同中文词，但必须保留 domain+code，不能靠标签合并业务逻辑。

| 状态域 | 建议标签 | 说明 |
|---|---|---|
| 本轮核验 | 待补充 / 核验中 / 待签收 / 已确认 / 受阻 / 需复核 | 同一轮次对照上的四项结论及进度，不新增阶段状态机；改善项目不得豁免改善达标 |
| 保障动作 | 待办理 / 办理中 / 待核验 / 已核验 / 受阻 / 不适用 | 周期性动作逐期核验，不用清单完成率代表文化或高层支持程度 |
| 方法记录 | 草稿 / 已应用 / 待核验 / 已核验 / 需修订 | 后续拟议表达，非当前code清单；保存或应用只产生记录，不自动判方法有效 |
| 证据 | 待补充 / 待审核 / 有效 / 不符合 / 已过期 / 不适用 | “有效”不等于流程绩效已达标 |
| 核对条件 | 未满足 / 已满足 / 不适用 / 需复核 | 原因单列，不在状态名堆长句 |
| 当前模型版本 | 草稿 / 待评审 / 已发布 / 已被替代 | 保持当前状态含义；用途/固定引用不自动改变发布行为 |
| 引擎部署（仅R3） | 接入计划定义的部署/待确认状态 | 当前不创建部署表/发布包状态来替代原模型版本 |
| 引擎启用（仅R3） | 接入计划定义的启用/停用状态 | 若与部署拆分，界面明确；不假装当前已有独立启用指针 |
| 命令 | 已接收 / 处理中 / 已完成 / 已拒绝 / 结果待确认 | “已接收”不可反馈任务已完成 |
| 运行 | 待启动 / 运行中 / 等待中 / 已挂起 / 已完成 / 已取消 | “同步延迟”另做质量提示，不直接覆盖引擎运行态 |
| 达成状态 | 达标 / 预警 / 未达标 / 暂不判定 | 后三种不能混同具体颜色；数值和文字同时呈现 |
| 数据质量 | 有效 / 样本不足 / 已过期 / 来源冲突 / 待核实 | 质量不足时不能用绿灯表示无风险 |
| 效果验收 | 观察中 / 待验收 / 改善达标 / 未达标 / 证据不足 | “停止实施”是项目处置，不等于改善失败原因之一已验证 |
| 复盘 | 待复盘 / 已复盘 / 已逾期 | 复盘需有结论与行动，不只有日期 |

固定结构：**事实或问题 + 必要原因/影响 + 可执行下一步**。事实未知时明确待确认。

| 情况 | 推荐文案 | 动作 |

| 未选流程 | 选择流程后查看闭环。 | 选择流程 |
| 无流程分类 | 尚未确认流程类型。分类后可按业务用途筛选。 | 确认分类 |
| 无基线 | 本轮尚无已确认基线。先选择样本范围并核验数据。 | 建立基线 |
| 无业务样本 | 当前范围没有有效业务样本，暂不计算结果。 | 查看样本范围 |
| 数据不足 | 样本不足，暂不判定达成状态。 | 查看数据质量 |
| 口径不一致 | 暂不可比较：前后指标口径不同。 | 核对指标口径 |
| 估算不支持 | 该模型包含并行路径，暂不提供本项估算。 | 查看支持范围 |
| 无任务 | 当前没有待办理任务。 | 查看流程实例（有权限时） |

| 投影延迟 | 状态同步中，最近同步于〔时间〕。 | 刷新状态 |
| 部署失败（仅R3） | 部署未完成；原版本状态需按对账确认，不在结果未知时保证“未变”。 | 查看原因 / 核对原操作 |

〔时间/原因〕必须来自当前结果，不硬编码“稍后自动成功”。复杂技术堆栈、账号令牌和外部请求载荷只进受控日志，页面显示去敏摘要和请求编号。

### 6.1 成功反馈的事实等级

- 本地保存事务成功：可以说“草稿已保存”。
- 命令入队：只能说“已接收”。
- 当前模型发布事务成功：可以说“本版模型已发布；在途实例仍使用原快照”。
- R3引擎已确认且本地投影同步：才说相应引擎任务已完成；入队只说已接收。
- R3若独立启用映射已切换：才说新版本已启用，不能把它写成当前已有操作。
- 仅写入验收意见：说“验收结论已记录”，不是所有情况下都说“改善已达标”。

## 7. 重要确认框

统一顺序：**操作对象—影响—不影响什么—前提/风险—确认动作**。无需风险的普通保存不加确认框。

### 当前发布模型

- 标题：发布模型。
- 对象：流程、模型版本、差异和适用变更单；核对当前版本，避免覆盖他人变更。
- 说明：本次发布更新当前运行模型及发布指针。新实例使用本版，在途仍使用启动快照；仅草稿冻结不会更新运行。
- 前提：原评审/权限/变更及用途准入通过；本轮上线证据另核，不把发布本身写成改善达标。
- 按钮：返回 / 发布模型。

### R3远程部署或启用（未来文案边界）

只有接入计划明确定义实际审批/部署/启用操作后，确认框才分别显示外部部署、结果未知及新启动影响；不提前要求不存在的发布包/部署ID。正式运行样本不得成为首次启用前提。

### 取消实例

- 标题：取消流程实例
- 说明：未完成任务将停止。已产生的外部业务结果不会自动撤销；需要补偿时将按配置生成待办。
- 字段：取消原因（必填）。
- 按钮：返回 / 取消实例。

### 申请不适用

- 标题：申请条件不适用
- 字段：条件、适用范围、不适用理由、审核者。
- 说明：批准后只免除此条件，不代表完成相关工作。强制条件不能申请。
- 按钮：返回 / 提交申请。

### 提交效果验收

- 标题：提交效果验收
- 对象：项目、已批准验收约定版本、基线、发布版本、观察窗口。
- 说明：按事先批准的目标与规则提交本次样本和证据，不能在此时修改原验收标准。后续补数需要新修订；验收由指定审核者独立完成。
- 按钮：返回 / 提交验收。

### 停止新启动（拟增能力）

当前无通用独立启用指针；停止新启动与取消/挂起在途须由实施计划分别定义。未实现前不出现假按钮。R3若支持，应明确禁止哪些范围的新实例、在途策略和外部业务影响，保存授权与原因；不能用数据库恢复代替业务回退。

## 9. 文案的唯一来源与审校

| 内容 | 归属 | 约束 |
|---|---|---|
| 枚举、状态、原因代码和允许操作标签 | 后端 schema/service 的 meta 与响应 | 不在 JS 创建平行中文映射 |
| 八阶段定义/映射 | 新 lifecycle 服务 | start/cbok/toolbox 读取同一目录 |
| 页面标题、短用途说明 | `core/state.js`、页面固定标题；共用文案集中 | 相同页面不得被 router/视图/help 三套称呼混淆 |
| 长说明、术语、边界和场景手册 | `web/js/help/catalog.js` | 页内不复制长文 |
| 动作成功/失败事实 | 服务端响应及通用 API 处理 | 不按中文字符串判逻辑；可行动错误含稳定 code |
| 用户填写内容 | 各自业务对象 | 转义展示，不重写用户意见来迎合规范 |

### 9.1 内容分类与唯一来源

统一的是概念、适用范围和表达规则，不是要求全系统只有一份字符串大文件。代码按业务域维护，公共表达复用；不同域的同名代码不合并为全局状态。

| 类别 | 标识及必备信息 | 权威来源 / 消费边界 |
|---|---|---|
| 术语 | concept_key、标准名、定义、英文/缩写、允许短名、禁用混称、业务域 | 本规范定义语义；运行时帮助复用原catalog，不复制第二套术语解释 |
| 字段 | object.field、界面名、含义、类型/单位、空值/零、必填时点、校验、示例 | schema与业务服务是实际约束；界面标签不能承诺服务端不支持的行为 |
| 固定枚举 | domain + code、标签、定义、适用对象、兼容值 | 后端原业务域单一定义，经meta/响应下发；前端仅维护视觉色调 |
| 可配置字典 | 稳定ID/code、名称、排序、启停、范围、变更影响 | 原组织/岗位/角色/工具等业务API；不把它们再复制到通用字典表 |
| 页面/动作 | page_key/action_key、主任务、标题、短说明、按钮、前提、实际结果 | 现有页面定义与动作注册；跨页公共部分集中，业务细节留所属模块 |
| 反馈/错误 | message_key/error_code、条件、级别、字段路径、文案参数、恢复动作 | 业务原因由后端决定；网络/会话/渲染失败由前端基础设施表达 |
| 示例/帮助 | example_key/topic_id、对应字段/场景、合法样例、适用版本、限制 | 示例与真实数据区分；方法/种子模板内容归原维护模块，长帮助归catalog |

清单记录权威来源、使用位置、拟维护职责、核对基线和落实状态。`concept_key/message_key`是设计标识，不自动要求新数据库表或全量翻译系统。首次实施选一个业务域验证后扩展；不为收集中文而新增接口暴露不可见业务对象。

### 9.2 名称与字段规则

- 同一概念一标准名；短名必须登记适用位置，例如“关键绩效指标（KPI）”用于首次说明，“流程指标”用于页面，“KPI”用于窄表头。不能随机把不同对象都叫“指标”。
- 字段以对象为范围：流程负责人、项目负责人、任务处理人、文件负责人分别表达；`owner`文本与`owner_user_id`权限账号不是一个字段。现有API名不因改标签而批量重命名。
- 列表可用上下文短名，详情/表单须明确对象；placeholder只给合法示例，不能替代标签、必填或默认值。示例不得自动写入真实业务。
- 数值同时约定单位、精度、范围及分母；缺失用“未提供/暂不计算”，不能转成0；百分比、比例、金额及数量不混换。模型估算、样本实测、目标值分开标明。
- UTC时间由前端按本地时区显示；日期与期间按纯日期处理。天/工作日、自然月/观察窗口、版本整数/版本行ID、技术编码/展示名不得混同。
- 对所有可编辑字段，清单最终须到 `对象.字段` 粒度，并关联真实schema/接口、表单标签和错误路径。首版重点字段清单不是全库字段已经完成盘点的证明。

### 9.3 状态与字典规则

- 状态键是 `domain + code`。例如 `project.CLOSED`拟显示“已结项”，`exception.CLOSED`按异常关闭规则显示，`instance.COMPLETED`显示“已完成”；不得全局替换CLOSED或“已完成”。
- 相同名称不证明相同状态机；不同名称也不证明不同对象。先核现有流转、权限和副作用，再决定合并标签源，不能为统一文字改变规则。
- 标签、说明、色调、是否终态、允许动作分开。色彩只是辅助；不能把红/黄/绿直接等同经过新业务规则认证的达标结论。KPI若实际含义仅为颜色，先明确口径再改为达成标签。
- 固定枚举不做任意CRUD；业务可配置字典用原功能维护，停用后禁止新选但保留历史引用。不复用旧code表达新含义，不静默重写历史审计文案。
- 服务端各消费接口共享同一域定义。列表、详情、meta、汇总、导出必须一致；缺标签展示受控回退或待核实，不在前端悄悄补一张中文业务表。

### 9.4 错误、提示与示例契约

反馈区分：操作结果、业务校验、权限/不可见、并发冲突、网络失败、系统故障、数据质量、未来异步待确认。第6节的短文案适用，但不得凭一条文案推断状态。

拟增的错误扩展兼容现有 `detail` 字符串：保留原HTTP状态，增稳定 `code`、安全参数、`field_errors`、可追踪编号（相关基础设施尚未完成时不得展示伪编号）；明确重试是否安全。字段错误包含对象路径与业务原因，前端在原字段旁展示，顶端只汇总。未经确认不全局改所有HTTP状态或API响应形状。

- 400/422：指出不合法字段与真实规则，不直接显示Pydantic数组JSON；数组行定位须保留索引，提示不拼回密码/token/完整请求体。
- 401：登录接口显示“用户名或口令不正确”，不透露用户是否存在，也不一律按会话过期处理；已认证业务请求按原策略处理会话失效。403说明允许披露的操作资格；不可见对象按原安全策略404，不透露其名称/数量。
- 409：区分版本冲突、重复操作、状态已变化；不能全都翻译成“版本冲突”。保留用户草稿，不自动重放不可幂等写操作。
- 断网/5xx：查询请求可提示“暂时无法加载数据，请重试”；写请求若无法确认是否提交，提示“操作结果待确认，请先核对原记录”，不把超时或5xx本身当作未写入证据。仅已确认未生效且允许重试时提示重新提交。技术异常进受控日志，不要求普通用户检查uvicorn。
- 未知写入结果：说明“结果待确认”，先查询原操作；不要在超时后宣称失败且未生效。当前无异步命令设施的模块不出现虚假的处理进度。
- 示例采用虚构、合法、可复核的值；JSON使用真实字段key和类型，显示“示例，不自动提交”；演示账号说明按运行环境限定。教程收益数字标为示例，不暗示产品承诺。
- 表单示例、模板版本、种子数据、帮助实例与专业计算使用同一语义，但不得把共享示例当真实证据。示例变更连同依赖字段校验，不做生产业务数据替换。

### 9.5 清单维护与实施验收

[文字清单](product-language-inventory.md)维护范围和证据，[页面表](page-responsibility-and-decomposition.md)定义职责与兼容路由。推荐每条登记状态为“已观察/拟统一/待业务定值/已实施待验/已验证”；这是文档跟踪标签，不新增业务状态机。

实施按域交付：盘点重复源→核语义→确定标准/短名→收敛权威定义→逐消费点替换→补行为测试→浏览器验收。维护职责为建议角色，不冒称已指定实际负责人：业务方确认含义，后端维护状态/字段契约，前端维护交互表达，测试核消费一致性，发布记录兼容影响。

验收至少包括：

1. 固定枚举所有现有code都能通过原meta/响应获得标签；域内列表/详情/汇总一致，前端无新枚举中文副本。
2. 更新标准标签后实际消费页面/导出一致；检查旧值兼容、停用历史引用，而不是只对源码做字符串搜索。
3. 错误按稳定代码/字段路径展示，422不泄露输入；409保留草稿，断网/未知结果不伪造成功，401/403/404不破坏原权限。
4. 导航、页头、页签、帮助和返回来源共享同页标识；同页短名可解释，跨页不产生不同业务含义。
5. 样例符合真实schema和单位约定，无密钥/个人信息泄漏，无默认写入；用户内容与历史证据不被改写。
6. 测试校验语义、域代码、动作和重要短语，不把所有长句逐字锁成快照；实际页面还需键盘、窄屏、长文本和错误恢复验证。

每切片审校：

- 标题是否说清对象；说明是否一句讲用途？
- 同一动作在按钮、确认框和结果里是否同名？
- 状态是否真实，是否把待确认写成完成？四项核验结论是否同时有本轮进度和具体结论，而非四个静态标签？
- 每个阶段是否把任务、方法、直接操作、业务产物和核验接起来，而不是让用户另找工具？
- 保障动作是否明确责任、时点、证据与审核；是否把“计划完成/填表”冒充组织行为已经发生？
- 错误是否指出下一步，且未泄露敏感信息？
- 空数据、数据质量、权限、异步和不支持是否分别处理？
- 是否存在新的前端枚举中文表或重复长帮助？
- 术语是否符合本表，是否误把 L5 定义和运行待办混同？
- 页面在窄屏、键盘操作和长名称下是否仍可理解；不用仅颜色传达状态？

文案测试应断言状态代码/权限/目标动作和关键表述，不把整段说明的每个字锁死成脆弱快照。浏览器验收同时检查截断、换行、焦点、pending 状态和失败恢复。
