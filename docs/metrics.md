# 指标逻辑与计算说明

这份文档是系统内所有可见指标的口径来源。页面上的 `?` 悬浮提示是它的简版；
两者不一致时，以本文和代码为准，并同步修正另一处。

约定：

- 时间统一按 UTC 存储，出参补 `+00:00`，前端按浏览器本地时区显示。
- 纯日期（`2026-04-01`）不做时区换算。
- “今天”指浏览器本地日期，用于超期判断；后端超期判断使用 UTC `now`。
- 所有比例默认保留 1 位小数，后端在出参前四舍五入。

## 1. 管理驾驶舱

数据来源：[app/services/dashboard.py](../app/services/dashboard.py)、[app/api/v1/dashboard.py](../app/api/v1/dashboard.py)

| 指标 | 计算逻辑 | 口径与边界 |
|---|---|---|
| 在办流程项目 | `count(project.status == ACTIVE)` | 不含待启动、暂停、已结项、已取消 |
| 今年结项 | `count(status == CLOSED and end_date.year == 当前年)` | 用计划结束年份，不是实际关单时间；系统没有 `closed_at` 字段 |
| 待改善流程 | `count(process_arch.is_improvement_target == true)` | 标记来自流程架构评估，不是按健康度自动推断 |
| 在办项目平均目标改善 | `mean(active_project.improvement_pct)` | 只统计有值的在办项目；没有值时为 0 |
| 未闭环异常 | `count(exception.status in (OPEN, IN_PROGRESS))` | 不含已解决、已闭环 |
| 流程资产（L1–L4） | `count(process_arch)` | 所有层级节点总数，包含 L4 活动 |
| 五阶段平均进度 | `mean(project.progress)`，范围限定为 `status == ACTIVE` 且 `current_stage == 阶段` | 该阶段没有在办项目时显示“—”，不按 0% 计 |
| 阶段健康度 | 无在办项目 → GOOD；平均进度 ≥60 → GOOD；≥30 → WATCH；其余 → RISK | 这是项目执行健康度，不是流程健康度 |
| 方法论占比 | 该方法项目数 ÷ 全部项目数 | 包含所有状态的项目；分母为 0 时不出图 |
| 风险提醒 | `health_score < 70` 或 `pain_score >= 4` | 健康度 <60 或痛点 ≥4 判 HIGH，其余 MEDIUM |
| 项目超期 | `end_date < 今天 and progress < 100` | 只看在办项目看板；已完成项目不标超期 |

### `improvement_pct`

```text
improvement_pct = |baseline_value - target_value| / |baseline_value| * 100
```

- 只在 `baseline_value` 与 `target_value` 都有值时计算；`baseline_value = 0` 时不计算，避免除零。
- 立项时若未显式传 `improvement_pct`，后端自动按上式推算。

## 2. 企业流程地图

数据来源：[app/api/v1/process_map.py](../app/api/v1/process_map.py)、[app/models/process.py](../app/models/process.py)

| 指标 | 计算逻辑 | 口径与边界 |
|---|---|---|
| 综合优先级得分 | `strategic_importance × pain_score × improvement_space` | 三项各 0–5 分，结果 0–125 |
| 热度等级 | ≥80 或健康度 <50 → CRITICAL；≥55 或健康度 <65 → HIGH；≥30 → MEDIUM；其余 LOW | 由后端统一判定；前端不再另算一套 |
| 健康度 | 0–100 分，来自流程架构评估 | 空值表示未评估，不参与平均 |
| 平均健康度（地图页） | 全部流程 `health_score` 非空值的算术平均 | 未评估节点不计入分母 |
| 层级节点数 | 该层级（L1/L2/L3/L4）的节点数量 | 前端从架构树递归统计 |
| 待改善数量 | `is_improvement_target` 为真的节点数 | 点击后地图列表按此过滤 |
| 下级数量 | 当前节点的直接子节点数 | 不等于整棵子树的节点数 |
| 流程资产 | 全部层级的节点总数 | 与驾驶舱同一口径 |

### 为什么优先级用乘法

三个维度都是“越高越该改”：战略重要性高、痛得厉害、改善空间大。乘法让任意一项接近 0 时整体得分显著下降，
避免“战略重要但没什么可改”的流程被排到前面。上限 125 用于热力图分档，不是业务约束。

## 3. 流程项目组合

数据来源：[app/api/v1/projects.py](../app/api/v1/projects.py)、[app/services/workflow.py](../app/services/workflow.py)

| 指标 | 计算逻辑 | 口径与边界 |
|---|---|---|
| 项目总数 | 当前筛选条件下的项目数 | 分页前总数 |
| 进行中 | `status == ACTIVE` 的项目数 | — |
| 已结项 | `status == CLOSED` 的项目数 | — |
| 平均进度 | 当前筛选结果 `progress` 的算术平均 | 空列表为 0 |
| 超期项目 | `end_date < 今天 and progress < 100` | 与驾驶舱一致 |
| 整体进度 | `已完成步骤数 / 全部步骤数 × 100%` | 标准工作流共 24 步 |
| 已用 / 预算 | `actual_cost / budget`，单位万元 | 预算为 0 时只显示实际成本 |
| 目标改善幅度 | `|基线 - 目标| / |基线| × 100%` | 基线为 0 时不计算 |

### 进度与阶段推进

```text
progress = DONE 步骤数 / 24 * 100
```

- 每次更新步骤状态后，`recompute_progress` 重新统计并写回 `project.progress`。
- 当前阶段全部步骤为 DONE 时，`current_stage` 自动 +1；可以连续推进多个阶段。
- 进度达到 100% 时，项目状态自动置为 `CLOSED`。
- 当前阶段回退不会自动把 `current_stage` 退回去；这是“只前进不后退”的保守策略，需人工调整项目阶段。

### 甘特图日期

```text
offset_days = round(项目总天数 × (步骤序号 + 1) / 24)
due_date = start_date + offset_days
```

- 项目 `start_date`、`end_date` 都存在且跨度 >0 时才铺开日期。
- 每个阶段的最后一步标记为里程碑（决策门）。
- 已逾期里程碑：`due_date < 今天 and status != DONE`。

## 4. 运营监控与 KPI

数据来源：[app/api/v1/monitor.py](../app/api/v1/monitor.py)

### 达成率

```text
LOWER_BETTER（越小越好）: target / actual * 100
HIGHER_BETTER（越大越好）: actual / target * 100
```

- 实际值为 0 且方向为 LOWER_BETTER 时，视为 100% 达成（零缺陷/零客诉就是目标）。
- 实际值或目标值为空、目标值为 0 时不计算达成率，显示“—”。
- 达成率可以超过 100%，用于表示超额完成；雷达图和柱状图按 130% 封顶显示，不改变原始数值。

| 指标 | 计算逻辑 | 口径与边界 |
|---|---|---|
| 维度达成率 | 该维度有目标值的 KPI 达成率算术平均 | 没有有效 KPI 的维度标为 WATCH，不参与综合 |
| 综合达成率 | 四个维度达成率的算术平均 | 只统计有数据的维度 |
| 维度状态 | ≥100% GOOD；≥85% WATCH；<85% RISK | 阈值见 `monitor.py` |
| 当前值 | 按 `period` 排序后的最后一个数据点 | 不是最大值/平均值 |
| 环比 | 最新值 − 上一期值 | 少于 2 个数据点时不显示；箭头好坏结合指标方向 |
| 6 个月走势 | 按 `period` 排序的最近 6 个数据点 | 前端画迷你折线 |
| 整体达成率趋势 | 每个月先按维度求平均，再对维度求平均 | 与雷达图同口径，避免指标多的维度权重过大 |
| 未闭环异常 | `status in (OPEN, IN_PROGRESS)` | — |
| 超期异常 | `due_at < now and status in (OPEN, IN_PROGRESS)` | 已解决/已闭环不算超期 |
| 已闭环异常 | `status in (RESOLVED, CLOSED)` | — |
| 异常严重度分布 | 按未闭环异常的 `severity` 计数 | 不含已解决、已闭环 |

### KPI 数据点覆盖规则

同一 KPI、同一 `period`、同一 `project_id` 重复提交时，更新原记录而不是新增。
这样导入/补录不会产生重复月份。

## 5. 流程设计器

数据来源：[app/services/designer.py](../app/services/designer.py)

### 期望值求解

模型按有向图处理，边上 `probability` 表示流转概率。某节点出边概率之和不为 1 时，按相对权重归一化。
期望进入次数 `A[v]` 满足：

```text
A[v] = b[v] + Σ_w A[w] × p(w → v)
```

- `b[v] = 1` 表示入口：显式 START 节点，或没有任何入边的节点（并集）。
- 用值迭代求解，最多 500 次，收敛容差 1e-9；超过 1e6 视为发散。
- 存在无法退出的环路或找不到入口时，`diverged = true`，退回“每个节点各算一次”的线性口径，
  并在建议里明确标注结果不可信。

### 返工

```text
节点期望执行次数 = 期望进入次数 × 1 / (1 - rework_rate)
```

- `rework_rate` 上限按 0.95 处理，避免 1.0 时除零发散。
- 路径级回路（驳回）通过边上概率进入期望进入次数；节点级返工通过倍率进入。
- 两种返工最终汇总到同一套口径，不重复计算。

### 指标

| 指标 | 计算逻辑 | 口径与边界 |
|---|---|---|
| 期望端到端周期 | `Σ(作业时间 + 等待时间) × 返工倍率 × 期望进入次数` | 计入分支、回路与返工 |
| 线性合计周期 | `Σ(作业时间 + 等待时间)` | 旧口径，每节点各算一次；用于对比期望值 |
| 期望作业时间 | `Σ 作业时间 × 返工倍率 × 期望进入次数` | — |
| 期望增值时间 | `Σ 作业时间 × 期望进入次数` | 只算一次通过，返工不计入增值 |
| 期望等待时间 | `Σ 等待时间 × 返工倍率 × 期望进入次数` | — |
| 等待占比 | `期望等待时间 / 期望端到端周期` | 周期为 0 时为 0 |
| 作业时间占比 | `期望作业时间 / 期望端到端周期` | — |
| PCE | `期望增值时间 / 期望端到端周期` | 行业基准 <15% 视为偏低 |
| 返工损失 | `含返工周期 - 不含返工周期` | 含返工含等待；回路与节点返工都计入 |
| 返工额外作业 | `含返工作业 - 不含返工作业` | 用于折算人力 |
| 单次执行成本 | `Σ 单次成本 × 返工倍率 × 期望进入次数` | 与时间同口径，返工重复计成本 |
| 跨泳道移交 | 跨泳道连线数；无连线时按相邻节点的泳道变化计数 | 有连线时以连线为准 |
| 累计审批层级 | `Σ 有效审批层级` | 审批节点未填层级时按 1 层计 |
| 可释放人天/月 | `返工额外作业分钟 × 1000 / 480` | 假设月均 1000 单、每人天 480 分钟；仅计返工作业时间 |

### 瓶颈判定

满足任一条件即标为瓶颈：

1. 节点期望时长 ≥ 可到达节点均值的 1.5 倍；
2. 审批节点有效层级 ≥3；
3. 节点返工率 ≥10%。

不能只用“等待占比高”判瓶颈：等待主导的流程里几乎每个节点等待占比都高，会得出“全是瓶颈”的结论。

### 改善建议规则

| 规则 | 触发条件 | 建议工具 |
|---|---|---|
| LOW_PCE | PCE <15% | BPR 六原则 |
| WAIT_DOMINANT | 等待占比 ≥50% | 产能与排队模型 |
| TOO_MANY_APPROVALS | 累计审批层级 >3 | RACI |
| REWORK_LOSS | 返工损失 >0 | 5 Why |
| MANY_HANDOFFS | 跨泳道移交 >3 | 跨职能泳道图 |
| SERIAL_TO_PARALLEL | 存在可并行的串行 TASK 连线 | To-Be 蓝图 |
| NON_VALUE_ADDED_TASKS | 非增值作业占任务节点 ≥30% | 精益七大浪费 |
| MISSING_OWNER | 有节点未填 `owner_role` | RACI |
| COST_CONCENTRATION | 单节点成本占期望总成本 ≥40% | 加权决策矩阵 |
| BOTTLENECK | 存在瓶颈节点 | 产能与排队模型 |
| NO_ENTRY / DIVERGED / UNREACHABLE_NODES | 模型结构异常 | 泳道图 / To-Be |

### 方法论反推

```text
PCE < 15% 且移交 ≥3        → BPR
返工占作业时间 ≥15%         → 精益
等待占比 >60%              → 精益
PCE < 35%                  → BPI
其余                       → BPI（持续微调）
```

## 6. 对标框架

数据来源：[app/services/benchmark.py](../app/services/benchmark.py)、[app/seed/benchmark_data.py](../app/seed/benchmark_data.py)

| 指标 | 计算逻辑 | 口径与边界 |
|---|---|---|
| 框架分类数 | 该框架下 `benchmark_category` 的数量 | 目前内置 L1/L2 基线 |
| 已映射流程数 | 该框架下映射表里去重后的流程数 | 包含 L3 与继承映射的 L4 |
| 对标覆盖率 | 被覆盖的目标层流程数 ÷ 目标层流程总数 | 默认统计 L3；可按 L1/L2/L3 查询 |
| 分类覆盖数 | 映射到该分类（含所有下级分类）的去重流程数 | 同一个流程映射到多个下级只算一次 |
| 未覆盖流程 | 自身及后代都没有任何该框架映射的目标层流程 | 是框架适用范围的缺口，不一定是数据缺陷 |
| 分类直接映射数 | 直接映射到该分类节点的流程数 | 不包含下级分类 |

### 覆盖的判定

```text
covered(process) = ∃ p ∈ {process ∪ descendants(process)}: mapping(p, framework)
```

- 覆盖率按后代聚合：L1 的覆盖率来自它下面所有 L2/L3/L4 的映射。
- L4 活动默认继承所属 L3 的分类映射；显式映射优先。
- SCOR 只覆盖供应链相关流程，研发、费用报销等会自然落在未覆盖里。

## 8. 时间与日期

- `utcnow()`：数据库时间戳统一使用 naive UTC。
- 出参 `UtcDateTime`：序列化时补 `+00:00`。
- 入参 `UtcDateTimeIn`：带时区的转 UTC 再去时区；不带时区的按 UTC 解释。
- 纯日期字段（KPI 期间、项目起止）不做时区换算，前端不得用 `new Date()` 解析。

## 9. 已知限制

1. 项目“今年结项”按 `end_date` 年份统计，不是实际关单时间；系统没有 `closed_at`。
2. 项目阶段只自动前进，不回退；回退步骤后需要人工调整阶段。
3. 设计器的可释放人天/月基于固定假设（月均 1000 单、480 分钟/人天），不是实际产能。
4. 对标框架只内置 L1/L2 基线；正式对标需要导入授权版本全文。
5. 工具箱匹配是基于关键词与同义词表的启发式打分，不是语义模型。
