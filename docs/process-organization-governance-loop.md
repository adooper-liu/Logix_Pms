## 1. 产品定位：治理不是权限编辑，而是有权、有责、有资源地解决问题

组织治理要共同回答：**谁对端到端结果负责，谁提供资源，谁支持方法能力，谁有权作取舍，冲突和缺口如何解决，决定是否真正执行。**

五个概念不是五个独立目录：

- Owner承担结果和协调，不自动接管部门人员；
- 委员会处理超出Owner授权的重大取舍，不替代经营层法定权力；
- CoE提供标准、工具、数据/方法支持与能力建设，不默认拥有业务收益或否决所有方案；
- 治理模型定义决策、授权、例外和复核规则，不等于软件角色表；
- 跨职能团队交付和执行，部门经理仍负责人员能力、资源和职能义务。

**合力的验收不看角色是否建齐，而看真实问题能否被识别、找到有权负责者、作出可执行决定，并验证客户/流程结果。** 文化表现为共同目标、实际协作、反馈和学习，不以组织图或签到率宣告完成。

## 3. 理想架构：不是理想组织图，而是目标治理运行模型

在原组织/角色/RACI/授权和章程上定义目标职责配置，不预置唯一的委员会人数、CoE编制或所有者头衔。

### 3.1 三个视图分别保留

| 视图 | 表达什么 | 约束 |
|---|---|---|
| 目标治理模型 | 本组织想具备的责任、决策权、资源与服务方式 | 由有权组织批准，适用范围、版本、时间与前提明确 |
| 当前治理事实 | 已任命人员、有效授权、已确认交接/资源、实际决定和结果 | 来源可查，未知不能照目标自动填“已具备” |
| 过渡安排 | 已批准缺口如何分步补齐、临时代理/风险接受 | 有责任、期限、影响/风险与复核；不是为了过门长期保留临时状态 |

不需要先画新治理图；首期用职责/决策表和证据差距对照。将来可视化也必须来自同一原记录，不建立另一棵真实组织树。

### 3.2 五概念的合力契约

| 参与方 | 主要产出/责任 | 决策边界 | 与其他角色交接 |
|---|---|---|---|
| Owner | 流程目标、绩效复盘、改进与跨部门协调 | 在书面授权范围决定；不以系统Owner字段代替资源调度权 | 与部门经理约定投入；与CoE约定方法支持；超权议题交委员会/经营授权方 |
| 委员会 | 架构/优先级/跨流程资源/重大变革决议 | 委员会章程授予的范围；法定、专业红线不能靠多数票越过 | 接收可决策议题，明确决策人/机制、执行责任和复核，不只保存会议纪要 |
| CoE | 方法规范、工具治理、能力建设、项目辅导、知识资产与质量支持 | 业务目标和剩余风险由业务/风险授权方负责；专业阻断须有已批准规则 | 提供服务目录/能力/响应约定；输出可复用标准与辅导结果，方法不足可接外部能力 |
| 部门经理/专业负责人 | 人员技能、资源、职能控制和真实执行支持 | 不以部门局部绩效否定经授权的端到端目标，也不被Owner任意越权指挥 | 确认资源承诺/约束；IT/数据/质量等确认专业依赖、风险和交付 |
| 跨职能团队 | 按共同目标完成分析/设计/实施/采用交付 | 事项有唯一负责者和执行者；RACI不授予系统权限 | 交付到原步骤/标准/模型/培训/样本；冲突有事实、方案和升级规则 |

Owner和Sponsor可以由同一人承担，但不是定义上必然同一身份；创建人、审批人、资源负责人、系统管理员不能仅因账号相同就合并职责。小企业可兼任角色，受职责分离要求的自批须明确规则/批准例外，关键法定控制不可豁免。

### 3.3 目标至少定义的治理对象

流程目录/边界、目标/KPI及口径、模型/规则、数据/集成、标准/培训、资源/岗位、改善投资、变更/上线/回退、运行风险与重大例外。按对象定义：谁提出、谁负责结果、谁执行、谁审批、谁专业核验、谁发布、谁复审/归档，何时升级及生效范围。

同一“事项”须有稳定语义/范围，不只靠自由文本相同就合并；法规/组织/产品不同的适用责任要显式分开。RACI唯一A是必要结构检查，不足以证明有R、A本人有效、授权足够或能力/容量足够。

## 4. 缺口评估与预警：从缺字段到缺治理能力

### 4.1 规则分层

| 检查类型 | 示例 | 判断依据与处理 |
|---|---|---|
| 结构完整性 | 无Owner、完全无RACI、缺A/R、停用角色/人员仍担责 | 对批准的必要对象全集扫描，不只扫已登记RACI；有明确缺项与原对象入口 |
| 授权一致性 | Owner有责任却无相应协调权，代理过期，审批超授权，系统可操作却无业务资格 | 角色/授权/适用期/范围和准入规则核验；高风险写操作实时阻断，不能只等定时告警 |
| 能力与资源 | CoE有名称无可用能力、项目资源未获确认、关键岗位无合格代理 | 原承诺/技能/培训/容量证据；机器可发现缺证，不能代替业务判断“人不行” |
| 时效与执行 | 到期未评审、决议未落实、争议超期、重复临时豁免 | 责任/期限/动作与复核来源明确；提醒/升级去重，按授权处理 |
| 有效性 | 有会议但问题持续复发、跨部门交接长期失约、局部KPI牺牲客户结果 | 运行/绩效/争议证据与独立复核；是待调查线索，不自动给部门或个人评级 |
| 历史/变更 | 人员离职、组织调整、模型改版后职责/批准失配 | 原任命/版本/决定留存，当前责任需交接；不能重写历史以消除冲突 |

### 4.2 当前扫描应收紧的行为

- `invalid_processes()` 主要从已有RACI取流程ID；零RACI流程/缺失事项可能根本不被检查。以目标必要流程/事项全集与当前记录做差集，空集不是治理100%完成。
- A唯一校验当前为服务层查询后写入；并发保障需测试及数据库/事务策略，不能只靠表单拒绝。
- 成员存在不等于成员启用、任期/代理有效、愿意接受职责；当前 add_member 的存在性校验不足以证明治理能力。
- 当前scan会对没再次出现的发现自动RESOLVED。只有来源扫描完整成功且原条件确实消失才可关闭；规则停用/范围变化/无权读取/数据失败应标“未评估/需复核”，不能伪装已整改。
- 当前IGNORED可持续被保留且不提醒。风险接受必须有理由、有权批准者、期限/补偿控制及重新触发条件，不能用永久忽略盖掉高风险治理缺口。
- 当前worker主要运行升级和Outbox，不能宣称治理扫描已自动周期执行。若补扫描调度，需有租约/幂等、任务健康和完整性，失败可见。

依据：`app/services/raci.py:289`、`:153`、`app/services/governance.py:470`、`:517`、`scripts/worker.py:34`。

### 4.3 每条预警必须可行动

保留 GovernanceFinding 为发现索引，明确：事实/规则依据、对象与版本/组织范围、风险影响、首次/最近发现、责任/期限、原处置记录、升级对象、当前核验和关闭依据。缺字段只补原发现/业务记录，不为每种扫描另造任务。

显示“缺口已发现”“待分派”“待补证”“协商中”“待裁决”“待验证”“已核验”时，应从原事实/处置引用派生，不将这些标签硬塞成新的项目阶段。发现消失不等于组织行为已改善，效果仍按问题风险核验。

## 5. 现实冲突协调：不是发现两个A就找管理员删一个

典型冲突包括：结果责任与资源权力分离、跨流程预算/产能竞争、总部标准与本地约束、客户时效与风险控制、数据所有权与使用需求、局部考核与端到端结果、CoE方法规范与业务时效。

推荐处理链：**登记原议题 → 澄清事实/授权与约束 → 相关方协商备选 → 在权限内决定或升级 → 执行原动作 → 核验结果 → 复盘修订治理安排。**

| 环节 | 必须留下什么 | 不允许的捷径 |
|---|---|---|
| 澄清 | 涉及流程/事项、客户结果、各方诉求、原授权和证据、影响/紧急度 | 未调查就判“部门不配合”或改权限掩盖 |
| 协商 | 可选安排、资源/控制/客户代价、各方反馈、未决点与协调人 | 把“沟通完成”当达成共识；强迫删除合理异议 |
| 决定/升级 | 授权范围、谁有最终决定权、为何需升级、期限；正常/紧急规则、回避和记录 | 系统管理员/CoE自动代替业务裁决；多数票取消法定义务 |
| 执行 | 原资源、授权、模型/规则/标准/项目动作，责任与期限 | 只有纪要，无实际更改；给双方复制平行任务 |
| 验证 | 决定是否落实、端到端效果/副作用、接受者和下一复核 | 把更换A或关闭发现当协作问题已解决 |

没有共识也可以有可追溯的有权决定，不能逼系统把“已决定”显示成“全体同意”。临时安排应有范围、失效/复核和业务连续性规则；支持复议，但保存原决定，不能不断重开同一议题逃避执行。

重大安全/合规事件先依已有应急授权止损，再补完整治理处理；一般争议避免上来就开委员会，把委员会留给超出Owner授权的跨流程取舍。

### 示例：O2C时效与财务风险

销售希望加速信用放行，财务担心坏账，Owner承担周期却不直接管理财务人员。先核对客户承诺、风险数据、规则、岗位能力和授权；比较分级放行/补资料/临时资源/调整承诺等方案。Owner协调权限内事项，超信用政策或资源边界交有权经营/风险方；委员会按章程协调，但不能非法放弃控制。决定后更新原授权/规则/岗位/培训并用同口径样本复核周期、坏账/差错与客户结果。不是在系统里给Owner一个ADMIN角色就解决。

## 6. 组织与文化的小闭环

G0–G6为作业指引，不另加阶段状态机：

1. **定义目标治理**：按客户/战略与风险确定必要对象、角色/决策权和CoE模式，明确批准来源。
2. **核实当前事实**：原人员/组织、任命授权、RACI、资源/能力、历史决定和结果；未知单列。
3. **评估差距**：结构、授权、能力、执行和结果，输出可解释发现和风险，不用任意总分。
4. **协调过渡**：相关方确认资源/职责；冲突协商/升级，批准临时范围和时限。
5. **落实原动作**：任命/代理、授权、规范、培训/辅导、资源、变更与实际协作。
6. **验证运行**：责任是否有人承担、决定是否落地、问题是否减少、客户结果/控制是否有效。
7. **复盘再调整**：目标/组织/版本变化触发复评，保留历史；项目可结项，流程治理继续。

20项保障视图引用这些原记录，不能自动生成20个新工作项。对文化的判断基于可观察协作行为和结果，禁止以员工主观“支持度”评分自动决定访问权、奖金或晋升。

## 7. 界面如何呈现“合力”

保留 orgs 的人员/岗位/角色维护、authorization 的贯穿治理入口、designer 的原RACI、deliverables 的扫描发现。增加聚合/下钻能力而非另建治理主模块：

| 现有位置 | 推荐增加的内容 | 原记录操作 |
|---|---|---|
| orgs治理页签 | “目标职责 / 当前任命与授权 / 缺口”对照；成员有效性、代理、CoE支持范围 | 维护角色/成员/任命，查原章程与授权；不自动授系统权 |
| authorization | 权力边界、例外及跨职能议题关联；当前谁有权决定、何时升级 | 原授权/例外办理；指回争议来源 |
| 流程卡 | “治理保障”摘要：Owner授权/责任、跨部门关系、开放缺口、待决定事项 | 打开原RACI、章程、培训、项目步骤/例外/发现 |
| 治理发现 | 规则事实、风险、责任/期限、原处置、复核/升级和接受期限 | 核验、申请有期限风险接受、按原事项协商/决策 |
| projects/workflow | 本轮跨职能参与/资源承诺、受阻/需决策及接收 | ProjectStep原决策/阻断字段和签收，不新建团队任务平台 |
| dashboard | 需行动的治理风险、超期决议/复核和关键责任缺口 | 按范围下钻原对象；不将角色数量当治理成熟度 |

短文案：“已任命，不代表授权已确认”“本事项尚无有效负责者”“资源承诺待接收方确认”“争议超出当前授权，待提交有权方决定”“已记录决定，执行效果待验证”“目标治理要求未满足；查看差距依据”。

信息结构固定：**治理对象/目标—当前事实—缺口或冲突—责任/授权—下一步—核验依据**。未核实不显示已具备；小企业角色兼任可解释，不能把推荐参考图当必须组织调整。

## 8. 原数据与工程边界

- OrgUnit/Position/User为真实组织主数据；目标治理方案用原受控章程/标准/模板和版本化引用描述，不以目标岗位写回真实组织。
- GovernanceRole/Member、ProcessCharter、RaciAssignment、AuthorizationRule/Exception补适用范围、责任接受、授权/代理有效期、核验等必要字段；不在多处独立编辑同一Owner/权限。
- ProjectStep已有受阻/待决/接收字段；项目内争议用其原记录。非项目议题优先引用原GovernanceFinding/授权例外/变更，按需要补责任、期限、协商/决定/复核引用，不伪造项目。
- 委员会章程、会议决议/CoE服务约定可先作为原版本化文件和结构化模板产物，再引用有权决定；缺少必要载体时先明确原对象增量，不提前建设完整会议/OA系统。
- 缺口规则用同一服务评估，前端只展示来源和原因；原扫描/人工核验分别注明。读GET不隐式执行整改或更新组织。
- 权限要区分系统操作准入、对象可见范围、业务授权和专业审核资格；RACI的A、治理角色成员或ADMIN任一身份均不能单独推导全部决策权。
- 并发唯一A、任免/代理交接、风险接受/关闭、组织变更历史和聚合可见性须测试。数据库改动走Alembic，不能靠UI禁用兜底。

## 9. 建议顺序与验收

1. 先选一条真实跨职能流程和若干关键治理事项，批准目标职责/决策表，而非先画完整组织大图。
2. 对照原记录识别真实责任/授权/资源/能力差距，修正零配置漏检与成员有效性等基础检查。
3. 用一个真实冲突走完澄清—协商—有权决定—执行—效果核验，验证Owner/部门/委员会/CoE配合。
4. 完善风险相称的预警、期限、升级、过渡/接受和复评，避免重复轰炸或永久忽略。
5. 确认运行有效后复用到其他流程，目标模型仍可因业务/组织变化调整，不当静态蓝图。

后续验收至少覆盖：完全无RACI/缺必要事项、A存在但无人/停用/失授权、并发写A、资源未确认、CoE有角色无能力、代理过期/组织变更、扫描失败不自动解决、风险接受到期、无权限泄露/自批、不同意见保留、紧急/普通升级、执行未验证不可当冲突解决，以及项目结项后流程治理持续。

代表位置：`models/raci.py`、`org.py`、`governance.py`、`authorization.py`、`services/raci.py`、`governance.py`、`maturity.py`、原项目/授权/扫描API、orgs/process_card/dashboard及帮助。测试沿原 `test_governance.py`、`test_raci.py`、`test_governance_audit.py`、`test_authorization.py`、`test_user_admin.py`、`test_workflow_workbench.py`扩展；后端pytest、前端verify_frontend、schema Alembic一致性及真实组织试点分开验收。本次均未执行。

**治理有效的最低证据不是五个概念都能编辑，而是责任与权力相称、专业支持和资源可兑现，发现与冲突有规则可处理，决定在真实业务里执行且结果可复核。理想架构是方向，现实证据与过渡机制让它能够活下去。**
