# BPM 技术：双向开放、能力接入与可替换演进

> 状态：待评审规格；基线 `ca20f88`，静态核对，未进行实际集成验收。
> 综合评审契约：[产品基本原则](bpm-product-principles.md)。本文负责双向交换/能力边界，受控输出不等于公开数据；非引擎集成不预设供应商，Flowable执行方向已选但尚未接入。
> 衔接：[总规格](bpm-lifecycle-implementation-spec.md)、[模型仓库](process-modeling-repository-gap.md)、[转型实践](process-transformation-practice-system.md)。
> 本次不实施接口、不连接外部服务、不发送业务资料。Flowable执行方向已采纳，其他外部能力不预设供应商；开放不绕过权限、业务审核与数据治理。

## 1. 产品原则

**Logix PMS 应是可连接、可交接、可退出的流程管理节点，不是把流程资产和运行数据锁在内部的封闭应用。**

开放包括四个方向：

1. 产物向外输出：模型、规则、数据定义、指标、样本与验收结果有明确的交换契约。
2. 外部数据向内输入：接收来自业务系统、设备、人工和专业工具的事实，保留来源并核验。
3. 外部能力受控调用：统计、仿真、挖掘、RPA、规则、预测/智能服务可以接入，但不取得未经授权的业务决策权。
4. 组件可替换：引擎、连接器、存储、分析/智能提供者升级或退出时，资产、历史和原业务语义仍可解释。

开放不等于所有数据公开、不等于允许任意插件执行，更不等于每项能力都必须自研。技术服务于客户价值与可靠运营，“不自动化”也是合法选择。

## 3. 输出什么：不仅输出图，还要输出可解释资产

| 产物 | 推荐交换内容 | 接收方可做什么 / 边界 |
|---|---|---|
| 公司流程目录 | 编码、稳定标识、类型/层级、关系、Owner适用范围及版本说明 | 建立外部引用，不复制另一棵竞争的公司主树 |
| 模型 | 指定 ProcessModelVersion 的 BPMN XML、扩展说明、哈希、用途与能力限制 | 外部建模/归档/运行适配；BPMN标准不保证各引擎扩展等效 |
| 规则/表单/数据定义 | 类型化字段、条件/默认、版本、来源、授权和枚举语义 | 外部映射和校验；未有标准转换就不把自有JSON冒称DMN等标准格式 |
| 标准/方法/交付物 | 原文件与版本、来源/许可、适用性、正文哈希、引用和审核摘要 | 培训、协作、复制；外部存储不是新的标准权威源 |
| 样本与指标 | 原事实/获准聚合、口径快照、模型/范围/窗口、质量及排除 | BI、统计、仿真、挖掘；先脱敏和最小化，不默认导出全部员工/客户数据 |
| 分析/设计/验收 | 原记录引用、输入版本、假设/方法、结果、审核/未决/限制 | 专家或外部工具继续工作；“收到结果”不等于本地审批通过 |
| 运行记录 | 实例/活动/任务/事件及业务关联、实际模型身份和时间 | 跟踪/对账/挖掘；日志缺失和并发不明须保留限制 |

**当前发布身份仍是已发布 ProcessModelVersion 行。** 不为交换先建部署表；Flowable 接入后再提供引擎部署/定义与该行的映射。正式改善交换带 round_id 及四身份，日常运行不强制项目。

### 3.1 交换清单（manifest）

交换包是原资产的带版本清单，不新建资产主库。至少标明：contract_version、导出范围/时间、资产类型、source_system、稳定外部键与本地映射、process_id/项目及轮次（适用时）、model_version_id、口径哈希、版本/依赖/来源、文件哈希、格式、许可/保密分级和已完成校验。

- 跨环境的本地整数ID只作来源说明，不能直接当目标库主键；按来源命名空间+稳定键显式映射。
- 需要离线独立使用时附获准的依赖文件；受控在线交接可给有期限授权链接。不能把数据库内部路径/长期Bearer令牌塞进清单。
- 大范围输出分页/分块，绑定一致快照或游标规则；删除/停用和字段脱敏明确，不能导一半版本后称一致快照。
- 哈希证明内容一致，不单独证明来源可信；正式跨组织交换可按批准策略附签名/来源验证。

## 4. 输入什么：先接收核验，再决定生效

外部输入包括新事实、外部资产、专业计算结果、执行命令/回执，四种输入不能共用一个“上传后立即生效”的动作。

统一作业链：**确认用途/权限 → 映射并预览 → 安全与语义校验 → 确认来源/版本/质量 → 保存接收记录 → 审核或受控执行 → 回执/对账 → 效果复核。**

- 资产导入形成草稿或新修订，不覆盖已批准模型/标准，不自动发布。
- 业务事实保留source/事件或批次/业务键、occurred_at与received_at、字段映射和质量；未知记录隔离待核，不填零或偷偷丢弃。
- 外部分析/AI结果保存输入版本、提供者/方法版本、假设、证据和限制；只能提出建议或草稿，正式改变调用原业务授权服务。
- 外部完成回执分别说明执行成功、外部业务结果和本地确认。传输2xx/机器人运行状态不是付款/收货/审批真实完成证明。
- 批量操作预览新增/复用/冲突/拒绝，确认写入；重复接收有稳定幂等键和内容哈希，相同ID不同内容返回冲突而非复用旧结果。
- 未知字段/枚举和不支持构造不静默丢弃语义；兼容策略按契约版本决定保存扩展、拒绝或显式降级。

## 5. 四条技术通道，避免只依赖某一种新技术

| 通道 | 面向场景 | 契约底线 |
|---|---|---|
| 文件/批量交换 | 传统系统、离线环境、专家/统计工具、长期归档 | CSV/JSON/Office及BPMN等明确格式、编码/日期/单位、清单/哈希、映射预览与回执；具体格式按需验证，不宣称现已全支持 |
| 同步API | 查询、小范围命令、业务操作 | 稳定schema、身份/对象范围、expected_version、幂等与结构化错误、分页/限流；超时未知需核对原操作 |
| 异步事件/任务 | 长时计算、集成通知、RPA/引擎/设备回执 | 先持久接收、event/job/command ID、契约版本、去重/重试/乱序/取消/对账，不承诺跨系统exactly-once |
| 能力适配器 | Flowable、统计/仿真/挖掘、OCR/AI或未来工具 | 类型化输入/输出、可用能力、版本、受限权限、资源/超时预算、验证/停用和替换；不开放任意脚本或任意URL执行 |

未来可能接消息总线、行业接口或面向智能工具的协议，但协议只能新增适配器，不成为业务模型/审批的权威来源；采用前另行核查协议版本、授权、许可证和安全。现在先建立契约，不以“面向未来”为理由建设万能插件市场或并行事件平台。

## 6. 可靠开放：传输、执行和业务结果分开

建议事件外壳按需演进为：contract_version、event_id、source/type、occurred_at/produced_at、subject、process/model/round引用、business_key、correlation_id/causation_id、payload及schema引用。投递attempt/delivery ID另记，重试不改变事件事实身份。只在确需顺序时定义聚合序号，不用接收时间猜全局因果。

- 先快照+增量时，明确快照水位、重叠去重、迟到/补数、删除和重新同步；历史重放不重复触发付款/通知等副作用。
- 幂等键作用域含来源/动作/对象，重放前仍核验授权；同键不同哈希409。外部业务幂等由双方约定，不能只用PMS投递ID覆盖对方业务重建。
- 异步显示“已接收/处理中/结果待确认/已完成/已拒绝”，完成的含义和证据由能力定义。超时查询原operation，不换新ID盲重试。
- 退避、限额、超时、熔断/停用、积压、人工处理和对账有Owner；恢复后怎样补齐明示。当前三次重试只是策略，不证明业务可靠性已充分。
- 服务/契约版本兼容测试、弃用窗口、变更通知及导出退出方案，避免新版本悄悄改变旧消费者语义。
- 当前UTC/日期规范持续遵守，时间字段只一个明确偏移，不重复拼接Z；定义事件发生与投递时间，统计不用发送时间代替业务发生时间。

## 7. RPA、挖掘与AI如何开放而不越界

### 7.1 RPA：外部执行器，不是业务权威

优先使用稳定业务API；确需GUI自动化时，声明输入、目标应用/版本、凭据作用域、运行ID、重试/恢复、业务确认与人工接管。UI成功、截图或机器人“成功”不能独立证明ERP业务已正确提交，需回读业务结果/对账。

高频/稳定/明确规则是适用信号，不是唯一标准；PDF发票可能需要OCR/文档识别+审核+ERP接口，不能自动归为纯RPA。非结构化或判断任务可组合辅助技术，但不因此取消授权/验证。

### 7.2 流程挖掘：日志证据，不是全部真相

外部工具可接收获准事件数据，并回传发现模型、偏离/性能线索和方法参数；它们是待验证分析结果，不能直接覆盖公司标准模型或裁定违规。

至少核查case/object键、活动与生命周期、时钟/时区、重复/缺失、并发、数据覆盖及模型版本。跨订单/物料/发运等多对象关系不可随意压成一个case导致假路径。访谈/现场观察仍用于解释未记录活动、业务例外和授权；不能宣传“不需要访谈，日志即真相”。

### 7.3 AI/预测：建议与授权执行分开

本次不选择模型提供者、不接SDK、不发资料、不调用付费服务。当前教练为规则式建议。未来能力至少定义：输入许可/脱敏、模型/提示/检索来源版本、任务与结构化输出、质量/误判/群组表现、成本/延迟、人工复核、监控漂移及停用回退。

外部文本/附件/模型输出都视为不可信内容，不能把其中指令当操作授权。结构校验通过不等于业务判断正确。读知识/生成草稿与审批/发布/付款/改权限等动作分权；高风险操作需有权确认、字段白名单和业务服务再次校验，禁止直接给模型数据库管理员凭据。

预测超时要说明观察时点、训练/验证窗口、标签泄漏防范、预测误差和人如何响应；情绪识别不可凭主观标签自动惩罚员工或拒绝客户服务。不同提供者更换需重新验证，不能因接口形状相同就认为输出等效。

## 8. 安全与治理是开放边界，不是附加项

- 专用机器身份、最小动作/流程/组织/字段授权，密钥轮换/撤销；不把MANAGER/ADMIN服务账号当永久万能入口。原HMAC基础可复用，细粒度服务身份分期升级。
- 入站每种动作都校验对象范围、参数哈希、版本和权限；KPI/工时/任务不得因共享钩子越界。
- 出站明确目的、数据最小化、跨法人/地域、保留/删除和可审计访问；对外发送业务数据需获准，不能以“测试连通”夹带真实客户样本。
- 出口域名/IP/协议/端口和重定向策略受控，防SSRF/元数据地址/凭据泄露；允许企业内网是经批准白名单，不是全部开放。
- 文件/XML/压缩包隔离、安全解析、大小/深度/解压限额、内容检测与敏感信息控制；扩展名/魔数检查不是完整恶意文件防护。
- 操作审计记录原业务操作者、服务身份、批准范围、输入/输出引用和结果；技术日志去敏，不重复存完整秘密或敏感文档。
- 撤销集成要能停新调用、处理在途、保留历史、导出资料及验证新组件接管，不能拔掉一个连接器就遗失业务。

## 9. 技术接入也要有小闭环

| 工作 | 必须完成 | 验收产物 |
|---|---|---|
| 明确需求 | 解决哪个客户/流程问题，为什么现有能力不足 | 价值与风险/替代方案，包括不接入 |
| 定义契约 | 输入/输出、身份/版本、数据与能力边界 | 原DataFlow/集成配置、模板/接口说明的受控修订 |
| 映射与验证 | 沙箱样本、正常/错误/边界、权限和语义 | 可复现测试与限制，不以ping/HTTP200验收 |
| 受控启用 | 批准范围、实际账号、监控、负责人和恢复 | 原发布/变更/运行证据；R3前不伪造部署表 |
| 运行对账 | 送达/执行/业务结果、延迟/失败/质量核对 | 原投递/回执/异常及修复证据 |
| 效果与退出 | 真实价值、风险/成本、升级/替换/停用 | 业务验收、兼容与退出/恢复演练 |

## 10. 五个练习场景的正确接法

| 场景 | 推荐能力组合 | 进入生产前必须回答 |
|---|---|---|
| PDF发票录ERP | 文档解析/OCR或结构化提取+校验/人工复核+ERP API；无API时再评估RPA | 字段准确、税额/重复发票、敏感信息、授权和入账确认，不以提取文本即完成 |
| 采购绕审批 | 事件采集/业务关联+挖掘/一致性检查+规则/例外核验 | 日志覆盖、标准版本和合法例外，不把不一致直接判违规 |
| 跨部门端到端审批 | BPM编排/规则/表单+业务系统连接；Flowable依R3验证 | 并行/会签/时限、身份、在途/失败、原系统权威归属 |
| 客服情绪升级 | 内容识别辅助+业务规则/人工复核+任务路由 | 误判、语种/群组、隐私、渠道和客户权益，模型不自行取得审批权 |
| 订单延迟预测 | 可追溯历史+预测服务+告警/管理决策 | 数据足够、预测发生在结果前、质量/误报、谁响应及行动后是否有效 |

答案可以是组合，也可以暂不采用新技术；技术成熟度不能由讲义“已可用/前沿”的标签替代本组织验证。CBOK/Competency Model版本与考试分级的讲义引文本次未核，不贴官方认证或据其决定产品范围。

## 11. 现有模块落点与分批交付

| 范围 | 原位置与增量 | 禁止的捷径 |
|---|---|---|
| 产物可移交 | 原designer版本导出、文件/模板/交付物、模型仓库/轮次对照 | 默认导最新；丢扩展后重建；输出不带语义/许可 |
| 接收与来源 | 原inbound/schema、DataFlow、导入/预览及原审核 | 导入即覆盖/发布；钩子启用即数据有效 |
| 能力调用 | 原IntegrationEndpoint/Delivery与受控适配服务、后台worker | 万能任意脚本/URL；外部结果直接写正式结论 |
| 可观测与可靠性 | 原投递/入站/审计/异常，按需扩schema版本、哈希和状态 | 技术送达等于业务完成；超时换ID盲重试 |
| 用户交互 | 原 execution→集成、data、资产版本页及相关模块帮助 | 新加独立万能“技术平台”主导航；普通用户看密钥/堆栈 |
| 引擎替换 | R3按已确认Flowable方向，原API适配与模型映射 | 当前先建部署台账；PMS与引擎同时算下一步 |

建议顺序：先形成最小“指定版本产物→外部受控使用→结果回传→本地核验”的闭合样例；再补可靠API/事件契约与对账；随后按真实需求增加专业连接器；最后验证组件替换和完整退出。数据安全、权限和恢复贯穿，不能最后补。

不把本稿视为立即建新实体清单；原模型可承载就扩字段/契约。长时任务等确需持久作业设施时另列计划和迁移，不能为了所有未来协议提前造架构。
