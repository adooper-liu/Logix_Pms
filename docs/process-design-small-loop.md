## 1. 结论：当前有设计工具，但未形成可证明有效的设计交付

项目已有 To-Be 建模、模型差异、测算/路径模拟、设计原则和 FMEA/决策矩阵模板、战略/KPI 关联、RACI、授权、变更影响及项目阶段门。缺口不在于“能否画未来图”，而在于这些信息尚未共同回答：

- 方案为什么能解决已经核实的问题，并交付客户需要的结果？
- 采用某原则/模式的前提是否成立，是否引入了新约束？
- 预测用了什么输入与方法，覆盖哪些正常、边界和失败场景？
- 控制是否仍足够，风险由谁接受？
- 谁按何标准接收这份设计，可以交什么、还不能交什么？

**设计有效的最小闭环**：承接分析 → 明确设计依据 → 形成备选 → 将原则落实为设计决定 → 建模并配置 → 验证效果与风险 → 比较取舍 → 评审接收；不通过则回到相关决定修订。

这是作业闭环，不是新状态机。设计获接收只表示具备进入试点/上线准备的设计输入，不能自动显示“上线就绪、运行有效、改善达标”。

## 3. 四组概念：既指导作业，也提供评价依据

### 3.1 设计原则与模式：从口号到可核对的设计决定

原则回答“为什么这样组织工作”；模式回答“具体改变哪种机制”。每项重要设计决定应形成以下结构化记录：

**问题/根因引用 → 原则/模式及适用理由 → 修改前后元素/规则 → 预期客户/KPI 作用机制 → 前提/依赖 → 风险和控制 → 验证办法 → 结论。**

例如“采用并行化”不足以验收。需说明两个活动输入是否独立、是否争用同一资源、是否必须同步、失败/取消怎样处理；验证这些前提后才有资格预测周期改善。

#### 七原则如何检查

| 原则 | 设计动作 | 可评价证据与反向检查 |
|---|---|---|
| 围绕结果组织 | 明确客户结果、减少断裂交接，必要时建立端到端责任 | 最终交付和接收条件完整；减少节点没有丢掉必要工作或转嫁客户 |
| 让产出使用者执行 | 减少转录/中介，授权能直接完成的人 | 使用者具备数据、权限、能力；不是把内部工作免费转给客户 |
| 信息处理并入实际工作 | 在产生/处理业务时校验和记录 | 数据来源、责任和校验点明确；不能取消独立性必要的复核 |
| 分散资源视同集中 | 共享服务、统一规则或可调度资源 | 服务时区/容量、数据权限、属地法规和故障保障可行；集中不自动更优 |
| 连接并行活动 | 提前协同、共享中间信息并正确汇合 | 输入依赖、同步/版本、失败影响可解释；不是简单画一个加号 |
| 决策放在执行处 | 明确分级授权、规则和升级 | 能力/权限匹配，保留职责分离、例外和证据；不是取消所有审批 |
| 源头一次捕获 | 指定权威数据源、复用传递，避免重复输入 | 更新/纠错/同步/主键明确；一次捕获不等于不再验证真实性 |

本专项拟以七原则修订统一设计检查清单，原则来源/适用性待批准；不另建BPR7与BPR6平行工具。BPR6原code及历史六原则模板保持，新增有效模板修订，不追认历史通过。ECRS是另一种简化思考法，可作为关联方法选用，不能混称或替代BPR原则。

#### 六种模式如何使用和验收

| 模式 | 采用前需证明 | 设计后需验证 |
|---|---|---|
| 并行化 | 无不可拆先后依赖，资源/控制允许 | 汇合、共享状态、取消/失败、资源竞争、端到端周期 |
| 合并/消除 | 原活动确为冗余，或有等效替代控制 | 输出/质量/法定职责不丢失，工作未隐形转移 |
| 自动化 | 规则、输入质量、接口及授权明确 | 异常/人工接管、重复/重试、留痕、准确性和恢复 |
| 标准化 | 共性与必要变体已分清 | 标准路径覆盖、例外处理；不以禁止合理例外制造绕行 |
| 分流/分级 | 分流字段可靠，复杂度/风险分类有依据 | 阈值边界、缺值/错分、升级、防拆单或误导分类 |
| 自助服务 | 用户有能力、渠道可及且愿意使用 | 真正完成率、求助/退出、无障碍、客户负担与满意度 |

“至少用三种模式”只适用于讲义演练约束，不成为生产门禁。实际方案应有充分理由选用/不选用，不能为了数量把流程改复杂。

### 3.2 模拟验证：验证设计假设，不制造精确幻觉

按问题选择合适验证，至少区分：

| 方法 | 可以回答 | 不能据此宣称 |
|---|---|---|
| 业务场景走查/桌面演练 | 正常、异常、边界、角色和控制是否说得通 | 已证明真实效率/吞吐 |
| 逻辑/路径/执行用例 | 条件、分支、汇合、失败和终止是否符合预期 | 已模拟资源竞争、排队与人员可用性 |
| 静态期望值/路径枚举 | 在给定参数和支持结构下的预计时间/成本 | 真实分布、排队时长、峰值产能、概率保证 |
| Monte Carlo | 在声明分布/依赖假设下的不确定性与敏感性 | 如果没有排队/资源竞争模型，不能据此断言系统容量 |
| 离散事件仿真/外部专业工具 | 按经过验证的到达、资源、日历、技能、路由模型评估负荷/队列 | 模型自身正确或上生产必然达到预测值 |
| 试点/受控实测 | 指定范围和窗口内的实际运行结果 | 未测试业务群组或规模下也必然成立 |

每份结果钉住模型版本、参数、数据来源、方法/算法版本、假设、测试范围、场景、输出及限制。随机方法附种子、重复次数、预热/运行窗口（适用时）和不确定区间；不能把估算标实测。

当前路径枚举遇回路会截断、只返回部分路径，期望结果是所返回路径的归一化汇总；**不能拿它当完整图测算或离散事件仿真**。界面需显式显示覆盖/截断和“暂不可用于该项结论”；未经验证的并行资源场景不给精确收益数。不要在仿真模块另写一套与现有图测算冲突的返工算法。

验证适用性允许裁剪：简单改名称无需做大型仿真；涉及并行、峰值容量或重大风险，不可只用流程图走查替代必要验证。方法是否足够由批准的任务风险与验收规则决定，不一刀切要求每个方案都仿真。

### 3.3 合规与控制：控制设计必须能落到行为和证据

控制记录至少包含：风险/失效模式、制度或法规来源及版本、预防/检测/纠正类型、对应活动/规则、责任及职责分离、输入/触发、正常与例外动作、留证、验证用例、剩余风险和有权接受者。

- 预防：例如授权/完整性检查，需测试正常、拒绝、越权和绕过。
- 检测：例如对账/抽样，需明确频率、覆盖、独立性、发现后的责任与时限。
- 纠正：例如退款/退回/补偿，需明确可逆性、授权、失败重试和业务结果核对。

“刚好够”不是控制越少越好；“可自动化”不是任何控制都必须自动化。法定检查、重大风险或职责分离属于硬约束；加权高分不能抵消红线。审批改事后抽检是否等效，须有风险依据和有权审批，不将讲义案例当成默认建议自动应用。

FMEA 用来组织风险，不把 RPN 当唯一准入：严重度红线、法律义务和重要但低频风险仍须独立处理。评分需有组织尺度与来源，不能用几个主观分数宣告已合规。

### 3.4 战略与客户价值：关联目标只是起点

每个方案至少说明：目标引用、客户/内部接收结果、相关 KPI 和冻结口径、预计影响机制、证据、风险/负向结果、后续验证方式。

策略目标、成本、体验和质量的方向可能冲突。设计方必须呈现取舍，有权方决定接受/修订，不默认“审批减少就是战略对齐”。例如更快首响不等于更快解决，更少内部操作也可能增加客户填写和追问负担。

目标验证以端到端结果为主；阶段效率指标作为解释，不以局部最优代替最终交付。不自定“周期缩短 30%”等收益目标，也不能看过预测后修改评价权重去支持偏好方案。

## 4. 小闭环作业链：输入、动作、产出、反馈

D0–D6 是工作指引，不新增数据库阶段。八阶段“设计”仍打开同一 designer 的方案模式；项目内方案工作继续在五阶段第 3 阶段办理。

| 指引 | 输入 / 问题 | 具体作业 | 产出 / 确认 | 不通过回到哪里 |
|---|---|---|---|---|
| D0 接收分析 | 客户差距、As-Is、样本基线、根因/反证、未决项 | 核对分析交付是否足够设计；明确边界/红线/责任和验收目标 | 设计任务约定及引用；缺证不装作已知 | 分析补证或缩小设计范围 |
| D1 确定评价依据 | 战略目标、风险、资源与客户约束 | 先定硬约束、比较指标/权重、需要的验证及接收人 | 事先固定的评价/验收约定；引用薄轮次对照 | D0/授权方决策 |
| D2 形成备选 | 经核实的根因和设计依据 | 依原则/模式提出备选，保留不改/小改/重构等真实可行选项；复杂度按任务裁剪 | 备选方案及决定记录、预期机制/依赖；不靠工具数量证明质量 | D0/D1 补事实与约束 |
| D3 具体化方案 | 备选决定 | 在原画布建 To-Be；同步规则、数据、RACI、控制和异常；固定版本与差异 | 可核验方案模型及相关原资产引用 | D2 修订设计决定 |
| D4 验证与反证 | 固定方案、输入数据、验证计划 | 结构/语义、场景、控制、测算/仿真/敏感性验证；保留失败与限制 | 版本绑定的验证结果及风险/未知 | D2/D3；假设被推翻则回分析 |
| D5 比较并选择 | 各方案同口径结果 | 先筛硬约束，再比较价值/投入/风险，说明选择和拒绝理由 | 选定方案、批准取舍、保留条件和未决责任 | D1 修订约定须留痕；D2–D4 改方案 |
| D6 评审交付 | 选定版本与全部依据 | 业务/IT/风险/执行接收方按用途核验，明确可交范围和残留问题 | 可交试点/上线准备，或退回/补证/停止；接收决定绑定版本 | 受影响的前项，不抹去原审核记录 |

作业可迭代并行，不能为了形式逼每个简单任务做多份方案；若只比较一个实施方案，须说明为何其他选项不适用并保留不改现状的基准。设计准备不强制先开项目，正式本轮改善验收按已锁定项目/轮次关联。

## 5. 一项设计决定的最小贯通实例

问题证据：小额采购与高风险采购走相同审批，等待集中在审批交接（仅作为待实测示例）。

1. 原则：围绕客户结果/执行层决策；模式：按风险分流，必要部分自动化。
2. 改动：低风险标准目录采购走批准额度内路径，异常/高风险进入原有或专门审查；不是只按金额一刀切。
3. 前提：目录、预算、授权、供应商和数据可靠；阈值/币种、拆单风险和异常定义有权批准。
4. 控制：事前额度/权限校验、检测性抽查/对账、纠正性冻结/退回/补偿，分别有责任和证据。
5. 验证：临界值、缺字段、超额度、重复、供应商异常、接口失败、取消/回退；估算不同业务混合和峰值负荷。
6. 评价：周期可能下降，但错误采购/合规/客户体验不得突破红线；预测不足时只批准受控试点，不宣告达标。
7. 交付：模型、规则和控制版本、测试结果、资源与培训要求、回退及观察口径一并接收。

因此“14 天变 3 天”不能由删除几个节点推导；题设 14 天不是全部活动参数，缺到达/资源/活动/风险数据时只能写假设范围，不能报实测收益。

## 6. 设计能交付的标准

### 6.1 五道质量检查，不能互相抵消

| 检查 | 最低问题 | 不成立时 |
|---|---|---|
| 技术正确 | 模型结构/语义符合标准及所选用途，版本可还原？ | 不能作为合格模型交付；修图不等于修业务 |
| 业务有效 | 对客户结果及已验证问题有合理、可检验的改善机制？ | 回方案或分析，不因符合 BPMN 通过 |
| 风险可接受 | 控制、授权、职责分离、例外及证据满足硬约束？ | 硬阻断或有权风险决定，不能用效率高分抵消 |
| 实施可行 | 系统/数据/资源/岗位/培训依赖、支持范围与回退可落实？ | 可限定为概念设计；不能称可试点/可上线 |
| 验证充分 | 用途相关验证通过，假设/样本/限制明确且接收方认可？ | 补证、缩小范围或受限试点，不冒充已证效 |

### 6.2 设计交付包是引用集合

- 分析接收、客户目标、根因和冻结基线；
- 原则/模式→决定→变更前后元素/规则→预期结果的对应；
- 备选、取舍及事先约定的评价标准；
- To-Be 精确模型版本、变更差异及规则/数据/角色/控制引用；
- 验证场景、输入、结果、失败与限制；
- 实施依赖、资源、培训、回退、观察与后续验收约定；
- 谁接收哪一版、通过/退回/受限范围/停止及依据。

这些继续留在原项目/步骤/方法记录/变更/授权/模型及薄对照，不新增设计项目、方案主库或本轮发布台账。正式项目方案核对process/project、现状/所选方案版本及比较口径；上线版本在真实发布后追加，不成为设计开始/交付的前置条件。后侧正式观察前固定验收目标/红线，不能见结果后修改。

设计接受不自动等于上线就绪：后者至少还需已发布模型和上线条件；实际运行有效及改善达标必须以后按同一冻结口径取真实样本验收。评审通过只冻结该版及用途，模型/规则变化后要复核受影响结论。

## 7. 理论与界面如何互相作用

保留设计入口和原画布，在同一 designer 的方案模式提供四个工作区（或同层页签），不增加顶级导航：

1. **设计依据**：客户目标、已接收分析、根因、范围与硬约束；缺项指回原记录。
2. **方案与决定**：模型/规则差异旁显示适用原则、模式、前提和预期机制；方法说明可展开，选择原则必须落到具体决定而不是打分凑齐。
3. **验证与控制**：原测算/路径工具、风险控制/授权及场景结果，分清估算、逻辑验证、仿真与实测。
4. **比较与交付**：同口径方案表、硬约束结果、待核验/未决、接收决定和原资产引用。

理论作为提示：例如选择并行化时询问依赖/资源/汇合/失败；选择自动化时提示输入质量/接口/例外/人工接管。理论作为评价：缺少前提或验证时标“未核实”，不能保存了原则表就通过；有依据的不采用也是合理决定。

界面反馈示例：

| 情形 | 文案 / 操作 |
|---|---|
| 初次进入设计 | 依据已确认问题形成方案，并核验效果、控制和实施条件。 |
| 选择模式 | 采用并行化前，请确认输入依赖、资源和汇合条件。 |
| 模型校验通过 | 模型检查通过，业务有效性与控制验证仍待确认。 |
| 路径枚举 | 静态路径估算；未模拟资源竞争，不用于峰值产能结论。 |
| 关键风险未处理 | 控制验证未通过，暂不能交付试点。 |
| 准备接收 | 提交设计交付；显示版本、范围、未决事项和验证依据。 |
| 已接收设计 | 本版设计已接收，可进入批准范围内的试点准备；尚未证明改善达标。 |

原则与模式标签、能力/错误状态由后端统一下发；原有工具帮助可复用。前端不新写一份根因判断、成本或返工算法；已存在的并行建议只能叫候选，不能代替设计评审。

## 8. 后端与原数据的增量落点

| 内容 | 复用对象/服务 | 增量，不另造台账 |
|---|---|---|
| 设计依据/决定/备选 | Project 的目标/对策/验证、ProjectStep、ToolSheet/ToolTemplate | 结构化原则/模式、根因/元素引用、备选及选择理由；模板明确版本，不靠长文本推断完成 |
| 方案版本/差异 | ProcessModelVersion、process_model.py、designer 画布 | 固定用途/内容引用；差异附原因/责任；不改 Project.current_stage |
| 评价/验收约定 | 薄轮次对照快照、原步骤条件/签收 | 事先固定目标/硬约束/评价依据及接收范围；结果引用原证据，后改不覆盖 |
| 控制 | 原授权/例外、变更影响、FMEA 方法记录、标准文件 | 补控制类型、风险—节点/规则—来源—测试引用；权限/法规变动触发复核 |
| 验证 | 原 simulation/designer 服务、ToolSheet 结果/交付物 | 按能力保存参数/版本/场景/限制；外部仿真报告引用与审核，不先造仿真引擎 |
| 交付协作 | 原评论、ProjectStep/GateAttestation、变更审核 | 指定接收方/期限/核验、精确版本引用；不生成四组平行任务或新阶段机 |

当前代码没有全部上述协作/验证字段。实施按原载体补必要引用与核验，不建设独立方案/发布/验收主库；本专项只定义作业交付，具体字段/API/测试由后续开发计划明确。

## 9. 验证清单与推荐顺序

优先顺序：**统一原则/模式与实际决定的对应 → 固定评价依据与硬约束 → 完善同版验证与控制 → 实现比较接收 → 按需求扩专业仿真。** Flowable 执行不是仿真工具，接入后也不能跳过设计评价。

实施验证至少覆盖：

- 六/七原则版本兼容，历史记录不自动重判；不强制删除节点或采用三种模式；
- 同轮不同方案用同口径比较；评价权重/目标不能结果出来后静默变动；
- 无依赖/容量证据的并行提示不作保证；静态路径截断/循环限制被显式展示；
- 自动化/自助不隐匿客户负担、人工接管和失败恢复；
- 法律/高风险硬约束不能被加权分数或低 RPN 覆盖；
- 规则/模型/测试版本不一致拒绝交付；有改动重核受影响决定；
- 无项目可进行方案草稿；正式改善用薄对照及原项目门禁，不增加阶段状态机；
- 设计评审、上线资格、运行有效、改善达标分别成立，不互相冒充；
- 项目结项后方案/版本/控制仍可查，流程持续执行、监控和复盘。

代表测试扩展 `test_tool_sheet.py`、`test_collaboration_simulation.py`、`test_changes.py`、`test_authorization.py`、`test_strategy.py`、`test_workflow_workbench.py`；前端按当前代码服务跑 verify_frontend，schema 改动跑 Alembic 一致性。上述均为后续验收要求，本次未运行。

**设计环节的结束不是“图完成”，而是“被明确用途的接收方按固定依据接收了这版可验证、风险可接受、依赖可落实的设计”。运行后的真正客户价值，仍留给后续真实样本与验收证明。**
