# 信息架构与页面依赖

这份文档回答三个问题：**“全局”指什么、三层/Q1–Q8 如何映射到页面、页面之间谁触发谁。**
它不是功能清单，而是系统的因果链和依赖关系。

---

## 1. “全局”是什么意思

“开始使用”里的**全局证据进度**是：

> **全公司范围内所有流程、制度、授权、工时、KPI 的证据汇总，不限定某一条试点路径。**

- 计算位置：`app/services/startup.py::status` + `_collect_evidence`；
- 数据来源：`process_arch`、`process_document`、`authorization_rule`、
  `work_measurement_standard`、`kpi_definition/record`、`project` 等；
- “当前阶段”= 第一个必需证据未满足、且未被“这次先不做”的阶段，不是人工设置的项目阶段；
- 9 阶段时间轴和 Q7 用的是同一个判定，所以两者不会各说各话。

它与**十层单页**的“项目当前层”不同：

| 口径 | 位置 | 是否持久化 | 回答的问题 |
|---|---|---|---|
| 全局证据进度 | 开始使用 / Q7 / 时间轴 | 否，按数据库实时计算 | 全公司这套体系还缺什么 |
| 项目当前层 | 十层单页 `pilot_path.current_layer` | 是，退出门满足后推进 | 这条试点路径做到哪一层 |

## 2. 三层与 Q1–Q8

### 地图层：统一认知

| 问题 | 对应页面 / 数据 | 输入 | 输出 | 下游 |
|---|---|---|---|---|
| Q1 要什么 | 战略目标 | 年度经营计划、客户/质量/成本目标、现状数据 | 目标卡、目标值、现状基线 | Q2、Q4 |
| Q2 有什么 | 企业流程地图、组织与人员、交付物、方法工具箱、运营监控 | 现有流程、岗位、制度、工具、KPI | 资产盘点 | Q3 |
| Q3 还缺什么 | 由全部证据派生，无独立页面 | 所有必需证据 | 缺口清单（共同语言/角色/制度/方法/指标/改善） | Q4、Q7 |

### 骨架层：统一语言

| 问题 | 对应页面 / 数据 | 输入 | 输出 | 下游 |
|---|---|---|---|---|
| Q4 做什么 | 企业流程地图、PCF 分类框架、1+3+10 引导 | PCF、流程清单、组织边界 | L1–L3 架构、PCF 映射 | Q5、项目组合 |
| Q5 输入什么 | 组织与人员、流程设计器「权责」 | 组织树、岗位、关键决策事项 | RACI、岗位边界 | Q6、流程设计器 |

### 执行层：逐层推进

| 问题 | 对应页面 / 数据 | 输入 | 输出 | 下游 |
|---|---|---|---|---|
| Q6 用什么 | 流程设计器、方法工具箱、交付物与模板库 | 控制点、表单字段、工具模板 | 表单/规则/工具绑定 | Q7、SOP |
| Q7 输出什么 | 当前阶段工作区（证据地图） | 当前阶段的真实证据 | 证据清单、缺口 | Q8 |
| Q8 下一步 | 十层单页、项目详情、首次上线确认 | 退出门 | 下一阶段 / 上线确认 | 运营监控、改善 |

> 三层不是三个并列模块，而是**同一条路径的三个认知层级**：
> 地图层定方向和差距，骨架层定口径和边界，执行层定方法、留证据、过退出门。

## 3. 页面之间的依赖与触发

### 3.1 主因果链

```text
战略目标
  → 企业流程地图（选 L1–L3、定边界）
  → 流程项目组合（为某条 L3 立项）
  → 流程设计器（L4 步骤、表单、工具、控制点）
  → 流程执行（实例、任务、实际工时）
  → 运营监控（KPI、异常、负荷）
  → 改善项目（红黄指标、异常根因）
  → 变更单 / 新版本
  → 回写流程地图、制度、表单、KPI 基线
```

### 3.2 不是所有页面都是“一步”

- **看板**（管理驾驶舱、运营监控）是**观察面**，不是流程阶段；
- **工具**（架构草图、流程设计器、方法论工具箱）是**能力面**，在需要时被步骤调用；
- **知识库**是**沉淀面**，既消费改善结果，也为下一次设计提供输入；
- **组织与人员、授权矩阵、交付物**是**支撑面**，被多个阶段引用。

把它们强行排成一条“7 步推进线”会制造错误的心智模型，所以驾驶舱已经改成“我的当前推进”。

### 3.3 关键触发关系

| 触发 | 被触发 | 携带的上下文 |
|---|---|---|
| 新建年度目标 | 选择/确认试点 L3 | 目标 ID、目标值、基线 |
| 确认试点 L3 | 创建改善项目 / 十层路径 | 流程 ID、Owner |
| 项目进入设计阶段 | 打开流程设计器 | 项目 ID、流程 ID、当前步骤 |
| 模型发布 V1.0 | 配置流程执行 | 模型版本、流程 ID |
| 异常/红黄 KPI | 创建改善项目 | KPI ID、异常 ID、根因 |
| 变更单批准 | 发布新版本 | 变更 ID、影响分析、回退方案 |
| 新版本生效 | 更新地图/制度/表单/KPI 基线 | 版本号、生效日期 |

### 3.4 数据依赖（当前实现）

- `process_arch`：流程地图、PCF 映射、Owner、项目关联；
- `process_document` / `authorization_rule` / `authorization_exception`：制度与授权证据；
- `project` / `project_step`：改善项目执行进度与下一步；
- `work_measurement_standard` / `capacity_calendar`：标准工时与产能；
- `kpi_definition` / `kpi_record` / `exception_event`：绩效与异常；
- `pilot_path` / `pilot_layer` / `pilot_task` / `pilot_issue`：十层试点路径；
- `startup_step_skip` / `startup_pilot_confirm`：全局证据的跳过与首次上线确认。

## 4. 行业最佳实践对应的逻辑

### 4.1 战略到执行

- **战略决定选择**：先定“打哪一仗”，再选承接它的 L3；不是先建全量流程。
- **架构定边界**：PCF 只做骨架，L4/L5 是公司本地模型，不照抄。
- **组织定责任**：每个 L3 一个 Owner，每个关键事项恰好一个 A。
- **制度定规则**：授权按风险/金额/影响/可逆性/频率分级，例外必须有时限和审批人。
- **流程定顺序**：L4 活动定义输入、输出、角色、控制点。
- **表单/工具做载体**：表单记录事实，工具固化控制，不能反过来支配流程。
- **工作量做配置**：先方法、再观测、再标准；标准工时只做能力基线。
- **绩效做验证**：2–5 个结果/过程/健康度指标，红黄绿阈值，异常闭环。
- **改善再升级**：PDCA/轻量 DMAIC → 变更单 → 新版本 → 知识复用。

### 4.2 单一事实源

- 项目执行进度只有一个源：`Project/ProjectStep`；
- 全局证据进度只有一个源：`startup` 服务；
- 试点路径当前层只有一个源：`pilot_path.current_layer`；
- 不把“记录数”当“就绪度”，不把“跳过”当“完成”。

### 4.3 证据门禁

参考 ISO 9001 审核思路，每一步至少回答：
**需要什么信息开始？负责什么决策？结果是什么？保存什么记录？出问题怎么办？何时改变？**
这就是“输入/处理/输出/退出门/证据/异常/改善/版本”的来源。

## 5. 当前实现与待补

已实现：

- 开始页 Q1–Q8 的页面映射与“前置/输入/输出/下一步”提示；
- 全局证据进度与十层项目当前层的区分；
- 驾驶舱“我的当前推进”替代静态 7 步横条；
- 十层单页第 4 层的制度—授权—证据—改善—退出门闭环。

待补：

- 页面间带上下文跳转（如设计器直接打开某项目/某流程）；
- URL 可分享到具体项目/层；
- 版本基线/草稿/发布差异；
- 七张地图的独立聚合与运行数据回流。
