# 流程建模与流程仓库：标准、适用性与资产协同对标

> 状态：待评审设计；基线 `ca20f88`，静态核对，不代表运行/安全/标准认证已完成。
> 综合评审契约：[产品基本原则](bpm-product-principles.md)。现状/方案是待实现的同一设计器用途；参考/分析版本固定与运行发布分开，不能声称当前已具备无损全标准建模。
> 对照：用户提供的流程建模讲义，重点为标准符合性与流程仓库。
> 约束：[闭环路线](bpm-lifecycle-gap-and-roadmap.md)、[落地规格](bpm-lifecycle-implementation-spec.md)、[表达规范](bpm-interface-content-standard.md)。
> 本次只形成评估与推荐，不修改业务代码；不新增第二套模型库、项目引擎或提前建立 Flowable 部署表。

## 1. 结论

**当前不是“画完存桌面”的纯绘图工具：已经有流程仓库底座；但尚不能称为标准符合性和资产协作都可靠的企业模型仓库。**

已有数据库模型/版本、完整 XML 保存字段、草稿/评审/发布、差异/回滚、并发版本号、元素评论、Owner 权限及交付物引用。真正需要补的是：

1. 把 BPMN 标准规则、企业建模规范、业务完整性和引擎能力明确分开；
2. 把校验从界面建议落实为服务端权威、按用途执行的门禁；
3. 精确版本上的讨论、业务确认、依赖、复用来源和变更影响；
4. 可检索、可复用、可受控分发、可持续复审的资产工作方式；
5. 与同一流程/轮次的样本、规则、标准、培训及验收关联。

目标不是“增加绘图功能”，而是**让正确的模型成为能共同理解、按授权使用、长期维护和追溯的企业资产**。

## 2. 先区分四种“能用”

| 用途 | 最低可用要求 | 不能由什么替代 |
|---|---|---|
| 沟通/知识 | 结构及符号语义清楚，边界、客户结果、角色、关键异常已由业务确认 | 画面整齐、格式没有报错 |
| 分析 | 符合所选分析方法的模型与数据，来源/假设/版本/范围明确 | 合规 XML 自动推导实际耗时或真实因果 |
| 自动化 | 标准/语义检查通过，且处于已验证的引擎支持范围，字段、权限和运行配置齐备 | bpmn-js 能画、导入能解析、前端 lint 无错误 |
| 合规证据 | 控制点、制度/法规版本、责任、执行证据和审核决定可追溯 | 语法合规、名称含“合规检查”、流程图本身 |

“符合 BPMN”是模型技术质量要求，不自动证明实际业务正确、符合法律或能在任意引擎运行。可读性和布局是必要的沟通质量，但不是技术语义与业务真实性的替代品。

## 3. 讲义口径需要校准的地方

本次查阅了 OMG 官方规范入口和 Flowable 文档；OMG PDF 已获取，但本地无法解析，未逐条核验全部规范条款。因此以下应区分已见官方实现说明、工程判断和待规范条文确认项，不声称已获 BPMN 认证。

| 讲义/常见说法 | 规格应采用的表述 |
|---|---|
| 每个流程必须有且只有一个开始事件 | 不能作为通用 BPMN 硬规则。Flowable 官方文档明确有一个流程定义包含多个消息开始事件的场景；当前单令牌引擎可限制唯一入口，但须标“当前运行限制”。具体开始类型和作用域按规范及引擎 profile 校验 |
| 泳道只能写角色，系统名是架构图内容 | 可以是企业规范的角色视角要求，不直接等同 BPMN 通用禁止。系统任务、参与方和责任角色需要分清；Pool、Lane 的规范约束必须独立核验，不靠名称猜测合法性 |
| 网关进得去也出得来 | 不足以保证正确。分流、合流、条件/default、并行同步、包容分支、事件竞争和作用域都需要按语义检查；不能把所有汇合都改排他网关 |
| BPMS 可以直接执行 BPMN 模型 | 仅限可执行且被目标引擎支持/配置完整的子集；描述性图和导入成功不等于可执行 |
| 一张流程图证明法规合规 | 模型可以组织控制设计证据，法规符合与控制实际有效仍需有权人员按来源和执行证据判断 |
| 标准只包括事件/活动/网关/泳道 | 这是入门摘要，不是完整 BPMN 分类；连线、参与方、数据与工件等也影响交换与语义，不应从校验范围遗漏 |

特别要复核当前 lint 文案：`sub-process-blank-start-event` 的建议可能误导用户给普通嵌入子流程添加带类型开始事件；`fake-join` 一律建议排他网关也不适用于真正的并行同步。此处先标为待修正规则解释，实施前用所选 BPMN 规则版本和真实样例验证，不能直接照中文描述改图。

官方来源：

- OMG BPMN 2.0.2 入口及规范/schema 清单：<https://www.omg.org/spec/BPMN/2.0.2>。
- Flowable 构造说明：<https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs/>，含 Message Start Event、Parallel Gateway、Inclusive Gateway、None/Error Start Event。其支持限制是 Flowable 行为，不等于所有 BPMN 模型的标准约束。
- 用户讲义中的 ABPMP Competency Model v1.5/2019 注释及 CBOK 相关原文，本次未核原件；不能把一段可能的作者意见直接当成组织正式承认遗漏或能力分级结论。Repository 的业务必要性可直接论证，不依赖未核引文。

## 5. 标准校验：分层、按用途、后端权威

### 5.1 五层规则，不混称“标准错误”

| 层 | 检查什么 | 示例 | 谁提供依据 |
|---|---|---|---|
| 文件/交换 | XML 安全、命名空间、ID/引用、所用 schema、DI 与扩展保留 | 引用不存在、损坏 XML、外部实体、超限输入 | 后端解析/schema；禁外部实体/网络加载、限制大小/深度/复杂度 |
| BPMN 结构/语义 | 事件与作用域、连线类型、网关同步、条件/默认、子流程与消息 | 消息流/顺序流边界、错误事件捕获关系 | 明确规范来源和版本的规则实现；XSD 通过不足以证明语义正确 |
| 企业建模约定 | 命名、视角、层级、粒度、布局、负责人 | 动宾命名、泳道角色视角、复杂度提示 | 组织批准的规范版本，不冒充 OMG 强制 |
| 业务完整性/真实性 | 客户/边界、正常/异常、控制、数据、执行责任及业务确认 | 入职未考虑账号开通失败、客户交付未定义 | 业务核验清单、原记录和授权评审 |
| 分析/运行能力 | 目标用途是否被实际实现支持 | 并行可用于建模，但旧引擎不能执行；算法不支持并行则不算 PCE | 测试过的 engine/analysis capability profile |

不能宣称普通静态校验器完整证明任意模型的无死锁/正确终止；对未覆盖的动态语义显示“未验证”，复杂情形结合 token 场景测试或专门分析工具。

### 5.2 一致的校验结果

每个问题至少包含：rule_code、rule_version、domain、severity、element_id/scope、message、reason、remedy、阻断哪些用途、是否可豁免及依据。中文标签由后端下发，前端只负责定位与展示。

结果绑定精确 model_version_id 或未保存 XML/hash、用途和 capability_profile；修改模型使旧校验不再代表当前内容，前端清楚显示“结果已过期”。校验器失败与校验未通过分开；0 个问题但规则未成功运行不能显示“通过”。

前端 lint 作为快速编辑提示，服务端对发布/复用/导出所需用途重新核验同一内容；不能要求调用方先从 UI 点击验证。所有发布/回滚发布/导入发布路径通过同一门禁，拒绝版本竞争期间的旧结果。

### 5.3 保存与使用准入分开

- **保存草稿**：允许业务尚未完整，但必须安全解析、能保留原语义；不可损坏的内容/引用错误给明确处理。不能为了“可保存”静默降级不支持元素。
- **共享评审**：具备沟通所需边界、名称和内容，保存版本/哈希，列出未决项。
- **作为分析输入**：语义及该分析口径满足要求，实际/假设来源明确，固定轮次/样本引用。
- **发布到当前运行时**：标准和当前执行 profile 无阻断错误，业务/授权/表单/规则齐备；上线就绪至少有已发布模型行，不再造部署 ID。
- **Flowable 接入后运行**：追加经过验证的引擎 profile 和部署映射，不能提前将全部 BPMN 符号标“可执行”。

可只读保留符合标准但当前引擎不支持的参考模型时，应明确“仅建模/不可运行”，完整无损保存是前提；若当前存储管线不能保留，则拒绝导入并说明范围，不声称已经支持。

## 6. 流程仓库：复用已有存储，补资产协作

Repository 是对现有流程及模型版本的统一资产视图和管理能力，不另建一棵模型目录或复制整套 XML。

### 6.1 一项资产至少能回答

是什么流程、服务什么客户结果、Owner/适用范围、当前用途（现状/方案/参考）、模型/发布版本、标准规范与运行支持范围、校验/业务确认状态、来源/派生关系、关联规则/数据/制度、谁在使用、何时复审、谁可看/改/批/下载。

资产状态与用途分开：As-Is/To-Be 是模型在某轮对照中的角色，不是“已发布”的同义词；一个不可变版本可在不同轮次复用，不能通过复制流程树来实现。

### 6.2 能力与操作

| 能力 | 用户操作 | 推荐落点/规则 |
|---|---|---|
| 查找 | 按流程、名称、Owner、用途、有效版本、组织、规则/活动查询 | 在现有地图/流程卡增加“模型资产”筛选/列表，进入同一 designer，不加并列主库 |
| 理解 | 预览图、用途、来源和支持范围 | 版本摘要与模型说明；原图只读预览，不需下载到桌面才能看 |
| 复用 | 引用现有版本，或从该版本派生草稿 | 引用钉 ID；派生记录 source_model_version_id/lineage；新目标流程/ID 由原服务创建，权限与适用性确认；复制不是自动批准 |
| 评论评审 | 在某版某元素讨论、答复、关闭并核验 | 扩 ProcessComment 的 model_version_id/hash 及范围；不随下一版同名 ID 自动迁移“已解决” |
| 冲突处理 | 保存时识别他人变更，查看差异后决定 | 保留 expected_version，禁止静默覆盖；多人实时协作不是当前已有能力，不为本轮引入 CRDT |
| 差异与影响 | 看元素/条件/数据/配置改了什么、影响谁 | 沿版本引用查项目、实例、标准/交付物/培训/规则；复杂 XML 不仅比较节点数量 |
| 更新和复审 | 提变更、批准新版本、通知受影响人 | 原变更/评审/审计；必要责任/复审期限补原记录，不生成平行治理任务 |
| 分发与留存 | 按权限导出、停用、保留历史 | 下载审计、版本/用途标识、许可/敏感信息范围；有历史引用的模型禁止普通级联删除 |

首期正式复用可先支持“原版本引用”和“整模型派生”，不必同时实现复杂片段库；若只允许导出再导入而不保留来源，不能称为完整受控复用。

### 6.3 协作不是有评论按钮就完成

业务人员确认“真实/清楚”，数据/分析人员确认“能作输入”，IT 确认“支持范围/字段/运行”，风险负责人确认“控制/制度依据”，Owner 接受整体责任。按实际用途裁剪参与者，不机械要求所有人签每张图。

评审决定引用精确版本和问题清单；模型变了要判断哪些确认失效。关键未决评论由授权人解决或记录批准例外，不能由任意人把所有评论标 solved 后自动发布。仍可保留非阻断讨论，不把每条评论都变成硬门禁。

## 7. 建模作业链：从建模任务到仓库可用资产

编号 M0–M6 仅为工作指引，不是新状态机，进入现有 designer 的现状/方案模式。

| 指引 | 做什么 | 产出 / 接收要求 |
|---|---|---|
| M0 定目的和范围 | 选择客户结果、流程、视角、用途及使用者；先检索是否已有有效版本 | 明确建模任务，不为同一流程重复开一棵目录 |
| M1 收集实际事实 | 走查正常/异常、输入输出、角色/系统、规则和来源；假设标注 | As-Is 证据或 To-Be 设计依据，制度不自动等于实际 |
| M2 选择表达 | 使用符合用途的 BPMN profile、池/道、层级、活动与数据规则 | 语义正确、细节适度，不为了图简单删掉真实并行/异常 |
| M3 校验与场景走查 | 分层自动校验，按业务样例回放路径，修正错误 | 精确版本的校验结果、正常/边界/失败场景说明 |
| M4 跨角色评审 | 明确业务、分析、IT/风险等需确认的内容；解决关键问题 | 版本/哈希绑定的确认、未决与裁剪依据 |
| M5 入库并关联 | 固定模型版本、Owner/用途/来源、原规则数据/标准引用；必要时绑定轮次 | 可查找、可预览、可引用的资产；不要求先建改善项目 |
| M6 使用与维护 | 经准入用于分析/执行/培训；变更时查影响、派生、复审 | 有使用与变更反馈的资产；项目结项后仍可持续维护 |

真正完成建模，不是最后一次保存，而是**目标使用者能够按约定用途接收、使用并持续维护这项版本化资产**。运行资格和业务绩效需要后续分别验证，不以建模验收代替。

## 8. 两个讲义场景怎样验收

### 8.1 采购金额分支

至少验证 <5000、=5000、>5000、缺金额、非法币种/单位或负值的处理；示例阈值不灌成全公司政策。两条路径都完成必要审批后创建订单，明确拒绝/退回/取消与外部建单失败。

标准语义、规则来源/批准和引擎路由分别检查。重复建单应有集成幂等方案，不因为图上只有一个“创建订单”节点就认为不会重复。模型说明与边界用例进入仓库，后续复用知道其适用范围。

### 8.2 员工入职

HR 发通知后，IT 账号、行政工位、经理导师在业务允许时可并行；迎新/完成是否等待各项，由实际入职交付条件决定。IT 故障必须有可理解的处理/升级路径，不为适应旧引擎就把真实并行画成串行并声称真实 As-Is。

当前引擎不支持并行/边界/子流程：说明“标准建模场景与当前运行支持存在差距”。无损保留参考模型和可执行模型分用途，待 R3 验证后才运行并行场景。角色/人员、账号系统、外部服务分别表达，不靠泳道名字确定所有语义。

仓库交付检查：有模型用途、来源与版本；可查/预览；评审绑定该版；规则/数据/异常可打开；权限和复用来源明确；换人后仍能理解和继续维护，而不是只保留一张好看的图片。

## 10. 推荐优先顺序

1. **先保证可信**：规则分域、修正文案、服务端发布准入和不支持元素不静默降级；结果绑定精确内容。
2. **再保证可交付**：业务走查、用途化验收、固定版本、评论与确认绑定版本、被引用资产保护。
3. **完善仓库协同**：统一查询预览、引用/派生、使用和影响分析、权限/复审/留存；复用原表和入口。
4. **最后扩展覆盖**：按业务优先级验证更多 BPMN 构造及 Flowable 能力，不以开放更多图标替代执行与资产治理验收。

**产品底线**：漂亮且容易上手是体验；按标准正确表达是最低技术质量；按用途被业务接收、可复用可追溯并被持续维护，才是流程建模作为企业资产的完成标准。
